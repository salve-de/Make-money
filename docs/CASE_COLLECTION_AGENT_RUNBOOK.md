## 0-1. 2026-10-15 最新読者向け編集ルール（全担当者・Codex）

**【2026-10-15 オーナー最新指示：読者向け記事のノイズ禁止・全AI必須】** MAKEMONEYの通常の成功事例は、誰が・何を・誰に・どう売り、どのように顧客を獲得し、どのような結果を出したかを具体的に伝える読み物にする。公開画面には、数字や事実の説明に必要ない「利益ではない」「これは売上であって利益ではない」「売上構成比は調査記録に残す」「記事には載せない」「具体的な単価は不明」「誰でも成功できるわけではない」「出典の照合が未了」等の断り書き・執筆者メモ・調査上の事情を一切混ぜない。例えば広告枠を103万ドル売ったなら「広告枠の売上は103万ドル」など事実を肯定形で簡潔に説明し、「利益ではない」を補足しない。実際の売上を利益・手取りと誤称することは引き続き禁止。売上と利益の区別、原価、赤字、損失、制約、不明点、矛盾、権利・QA状態は内部research/qaに正確に保持する。通常の成功事例の見出しや冒頭に、赤字・失敗・一般的リスクをわざわざ掲げない。失敗から成長に至る明確な転換点など、成功の実際の経緯を理解するために不可欠な場合だけ必要最小限に触れる。事実をねじ曲げて黒字や高利益に見せることも禁止。掲載する情報は「読者にとって価値がある具体的な事実・工夫・販売実績」から逆算して選び、調査原本の範囲は狭めない。編集・受入・検査担当AI（Codex含む）はこのルールを適用し、違反する原稿を公開用完成扱いにせず修正候補を記録する。これは**表示内容の編集方針**であり、元データ・承認・権利ゲートを弱める指示ではない。

## 0. 完成目標／状態の区別

目標は、事業・サービス・現場・小規模商売・企業など**種類にかかわらず、読者が価値を感じる完全な事例記事**を自動で作ること。将来1万件・1億件でも、完成記事の品質を意図的に下げない。

- **調査候補数 ≠ 完成した記事数 ≠ R2保存成功数 ≠ UIで読める件数。** それぞれを別に報告する。
- 自動収集で従来形式の調査JSONができただけでは、新形式の `article.json`・図解・独立検査が完成したことにならない。
- `ready_for_review` は掲載承認ではない。審査未完了なら本番公開に進めず、差戻し・保留にする。
- 「材料が少ないから簡単な記事にして完成」ではない。重要情報を追加調査し、それでも欠ける事実は捏造せず、確認できた価値ある内容で編集する。内容全体が理解不能なら完成を宣言しない。

## 1. 新規事例を引き受ける前の確認（スキップ不可）

1. **最新の対象と正本**：GitHubのdefault/mainと未マージPRを確認する。PR #224（新記事形式）、#225（本方針）、#226（Sleep Jar検証例）など、該当する実装の最新状態を読む。未マージの仕様を本流の実装と偽らない。
2. **重複防止**：既存事例の安定ID、ドメイン、社名・別名、買収・社名変更、作業予約 `data/CLAIMED_TARGETS.txt`、候補キューを照合。他のAIが先に確保している同一事例を重複収集しない。予約操作の書込経路と権限を守る。
3. **保存権限と権利**：本番R2・公開ポインタ・本流・定期実行・外部API課金は明示許可なしに変更しない。著作物の収集・保存・商用表示は別の判断。ログイン壁・CAPTCHA等は越えない。
4. **個別の事業の理解**：出典を見て実際に「何を売っているのか」を把握してから書き始める。一般的な業界説明や目標だけで記事を始めない。

## 読者に見せる価値の選別（必須の編集判断）

収集した有益な情報を`research.json`から捨てることと、記事に載せないことは別。**初見の読者が『こういう商売か』『こうやって売ったのか』と理解できる具体的な新情報**だけを記事に出す。

各見出し・段落・箇条書き・代表数値・表の行・年表・図解を保存する前に「この一項目で何が新しく分かるか」「本人固有の実行と成果か」「他章で説明済みではないか」「削除しても理解が変わらないか」「普通の日本語として自然か」を判定する。消しても読者の理解がほぼ変わらないなら、記事から外し元研究は保持。意味が通らないが重要なら追加調査して書き直す。本文を増やすためだけの一般論・『利益ではない』等の否定注記・内部監査メモ・重要でない細かな契約条件・図解のノルマは不要。**この判断は項目ごとの価値の編集であり、単なる文章の短縮や機械的な点数付けではない。**

## 2. 編集に着手する前に、必ず内部で決めること

調査で広く事実を集めた後、記事を機械的に各表示分類へ割り付ける**前**に、内部の編集メモを作る。これは読者の画面に出すための質問項目ではない。

- この商売の**主役**は何か：その事例だけに固有の「商品・仕組み・実行した工夫・結果」から、初見の読者が興味を持ち、事業を理解する最重要の事実を選ぶ。
- 何を見せれば商売として理解できるか：**商品／客／対価／提供の仕組み／集客／運営／主要な数字／転機**のうち、今回の記事で意味がある要素と根拠を選ぶ。
- 重要事実を**主役・重要な補足・内部記録のみに残すもの**に分ける。固有性・根拠・具体性・読者の理解への寄与で判断する。単に数値が大きいという理由で最上位にしない。
- **章間の所有者**を決める。例：集客の具体策は集客章、資金と料金はお金章、年代と転機は経緯章。「成功理由」は前章の文章を複製せず、関連する事実を別の観点から短く解釈する。
- 最も理解を助ける視覚素材は何か。商品の姿→権利確認済み実画像、関係者や商流→図、時間推移→グラフ、工程→手順、変化→前後比較、転機→年表。**重要な内容が伝わらない図なら作らない。**
- 調査に不足があれば追加調査する。特に実際の顧客獲得・商品利用方法・課金の流れ・実務の工夫を一次資料から探す。利益や原価の数値そのものを全事例へ要求しない。

このメモは納品の `editorial-plan.md` 等の内部資料、または既存スキーマの編集記録に保存する。表示記事へ長い「考え方」を掲載しない。

## 3. リード見出し・導入文：読者が開きたくなる情報を最初に

**見出しの主役は「その事業は何をしたか・何の仕組みか・結果はどうなったか」。** 創業者の私生活の面白い話や取材の導入があっても、事業の本質を押しのけない。

### 見出しに優先する内容

- その商売特有の商品・工夫・仕組み・行動と、確認できた結果を、普通の日本語でつなげる。
- 件数・金額・顧客数が強い根拠付きなら使う。**実績の種類と時点**を誤認させない。数字がなくても具体的な商売の仕組みで魅力的に書ける。
- 「○○に答える」「なぜ○○なのか」「成功の秘密は」などの**設問を本文の代わりに置かない**。分かった内容を直接伝える。
- 見出しを大げさな煽り、人工的な二段のドラマ、曖昧な「サービスへ成長」だけにしない。小説・人物紹介より事業解説を優先する。
- 導入文は見出しを言い換え直さず、**商品・客・課金／販売の関係**など新しい情報を加える。見出しと導入文と数字帯で同じ数字・エピソードを3回繰り返さない。
- 良い見出しが決められないなら、キャッチコピーを生成し続けるより**「主役の事実が収集できていない」可能性**を再検証する。

### 2026-10-14 に実際に採用された例（決して全ジャンルへ流用しない）

**Sleep Jar の承認済み見出し（表記を勝手に直さない）：**  
「**犬の鳴き声対策に作った雨音音源が、有料会員10万人超のサービスに**」

**採用しなかった方向：**  
「朝6時、隣人の犬に起こされる。」から始め、創業者のエピソードを記事の主役にする方式。

違い：犬の鳴き声は商品の開発経緯を伝える手段であり、**記事の主役は雨音音源の事業化と有料会員の獲得**。最初の数行だけで「何のビジネスか」が把握できなければ見出し不合格。Sleep Jarの「有料会員10万人超」は2022年6月時点の当事者公表値なので、現在の会員数だとは書かない。

他の事例では、別の具体的な工夫・顧客獲得・結果を中心にゼロから見出しを作る。**Sleep Jarと似た「AをBに変えてX万人」型を大量生産しない。**

### 一覧・詳細・導入・数字の役割を混ぜない

| 掲載欄 | 役割と合格条件 |
|---|---|
| 一覧の1行（`listLine`） | 一覧を流し読みして**何の商売か・なぜ読む価値があるか**分かる短い紹介。会社名だけ、業種名だけ、抽象的な成功物語は不合格 |
| 詳細見出し（`headline`） | その事業固有の工夫・商品・ビジネス構造と、根拠のある結果を**読者に直接伝える**。人の私生活の導入や「○○とは？」だけなら不合格 |
| 見出し下の導入（`lead`） | 何を売り、誰がどう使い、どこから収入があるかなど**見出しになかった補足**を与える。見出しを語順だけ変えて繰り返さない |
| 主な数字（`kpis`） | その事例で重要な事実を少数、時点・単位・意味と一緒に示す。同じ情報を大小で何度も強調しない |
| 章見出し（`topics[].title`） | 一章で読者に新たに分かる具体的な内容を言い切るか、自然に内容を示す。AIが作った分類語や無意味な問いは避ける |

`listLine` と `headline` は別の画面に置かれるため、同じ重要事実を別表現で伝えてもよい。**同一画面の headline・lead・KPI・概要で同じ説明を延々と繰り返すのは不合格**。

### 見た目と文章の役割

リード・headline・KPI・画像は現在の共通UI部品が描画する。**本文と図を改善するために既存の暗色・セクション見出し帯・罫線・目次を勝手に変更しない。** スマホ本文の小さすぎる文字は共通UIの課題として検証・修正対象にする。記事ごとに独自CSS/HTMLを足さない。

## 4. 決まっている事例詳細UIの本文7分類＋別枠出典

| 章 | 最初に伝えるべき中身 | 避けること |
|---|---|---|
| 概要 | 具体的な商品／誰がどの場面で使う／なぜ選ばれるか | 見出しの言い直し・他の章で詳しく書く経緯の重複 |
| 仕組み | 商品が届く／機能する手順、売り手・客・仲介者・技術の関係 | 中身が見えない抽象的な「3段階の仕組み」図 |
| お金 | **誰が何の対価に払い、どう収入が生じるか**。料金・売上・費用・利益のうち有用な確認済み情報 | 利益や採算を全件必須にする、別時点の数字を掛けて会社の売上を推定する |
| 集客 | 最初とその後の実際の客の獲得方法。どこに何を出し、どうなったか | 「SNSで拡散した」だけ、媒体名の列挙だけ |
| 運営 | 誰が何を制作／配達／維持し、どんな設備・人手・外注が必要か | 仕組み章の取引図を繰り返す |
| 経緯 | 開始・転機・方向転換・失敗。結果を変えた事実を年代順に | 他章の詳しい文章の再掲や全イベントの年表化 |
| 成功の理由 | その会社の具体的な工夫と顧客が買った理由、実際の行動・結果の結び付き | 失敗／リスクの羅列、抽象的な成功法則、集客や仕組みの単なる言い換え |
| 出典 | どの数字・出来事をどの資料で確認できるか | 出典を本文の主役にする、許可のない原文や画像の大量転載 |

**現在の新記事UIは本文7分類＋別枠の出典**。目次には『概要・仕組み・お金・集客・運営・経緯・成功の理由・出典』の最大8項目がこの順で出る。実際の本文分類は `overview / mechanism / revenue / acquisition / operations / history / reasons`。『成功の理由』を独立分類として保持しつつ、他章の重複を水増しせず具体的な発見がある場合にだけ表示する。内容がない任意章は出さず、文章・図・表の数は事例に合わせて変える。

## 5. 図解・数値：完成前に「図を見た読者」を試験する

図ごとに次の3点を**作成前**に一文で書く：**この図から読者が何を理解するか／根拠となる記録ID／他の部品より図が優れている理由**。

- **見出しは、問いかけではなく図から分かる結論**にする。悪例「無料でも聴ける。有料で増える内容は何か」。改善例「有料会員は睡眠物語178話・瞑想100本を聴ける」（Sleep Jarの当時のデータ）。
- 図中の「利用者」「Sleep Jar」「プレミアム」を矢印で結ぶだけなら、結局何の行動・商品・お金か分からない。各矢印に実際の行動（聴く、支払う、納品、手数料等）が正確に分かる言葉を置く。関係が簡単なら**図を作らず文章にする**。
- **同じ数値・同じ時点・同じ単位**で比較できる場合だけ適切なグラフを作る。異なる時点や企業の財務数値を架空の推移に変えない。無料と有料の件数は「何の収録数か」「何話・何本か」「いつの仕様か」を明示する。
- **UIでの実際の横幅**を想定する。モバイルで縮小すると小さすぎる文字の図は不合格。必要なら縦積み・要素分割・拡大表示を使う。デザインは共通部品・既存の暗色系統へ揃える。
- 図解の元数値や矢印は調査の recordKey に結び、読者向けの図には説明に必要な情報だけを載せる。画像を無許可で転載しない。

## 6. 納品契約（1件を完成させる時）

対象の現行GitHubスキーマ・バリデーターを先に確認し、その**実際の名前・形式**で以下を作る。Sleep Jarの完成前パッケージを参考にするが、誤りや弱い図をコピーしない。

```text
data/case-articles/<安定した事例ID>/
  research.json             取得事実・数字・原典・時点・権利・未確認・矛盾
  article.json              読者向けのリードと章／図表の配置／根拠参照／編集記録
  figures/<内容に適した図>.svg  （必要な場合。原典事実に根拠を結ぶ）
  README.md                 素材・編集判断・検査と未完了・引継ぎ
```

必要な場合は、現行の *既存CLI* で生成する表示用 `data/case-articles.json` と身元の登録記録を整合させる。**生成物を手書きでしか更新できない運用にしない。** 調査資料からの文案・編集判断・図中の文字が自然であることを一貫して確かめる。

- **担当を分けられる場合**：調査役→編集役→図解役→独立読者役→原典・権利検査役。各段階で同じ情報の定義を共有するが、後段は単に前段を褒める役にしない。
- GitHubに書ける場合：新規ブランチ・PR等の既存手順を使い、元の記録・原稿・図・検査結果を保存し、読み戻す。変更権限のない場合：**同内容を自分でDLして引き継げる一式**として納品し、GitHub保存済みと偽らない。
- R2に書く場合は既存Foundation保存契約と明示許可が必要。**GitHub納品・ローカル表示・R2に保存・本番公開は別の完了条件**。
- 同じ情報を別AIが調べる時は対象の固定IDを渡し、独立検証か新規収集かを区別する。必要な原典がない事実を埋めず、編集し直しても調査記録を上書きしない。

## 7. 独立QAと差し戻し

各記事を**実際に初めて読む人の視点**で判定する。単なるチェック欄の全てPASSや、別AIの「高品質です」の自己申告だけでは完成ではない。

### 読者テスト（人・独立AIの両方で評価）

1. **冒頭だけで**何を売る事業で何が特有か分かるか。人物の経歴・動機しか書いていなければ差し戻し。
2. 章ごとに「読者が新たに知る具体的なこと」を一つ以上言えるか。単なる同じ話の言い換えなら差し戻し・統合。
3. 5秒で目に入れるべき主要情報は正しく強調されているか。金額の大きさだけを目立たせ、商品や収益の仕組みが見えないなら差し戻し。
4. 見出し・章の見出し・太字だけでも商品・収益・集客・実務の要点が把握できるか。
5. **お金の実体**（誰が何のために払うか）が分かるか。原価・利益が無いというだけで失格にしない。分からない採算を想像で埋めていたら失格。
6. 図解を1枚ずつ見て「図の意味」「視線の順序」「何が正しい事実か」が分かるか。**意味不明なら図を作り直すか削る**。
7. 実物の商品・サービスが一度も視覚的に分からない場合、利用許可された実画像や画面を探し直したか。無理なら実際の画面へ誘導する外部リンク等で補ったか。
8. スマホで本文が小さくないか。長いタイトル・図のはみ出し、操作不能、目次、出典リンク切れはないか。
9. 同じ事実が見出し・概要・お金・集客・経緯・理由に重複していないか。**文面が違うだけの意味的重複も検出**し、特に章の役割が同じ場合は1か所へ統合。
10. それぞれの数字の**期間・通貨・指標・対象・出典**は一致しているか。過去の会員数と今の価格で現在の売上を推計していないか。

- **差し戻し結果**は `stage / location / problem / evidence / proposed_remedy / retry_count / final_status` 相当で記録。原因が原典不足なら「再調査」、文の弱さなら「再編集」、不明瞭な図なら「視覚部品再選定」、権利なら「素材差替」、表示崩れなら「共通UIの修正」へ戻す。
- 既存の `pnpm case-articles:build --check`、lint、型、モバイル表示テスト等、今の実行環境で使える検査を実行。**通過した検査の名前と出力**を記録。実行できない検査は NOT_RUN とする。
- 評価者が根拠なく「全て理解できます」と返した場合は検査合格にしない。**その読者が一文で説明できた具体内容と理解に必要だった箇所**を根拠として残す。
- 不合格でも形式合わせ・短文化・図解の削除だけで「合格」を演出しない。重要情報の調査や図の意味が不足する場合は前段へ差し戻す。

## 8. 今後の自動処理・ほかのAIに対する具体的な運用

`case:discover`、`case:research`、`case:run` は現在の従来形式で動く経路。**この指示書を追加しただけで、これらが新7セクション＋自動図解を作るようになったとは扱わない。**

本当に自動化するには、既存の研究記録から**編集計画→根拠付き記事原稿→内容に即した図解→独立QA→ローカルUIプレビュー→承認を経た保存**を構築し、収集を初回実行した未知の業種混在事例でエンドツーエンド検査する。自動実装が間に合うまでは、ほかのAIにこの文書を渡し、各段階を順番に実行・納品させる。

### 依頼主が他AIに渡す一行（既存の最高運用契約に従う）

> **「GitHubの `docs/DATA_COLLECTION_MASTER_GUIDE.md` を読め。」**

マスターガイドの冒頭から本書まで自動で読み進めさせる。依頼主に長い指示文や追加の入口指定を求めない。依頼内容に実行対象や許可が必要なときだけ、その具体条件を既存の会話・依頼から読み取る。

### 最後の報告様式

`case_id`、公式の識別子、調査範囲と出典、作った章、調査記録数、図・画像、編集方針、出典と記事の参照整合、実際に行った検査と未実行の検査、差し戻しと未確認、GitHubパス・PR・ハッシュ、R2保存の成否、本番UIの成否を**別々**に報告する。

**一件が出来たように見えたことと、全ジャンルで1万件・1億件を高品質で自動制作できることは別。** 対象ジャンルを変えて反復検査し、未検証の部分は未検証として報告する。
