# 画面の1文から元の事実へ辿る（設計）

2026-10-07 夜のオーナー指示への設計です。指示は「UIに出す内容から、収集の段階まで、本当に問題なくできているのか」。
画面の1文 → 事実ID → 原文の引用 → 出典URL を機械で辿り、辿れない文や元の事実と食い違う文は画面に出しません。

## 今の切れ方（2026-10-07 実測、公開10件、main 9882c43c）

画面に出る行を全部数え、照合結果（`data/reader-verdicts.json`）の引用まで辿れるかを確かめた結果です。

| 画面の欄 | 行 | 引用まで辿れる | 切れている所 |
|---|---|---|---|
| 一覧の文 | 10 | 10 | なし（`factId`＋`factHash`） |
| 概要 | 10 | 10 | なし |
| 成功の秘訣 | 39 | 39 | なし |
| 分析欄（隠す行を除く） | 94 | 94 | なし（`analysisId` → 分析の `basis`） |
| 数値の帯 | 26 | 26 | なし（数値の id で照合結果を引く） |
| **章** | **328** | **0** | **事実IDを持たない。229行は、出典URLがその事例の照合済みの出典に無い。59行は同じ出典の事実が複数あって決まらない。1つに決まるのは40行だけ** |

原因は2つです。

1. 章の10件分は、照合済みの事実を通らずに `data/case-chapters.json` へ直接書かれた（6e8d3756）。その時に読んだ外部の出典（本人ブログ・別のインタビュー・保存版など）を引いているため、照合の対象になっていない。
2. 画面の層を作る道具でも、AIが行ごとに返した `factId` を出典URLに変えた時点で捨てている（`src/shared/display-build.ts` の `assembleDisplay`、章の組み立て）。作り直しても事実IDは残らない。

## 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| D1 | 章の行に `factId` と `factHash` を保存する（`{ text, source, factId, factHash }`）。`source` は `factId` から機械で付ける | 他の欄と同じ結び方。AIには事実IDだけを書かせ、URL・指紋は機械が付ける（表示の層の既存の決まり） |
| D2 | 辿りの検査 `pnpm display:trace`（純関数 `src/shared/fact-trace.ts` と道具 `scripts/reader-case/trace-check.ts`）。画面に出る全行を列挙して、`TRACED` / `NO_BASIS` / `BASIS_GONE` / `STALE` / `NO_QUOTE` / `NOT_PASSED` に分ける | 1000件目でも人が見ずに数えられる。行の列挙は `reviewRows` に数値の帯と分析欄の根拠を足したもの |
| D3 | 辿れない行は画面に出さない（`reader-display-model` で落とす）。ただし公開10件の章の作り直し（D5）が終わるまでは、件数を増やさない検査（基準の件数ファイル）だけを入れる | 今すぐ落とすと、公開10件の章328行が全部消える（行に事実IDが無いので D2 では全行 `NO_BASIS`）。先に作り直してから閉める |
| D4 | 食い違いの判定は、作ったAIとは別のAIが行う。入力は画面の行と、`basis` の事実の文・引用。返すのは `一致` / `食い違い（数字・時点・主体・何の数字か・程度）` / `引用で言えない`。食い違った行は作り直しへ回し、3回で保留にする | 作った本人の点検は独立していない。今の確認役（`display-review-prompt.md`）は作る時の1回だけで、元の事実が後で直された時に見直さない |
| D5 | 公開10件の章は、外部の出典を収集の層で事実として集めて照合を通し（調査記録 → `--from-research` → 原文照合）、その後 `display:build` で作り直す。章に事実IDが無い行は、`chapter-gaps` が「作り直しが要る」と判定する | 照合済みでない出典からは画面の文を作らない。外部の出典を捨てると章が痩せるので、先に集める |
| D6 | 回ごとの記録は `data/pipeline/display-trace/ledger.jsonl`（1行＝1回）。中身は行数・状態ごとの件数・食い違いの件数・判定したAI | 原文照合の台帳と同じ形 |

## 採らなかった案

- 章の行を出典URLから事実に後で結ぶ: 1つに決まるのは328行中40行だけで、残りは推測になる。
- 画面のファイルに引用文を写して持つ: 元の照合結果が直された時に古くなる。引用は検査の時に照合結果から引く。
- 作ったAI自身に確かめさせる: 独立していない。
- 辿れない行があれば今すぐ lint で落とす: 公開10件で328行が落ちて、全部の申請が止まる。件数を増やさない検査から入り、作り直しの後に0件を必須にする。
- 出典URLが1つの事実に決まる40行だけを先に結び直す: 他の288行と同じく作り直しで直るので、別の移行を作らない。

## 実装の順番

1. D1: `ChapterEntry` の行の型に `factId` と `factHash` を足し、`assembleDisplay` で保存する。試験は `src/shared/display-build.test.ts`。
2. D2: `src/shared/fact-trace.ts` に、画面の行の列挙と状態の判定を純関数で書く。`scripts/reader-case/trace-check.ts` が読み込みと出力と台帳を受け持つ。読み込みは `build-display.ts` の `liveReaders` と同じく、照合を反映した後の reader と `data/reader-verdicts.json` を使う。数え方の見本は、この設計の実測に使った測定（上の表）。
3. D3（前半）: `data/display-trace-baseline.json` に今の未辿り件数（章328行。D2 は事実IDの無い行を全部 `NO_BASIS` に数える）を置き、`pnpm lint` の中で「これより増えたら落とす」。
4. D4: `trace-check.ts --judge` で、辿れた行を別のAIに渡して判定する。食い違いは `displayGaps` の作り直しに足す。
5. D5: 章が引いている外部の出典を、収集の層で事実として集める。原文照合を通した後に `display:build` で章を作り直す。手元での作り直しに人の許可は要らない（OWNER_INTENT 19章7）。ただし `data/case-chapters.json` は目録の公開の入力で、他の申請（#175）も触っているので、取り込みの順番は指揮役と合わせる。
6. D3（後半）: 基準の件数を0にし、辿れない行を画面で落とす。

## 取り込み側の差し込み口（もうある物）

- 事実の文の検査: `scripts/architecture/fact-text-checks/*.mjs`。既定の出力は `(text, fact) => string[]` の関数で、空なら合格。`add-entity-records.ts` の `loadFactTextChecks` が読み込み、落ちた事実を差し戻す。
- 差し戻し: 指示書は `data/runner/instructions/collect-return/<名前>.md`。項目ごとの回数は `data/runner/collect-return-state.json` に記録し、3回で保留にする。
