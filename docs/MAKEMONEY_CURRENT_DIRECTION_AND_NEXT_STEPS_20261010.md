# MAKEMONEY｜結局、何を作り、何をどう進めるのか（2026-10-10）

> **目的**：長くなった対話を読まなくても、事業の全体像・今回の結論・次の作業・未決の境界が分かる実務入口。
>
> **状態**：オーナーの意図と、現時点の有力な実現方針・検証順序の要約。**正式な製品仕様、料金、技術選定、商用契約の最終承認ではない**。既存の詳細要件と調査記録を廃棄・上書きするものでもない。
>
> **適用範囲**：今回の追記は **文書のみ**。mainへの直接変更、PRマージ、既存UI・収集・R2/D1変更、実課金・送金、外部公開、契約締結・デプロイを行わない。

## 0. 一言でいうと

**MAKEMONEYは、世の中の実在する事業・稼ぎ方を発見・分析し、自分の事業をAIで制作し、販売・宣伝し、他人の製品を紹介して稼ぐまでをつなぐプラットフォームを目指す。**

単なる成功事例サイト、汎用ノーコード制作ツール、商品販売サイトのどれか一つではない。これらが相互に利用者を増やし、MAKEMONEY自身の継続収益を生む構造が狙い。

**経営上の最優先目的はMAKEMONEY運営者の長期的な実利益の最大化**。ユーザーが本当に価値を得て再訪・課金・販売・紹介することが、その収益の前提。事例数、記事数、制作数、取引総額は利益の代替指標ではない。

## 1. 提供価値は4つの入口（技術や画面の全面承認ではない）

| 入口 | 利用者の目的 | 提供価値 | 収益との関係 |
|---|---|---|---|
| **事例** | 誰が何をどう売り、いくら稼ぎ、何につまずいたかを知る | 出典付きの実例を大量に収集し、成功・失敗、原価、初期顧客、販売・継続のメカニズムまで理解できる | 主として発見・信頼・自然流入 |
| **機会** | 今どんな事業機会があり、何が共通して通用するかを探す | 多数の事例の横断分析、最新の需要、稼ぎ方の型、継続更新 | 完成済み情報ライブラリ等の有料会員 |
| **作る** | 自分のアイデアを本当に稼働するWebサイト/SaaSにする | 企画→AI生成・修正→プレビュー→本人の環境で公開→作品情報を管理する一連の体験 | 適法な外部制作連携、個別AI処理の利用料等 |
| **市場** | 自作・外部制作の商品を宣伝・販売する／他人の商品を紹介する | 作品の自動下書き/同意後掲載、ストア、記事、リンク、紹介者、購入者との接点 | 成約手数料、広告・有料露出、正式な紹介収益等 |

この4つは**入口**であり画面枚数・機能範囲の上限ではない。事例から制作する経路のほか、最初から制作する、外部制作物を出品する、紹介だけする、読むだけで有料会員になる、といった利用者も対象。

**既存の強い価値は削らない**：数千件規模の広範な事例収集、出典、読みやすい詳細記事、事例横断の分析、需要/トレンド、制作・販売の体験を、短絡的に「単なるリンク集」へ縮小しない。既存の良い事例UI・画像・編集された本文・権利/公開ゲートも勝手に変更しない。

## 2. ユーザーから見た一連の体験

1. 事例を探す／市場の機会を読む／直接「こんなサービスを作りたい」と入力する。
2. 自分の事業プロジェクトに、着想、参考事例、検討内容、制作物の識別子、公開・販売状態を必要な範囲でまとめる。
3. 可能な限りMAKEMONEY画面でAIに制作・修正を依頼し、プレビューと成果物を確認する（実生成処理は外部会社）。
4. 制作者本人が契約する外部の公開環境でSaaSを稼働する。本人のソース・ドメイン・ホスティング・DB等の独立性を重視する。
5. MAKEMONEYは制作物の情報を連携許諾の範囲で取得。まず**非公開の商品下書き**を自動生成し、本人の掲載意思・審査条件が満たされた場合のみ公開ストアへ掲載する。
6. 本人が宣伝・販売し、紹介者は本人が許可した商品を記事やSNSで紹介できる。MAKEMONEYは、正式に紐付いた契約・成約・継続取引から合意した対価を得る。
7. 利用者が許可した事実・成約の集計を、次の事業機会の発見や商品改善に活かす。架空の実績や無断追跡はしない。

**注意**：「MAKEMONEY内で一貫して操作」を目指すことと「初回の外部ログイン・本人確認・決済設定が一切不要」は別。制作会社のAPI・認証・契約の正式対応を実証するまでは、完全なサイト内完結を保証しない。

## 3. 誰が何を担当するのか（重要な直近の結論）

| 業務・資産 | 原則としての担当 |
|---|---|
| 事業事例・分析・機会提供、MAKEMONEYアカウント、作品ID/作品情報、ストア・集客・自社会費 | MAKEMONEY |
| AIによる生成・修正・プレビューの実処理 | 正式な商用組込契約のある外部AI会社、または利用者と直接契約する会社 |
| 完成した**個々のSaaSの本番サーバー、DB、ドメイン、実行費** | 原則、制作者本人と直接契約する外部ホスト等 |
| 個々のSaaSの顧客契約・役務提供・通常保守・個別問い合わせ・税務 | 原則、制作者本人 |
| MAKEMONEY上の商品掲載・通報・削除対応、自社会員/入力情報の適切な管理、取引連携 | MAKEMONEY |
| 決済処理・本人確認・適法な支払い実行 | 外部の対応事業者。MAKEMONEYは自己の契約・データ・手数料台帳上の義務を保持 |

**MAKEMONEYが自社名義で全利用者のSaaSを生成→自社サーバーで永続公開→あとから所有権を一斉に引き渡す構成は、最初から必要だと決めない。** 本人が外部提供会社と最初から契約・所有できるなら、移管業務と運営負担を大幅に避けられる可能性がある。

ただし、**外部会社を使えばMAKEMONEYの責任がゼロになるわけではない**。少なくとも以下を区別する：

- **A：AI制作会社とのAPI/再販契約**：利用者の違反、権利侵害、情報漏洩、契約の補償・賠償上限等。MAKEMONEYが契約者なら自社責任が残り得る。これが重要な未決事項。
- **B：ストアの責任**：商品掲載・広告表示・通報・不正商品対応など、自社が実際に運営する部分。
- **C：自社への入力情報の責任**：MAKEMONEYが保持・外部送信する会員/企画/作品情報と連携情報。独立SaaSの全顧客DBを自社に集めない。

## 4. 外部制作の方式は決め打ちしない

| 方式 | できること | 制約・運営負担 | 現状 |
|---|---|---|---|
| **A. 利用者が外部制作会社と直接契約** | 契約と稼働費用を本人へ分離しやすい | MAKEMONEY内でどこまで生成・継続編集できるか、OAuth/API/埋込の正式対応に依存 | **責任最小化の観点の有力候補。採用未確定** |
| **B. MAKEMONEYが生成APIを組み込む** | 自社画面で制作・修正・プレビューを実現しやすい | MAKEMONEYにAPI原価・契約・利用量・補償・情報処理責任が残り得る | **UXとの均衡から比較対象** |
| **C. MAKEMONEYが各SaaSを自社ホストする** | 一体的に作り込みやすい | 維持費・顧客データ・停止事故・後日引渡し負担が膨らむ | **現時点の目的と衝突し、原則非推奨** |

Lovable、Replit、Bolt、v0、OverSkill、Totalumなどは**比較対象**であり、2026-10-10の議論で特定の会社を本採用していない。公式説明に機能があることと、MAKEMONEYの実契約/本人認証/サイト内制作/E2Eができることは別。

重要な判断軸は、**①利用者が制作・公開できる価値 ②正式な組込/本人契約の許諾 ③契約責任と賠償/補償上限 ④利用量・失敗を含む原価 ⑤本人の所有・撤退自由 ⑥外部変更の情報取得可能性 ⑦自社の運用工数**。

## 5. 収益モデル：狙いと未確定を分ける

- **会費**：読み続けたい有料の機会・稼ぎ方の型・追跡更新。読むだけの人も対象。
- **個別AI利用**：無料体験の原価上限を設け、追加調査・制作は利用量で課金する案。
- **ストア**：売主本人が販売・顧客対応し、MAKEMONEY経由で成立した取引に限り合意済み手数料を得る案。
- **紹介**：商品の制作者・紹介者・MAKEMONEYがそれぞれ経済的利益を得るよう、合法で確認可能な成果帰属・返金・報酬管理を行う。
- **広告/掲載**：集客と成約価値がある場合に追加収益化する。
- **将来のロイヤリティ**：制作を支援した全SaaSから自動的・永久に徴収できるわけではない。事前契約、売上証明、期間・上限、離脱条件等が必要。**MVP必須ではない**。

2026-10-09案のPRO月額2,980円、年額29,800円、無料50クレジット、PRO月100クレジット、追加100クレジット1,100円、内部取引10%は**比較・採算検証のための従来提案値**。最新のオーナー指示により、採用・実課金が無条件に確定したものではない。実原価・需要・法令を踏まえて再評価できる。

**売上総額（出品者のGMV）を自社売上と混同しない。** 月次事業利益、継続率、利用者当たり変動費、獲得費、サポート工数と、制作者・紹介者の実成約を測る。

## 6. 次に何をするか：責任を持って進める実務順

### 最優先｜G0：成立条件の検証（制作Provider・本人所有・責任・原価）

1. 候補ごとに公式仕様・契約文書・APIの現在の条件を取得。第三者への商用組込、利用者本人契約、MAKEMONEY内での制作/修正、データ保持、補償上限、課金主体を照合する。
2. **同じ試験仕様**で「静的LP」「ログイン/DB付きWebアプリ」「課金可能なSaaSの前段」を比較。費用、実行時間、失敗・修正率、ソース取得、本人の公開環境での稼働を測る。規約上不可の試験は実行しない。
3. 外部制作者の本人アカウントを最初から接続して公開できるか、退会・権限解除後もそのSaaSが独立して稼働するかをテストする。外部変更をMAKEMONEYへ戻せるかもAPI能力の範囲で確認する。
4. Providerを比較し、①本採用推奨/②代替案/③捨てる案を出す。**サイト内完結ができない場合、黙って単なる外部リンクに仕様を縮小しない。**

### 並行｜情報商品と既存の事例の価値を完成させる

- 既存の大規模な事例収集・出典・権利・公開品質ゲートを保護し、読む価値のある事例本文と横断分析を強化する。
- 「機会」と「稼ぎ方の型」の完成済み情報商品・更新が、実際にPROの継続課金に値するかを具体的なコンテンツとテストで確かめる。
- 制作Providerの決定を待つ間にも、**情報商品の設計・画面の検証・採算測定を止めない**。

### G1～G3｜制作→本人公開→ストア自動掲載

- 共通Project/作品ID、外部Provider接続、生成・修正・プレビュー・成果物、本人公開接続、作品の非公開下書き、掲載同意/審査、自動商品ページを実装・E2Eで確認する。
- 本人が公開を選ばない限り、秘密の事業企画を一般公開しない。
- 他のユーザーのコード・企画・鍵・顧客情報が見えないこと、本人退会後も独立SaaSが動くことを検証する。

### G4～G5｜月額販売と他者紹介

- 制作者自身が販売者となる正規の決済連携を調べ、購入・2回目請求・失敗・解約・返金・支払済み利用権・MAKEMONEY手数料をテストする。
- 紹介者報酬は、成果帰属、不正/自己紹介、返金、KYC、税務、合法な送金業者まで検証する。実送金は事前承認後。
- **自社会費用のStripeと、他人のSaaSの販売・紹介の決済を混同しない**。

### G6｜記事・広告・流通・需要への還流

- ユーザーが自由に記事を書いて自作品や他人の商品の宣伝を行えるようにし、表示責任・出典・広告表示・不正対策を整える。
- ストアの供給量だけでなく実成約・継続・紹介流入・運営利益で仕組みを評価する。

**機能を安易に削るのではなく、必要な実装・契約・検証を依存順に分けて進める。** 各段階は実操作・実データ・実画面・事故系の試験が通るまで完成と呼ばない。

### 次の作業者への引き継ぎ（重要）

**最初にG0の契約/現物/E2E検証を行う。情報商品の改善は並行させる。** 実契約・補償・原価が合わなければAPIを替えるか本人直接契約方式を試す。旧提案のv0/Netlify/Vercel/Prisma/Stripe構成を既成事実にせず、今回の事業目的から比較・判断する。

**ユーザーへの報告は「確認済み事実」「採用推奨と根拠」「未確認」「次に実行すること」を分離。** 自社で作る必要のない移管・ホスト・顧客DB機能を惰性で追加しない。実課金/公開/契約など外部効果のある行為は個別承認を要する。
