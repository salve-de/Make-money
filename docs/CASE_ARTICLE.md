# 事例の記事（case-article）

事例の詳細に出す、新しい記事の形式。旧形式の「章ごとの文」（`data/case-pages/<事例ID>.md`）と並んで使う。旧形式の事例はそのまま。

## 形

- 分類は8つで固定: 概要・仕組み・お金・集客・運営・経緯・成功・失敗の理由・出典。詳細の上に目次として固定で出る。データに無い分類は出ない。
- 見出し・見出しの下の文・主な数字は、章の前に出す。
- 分類の名前（概要・仕組み…）は全事例で同じ。その下に、事例ごとの章の見出し（章の `title`。「Tallyは何を提供し、誰がお金を払うのか」）を付けられる。集める時にその事例に合わせて書く。無ければ出ない。
- 章の中の小見出し・部品の種類・並び・数も、集める時に事例ごとに決める。
- 章は、流し読みで分かる形にする（太字の行動とその結果、数字、箇条書き）。書き方は下の「章の書き方」。
- 部品は、項目の行、番号つきの説明、縦並びの金額、年表、箇条書き、小見出し、図、文章。事例に合う物を選んで組み合わせる。
- 事例ごとに画面を手書きしない。どの事例も同じ表示部品（`src/features/company-inspector/ui/CaseArticleView.tsx`）がデータから描く。
- 定義は `src/shared/case-article.ts`。

### 部品の見え方（2026-10-14）

原稿は中身だけを書く。見え方は、詳細の欄の幅に合わせて表示部品が決める。

| 原稿 | 画面 |
|---|---|
| 行頭の見出しつきの箇条書き（全部の行に `lead`） | 見出しを太字で1行に立て、説明をその下に置く。欄が広い時は、見出しを左・説明を右に分ける |
| 番号つきの箇条書き（`ordered`） | 順番に起きる流れとして、番号を線でつなぐ。欄が広く4つまでなら、横に並べて矢印でつなぐ |
| 縦並びの金額（`rates`）に `bars: true` | 数字の横に棒を出して大きさを比べる（月の売上の移り変わりなど。全部の値が同じ単位の数の時だけ） |
| 小見出し・`rates` の題 | 新しいまとまりの始まりとして、線で区切って出す |

## 型ではなく見本（2026-10-14 オーナー決定）

集める所から画面に出す所まで、今後はこの文書の形と見本（Plausible）に合わせる。ただし型に押し込めない。

- 見本と同じ章立て・同じ項目数・同じ「太字＋説明」にそろえる必要はない。事例に合わせて変える。
- 文章で説明したほうが分かる所は文章で書く。図のほうが分かる所は図にする。書く事が無い章は出さない。
- 形が見本と違う事を理由に弾かない。自動で止めるのは、画面が壊れる物と、数字・出典の誤りだけ。
- 迷ったら「読む人が流し読みで商売の全体を分かるか」「その行を消すと理解が変わるか」で決める。

## 集める時（調べる担当が、原稿まで書く）

- 後で原稿にする事を考えて、最初から具体的な所まで調べる。「SNSで集客した」で止めず、どのSNSで、何を投稿し、誰に届き、結果がどうだったかまで取る。「価格を変えた」なら前後の金額と理由、「少人数で運営」なら誰が何を担当しどう手間を減らしたか。
- 実際の宣伝文句（変える前と後）、使った掲載先・販売先の名前、施策ごとの結果の数字、失敗とその後の対応を、出典・日付・数字の単位と期間つきで残す。
- 調べた担当が、出典を読んで事業を理解した上で、読む人向けの原稿（`article.json`）も一緒に書く。後から事実の断片を機械的につなげない。
- 画像は、アプリの画面写真に限らず、その事例が何を売っているかがいちばん伝わる物を選ぶ（選び方は [`COLLECT_TO_UI.md`](./COLLECT_TO_UI.md) の「4. 画像」）。
- 広く集め、載せる時に選ぶ。載せなかった事実・足りない情報・権利の懸念は `editorialChanges` と調査の記録に残す。
- 分からない数字を、記事の事実の行に推定で入れない。

## 8つの分類の役割（集める時も、書く時もこれで分ける）

| 分類（id） | 読む人が知りたいこと | 入れる内容 |
| --- | --- | --- |
| 概要（overview） | 何の商売？ 誰がなぜ買う？ | 商品・サービス、顧客、使う場面、買う理由、それまでの代わりの手段 |
| 仕組み（mechanism） | 具体的にどう使い、何を受け取る？ | 利用・購入・提供の流れ、参加者それぞれの役割、商品に組み込まれた工夫 |
| お金（revenue） | どう稼ぎ、いくら残る？ | 料金、何に課金するか、収益源、売上・利益、費用、初期資金、入出金の条件 |
| 集客（acquisition） | 最初の客をどう取り、その後どう増やした？ | 初期の営業、広告、検索、紹介、販売経路、購入・再購入につながった施策 |
| 運営（operations） | 誰が、どんな仕事をして支えている？ | 人員、技能、作業の工程、設備、技術、仕入れ、外注、必要な許認可、運営上の負担 |
| 経緯（history） | どう始まり、何が変わった？ | 創業の背景、開始時の状況、主な出来事、失敗、方向転換、成長・縮小の年表 |
| 成功・失敗の理由（reasons） | 何が結果につながった？ 別の事業にも通じる？ | 行動と結果の関係、競合との差、成り立つ条件、外の環境、頼っている先、ほかでも通じる所と限界 |
| 出典 | 何を根拠に書いている？ | 本文・数字に対応する原典。記事の `sources` から自動で出る |

概要〜経緯は事実の整理、成功・失敗の理由は前の章の事実をつないだ分析、出典は根拠。

重なりやすい所の分け方:

| 組み合わせ | 分け方 |
| --- | --- |
| 仕組み／運営 | 仕組みは、客や参加者から見た使われ方・提供の流れ。運営は、それを成り立たせるために会社が実際にする仕事 |
| お金／運営 | お金は、何にいくらかかり、収支がどうなるか。運営は、その費用が生じる仕事や体制の中身 |
| 集客／経緯 | 集客は、客を取った方法を詳しく書く場所。経緯は、いつ何が変わったかを見渡す場所 |

- 同じ事実に2つの章で触れてよい（年表で発売に触れ、集客で発売時の営業を詳しく書く）。同じ説明をそのまま繰り返さない。
- 章の中の小見出し・項目の数・部品の組み合わせは、事例ごとに変えてよい。
- 成功・失敗の理由は、成功した会社に見られる特徴をそのまま原因と書かない。どの事実からそう言えるか（記録に結ぶ）、成り立つ条件、頼っている先、限界まで書く。

## 章の書き方（流し読みで分かる形）

2026-10-14 オーナー決定。情報を減らすのでなく、読む負担を減らす。見出し・太字・数字・箇条書きを追うだけで商売の全体が分かり、気になった所だけ詳しく読める形にする。見本は `data/case-articles/ent_plausible/article.json`（r7）。

- 基本の形は、箇条書きの行頭に太字で具体的な行動や内容を書き（`lead`）、すぐ後に何をしてどうなったかを書く。`lead` は見出しとして1行に立つので、句点を付けない。例：「**キャッチコピーを変えた** 「…」を「…」に。前日のサイト訪問者は49人だった。」
- 章の最初の文（章の `lead`）は必須ではない。箇条書きや数字から直接始めてよい。小見出しを機械的に付けない。章の長さや項目の数をそろえない。書く事が無い章を一般論で埋めない。
- 載せるかどうかは「その行を消すと、読む人の理解や判断が変わるか」で決める。変わらない行は載せず、`editorialChanges` に「載せなかった事実」として残す。資金の負担・実際の利益・重大な失敗は残す。
- 横の表（`table`）は使わない。料金・月ごとの数字・比較は縦並び（`rates`）、出来事は年表（`timeline`）にする。
- 見出しは短くし、商品・競合・料金・人数・売上を全部詰め込まない。見出し・見出しの下の文・概要で同じ商品説明を繰り返さない。主な数字は要る物だけ（同じ意味の数字を2つ並べない）。
- 同じ事を複数の章に書かない。同じ数字の一覧と図を続けて置かない。
- 章の最初の文を書く時は100字以内。
- その下は数字・項目の行・箇条書き・表・図。長さの上限は、項目の行と年表が110字、箇条書きが140字、手順の説明が170字。上限は長い段落を置かないための物で、文を切るための物ではない。
- 背景や理由の説明が要る所は、文章（`paragraph` の `body`。240字以内）で書いてよい。長い文章を続けて並べない。表や行に添える短い補足は `note`（80字以内）。
- 数字には時点を付ける。外貨は直後に円の概算（為替は `docs/CASE_TEXT_STANDARD.md`）。
- 画面に出すのは読む人に要る事だけ。調べた側の都合（未確認・読めなかった・採用しなかった理由）は `editorialChanges` に置く。

### どの文も、その文だけ読んで意味が全部分かるように書く（2026-10-13 オーナー承認）

一覧の1行・見出し・見出しの下の文・主な数字の名前・章の最初の文・箇条書きの1行・図の中の文字、のどれにも当てる。

- **「何の事？」「なぜ？」「それで？」が残る文は、短くても書き直す。** 答えを同じ文の中に書く。
  - 前：「データはEU内に置く」
  - 後：「集めたデータはEU内のサーバーに保存する。EUの個人情報保護の規則は、個人のデータをEUの外へ持ち出すことを厳しく制限している」
- **雑誌や記事で人が普通に書く言葉を使う。** 専門語を避けようとして、誰も書かない幼い言い換えにしない。アクセス解析・マーケティング担当・キャッチコピー・無料体験・顧客は、そのまま使ってよい。

  | 前 | 後 |
  | --- | --- |
  | 働く人 | 社員 |
  | 金を払うようになった | 有料契約に移った |
  | 誰が来たかは追わない | 訪問者が誰なのかを特定する情報は保存しない |
  | 1か月に入る利用料 | 月の売上 |

- **読む人が最初に抱く疑問には、見出しの下の文で先に答える。** 無料の競合があるのになぜ金を払うのか、など。
- **名前を出す。** 「ほかの製品」「別の会社」とぼかさず、相手の名前・見出しの文言・製品の名前をそのまま書く。
- **一覧の1行は字数で止めない。** その1行だけで何の商売かが分かる所まで書く。ただし一覧の画面は1行で切れるので、切れない長さ（詳細を開いた1440幅で全角およそ58字）に収める。
- 書いた後、1行ずつ「この行だけ読んだ人に疑問が残らないか」「大人が普通に書く言葉か」で読み直す。図の中の文字も同じ目で直す。

### 分析の言葉でまとめない。起きた事と数字を書く（2026-10-13 オーナーの指摘）

事実を「効いたこと」「成り立つ条件」「頼っている先」のような分析の言葉でまとめると、AIが書いた文に見える。言葉を1つずつ入れ替えても直らない。直すのは書き方のほう。

- **行の左に言葉を置くのは、普通の名詞が自然に付く時だけ。** 商品・客・料金・競合・人数、人の名前、プランの名前、年月。それ以外は箇条書きにする。書き手が作った分類の言葉（効いたこと、競合との差、成り立つ条件、追い風、頼っている先、通じにくい所、線引き、欠かせない仕事、強み、課題 など）は置かない。年表にも題（「始まり」「伸びる」など）を付けない。
- **1行に、起きた事と数字を入れる。** 誰が・いつ・何をして・どうなったか。「育てた」「支えた」「つながった」「確立した」のようなまとめの動詞で終わらせず、その中身（何をしたか、何人来たか、いくら入ったか）を書く。
- **「成功・失敗の理由」も同じ。** 理由を言葉でまとめず、理由になった出来事と数字を並べる。うまくいかなかった事、金がかかった事、時期に助けられた事も、出来事として書く。
- **人が書いた手本を横に置いて書く。** 手本は `data/case-pages/ent_candy_japan_954236d663a8.md`（オーナー承認済み）。書いた後、書いた本人でない読み手が手本と並べて読み、調子が浮いている行を直す。

前（Plausible の「成功・失敗の理由」）：

| 行の左 | 文 |
| --- | --- |
| 効いたこと② | 一度きりの掲載に頼らず、記事・検索・紹介で人が来続ける道を育てた |
| 競合との差 | 機能の数で競わず、単純さ・クッキー不使用・欧州でのデータ管理で選ばれた |
| 成り立つ条件 | 不満がはっきりしていて、比べる相手が明確で、読んですぐ試せる製品がある |
| 追い風 | 2022年ごろのプライバシー規制の動きと、Google Analyticsの製品変更 |

後（行の左の言葉なし。箇条書き）：

- 2020年4月のこの記事は数日で5万回以上読まれ、1週間で166人が無料体験を始めた
- 無料体験は30日間で、カードの登録が要らない。記事を読んだその場で試せた
- 新製品の紹介サイトに載った日は1,000人以上が来たが、数日後は20人未満。その後の客は記事と検索から来た
- 2022年ごろには、プライバシーの規制の動きとGoogle Analyticsの仕様変更が重なった
- 黒字になるまでに、創業者2人は貯金から5万ドル（約750万円）以上を出した

見本は `data/case-articles/ent_plausible/article.json`（全章。オーナー承認済み）。

## 置き場所

`data/case-articles/<事例ID>/`

| ファイル | 中身 |
| --- | --- |
| `article.json` | 掲載用の原稿（読む人向けの文と構成の正本）。各文は `recordKeys` で調査の記録に結ぶ |
| `research.json` | 元の調査データ（事実・数字・出典の正本）。受け取ったまま変えない |
| `figures/*.svg` | 自作の図。写真や外部の画像は入れない（既存の画像欄が審査して出す） |

`article.json` の `editorialChanges` に、原稿で変えた点を残す（円の概算の追加、画面から外して内部に持つ文、調査にあって記事に無い情報、記録に結べなかった文）。

## 流れ

1. `pnpm case-articles:build` … 原稿を検査し、画面用の `data/case-articles.json` を作る（`recordKeys`・審査の状態・編集の記録は画面用から外れる）。`pnpm lint` に検査（`--check`）が入っている。
2. 新しい事例は `node --import tsx scripts/case-articles/add-records.ts` で身元の記録（`data/entity-additions/gen5-case-articles.json`）を作る。
3. 公開版を作る時（`scripts/prepare-catalog-release.ts`）、**`reviewState` が `approved` の記事だけ**が事例の `reader.display.caseArticle` に入る。それ以外の記事は無いものとして扱い、その事例のこれまでの扱いを変えない。
4. 新しい事例を本番に出すには、身元の記録を事例の一覧（`data/entities-index.json`）へ合流させる手順が別に要る（公開データを作る直前に行う）。

検査の中身: 章の結論の1文があること、1行の長さ（章の最初の文100字・項目の行と年表110字・箇条書き140字・手順170字・補足80字・文章240字）、です・ます調、外貨の直後の円の概算（為替は `docs/CASE_TEXT_STANDARD.md`）、出典の番号、図のファイルと中身、分類の順、調査データの指紋、`recordKeys` が調査の記録にあること。
