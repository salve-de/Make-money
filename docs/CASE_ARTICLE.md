# MAKEMONEY｜事例詳細の記事・画面・収集データの共通仕様

更新：2026-10-15。最新のオーナー意図：[事例収集・記事編集・7セクション統一仕様（PR #228）](https://github.com/salve-de/Make-money/blob/docs/makemoney-owner-reality-20261015/docs/MAKEMONEY_CASE_COLLECTION_SPEC_20261015.md)。

## 目的

**世界の実在する成功事例を、普通に調べて普通にわかるように表示する。** 読者に「何を誰に売ったか、どんな工夫があり、最初の顧客がどう来て、いくら売れ、どう伸びたか」が具体的に伝わること。調査項目の埋め尽くし、記事の長さ、無意味な図や厳密な監査それ自体は目的ではない。

読者向けの記事では、商品の特徴・仕組み・売り方・初期獲得・伸びた実績を主役にする。**本文に要らない注意書き・抽象的評価・執筆メモ・調査上の都合・リスク列挙を入れない**。研究原本には有用な事実や出典を保持する。失敗→改善→成長の実際の転換点が理解に役立つ場合は普通に書けるが、機械的に赤字・失敗を主題としない。

## 1. 決まっている画面の構造：最大7セクション

分類と順序は**「概要／仕組み／お金／集客／運営／経緯／出典」**で固定。すべての事例に7章を無理に埋める意味ではない。本文6分類のうち材料があるものを目次・章へ表示し、出典は最後に表示する。

| セクション | id | 読者に見せる内容の基準 |
| --- | --- | --- |
| 概要 | `overview` | 商品／サービス、誰が買うか、選ばれる理由、何が独特か |
| 仕組み | `mechanism` | 買う・使う・受け取る・納品するまでの具体的な仕組み。取引の流れ |
| お金 | `revenue` | 誰が何に払うか、料金や手数料、実際の売上・販売数・顧客数等の意味ある実績 |
| 集客 | `acquisition` | 最初の顧客、具体的な告知・投稿・営業、口コミ・紹介・流通による拡大 |
| 運営 | `operations` | 実際の作業、人数、開発・製造・仕入れ・物流・サポート、特徴的な工夫 |
| 経緯 | `history` | 創業から販売開始、伸びた出来事、重要な転換点を必要なだけ |
| 出典 | UI側で `article.sources` から生成 | 本文と数字の根拠URL、資料名 |

**「成功・失敗の理由（reasons）」は独立の8番目のセクションにしない。** 成功した理由につながる事実・行動・結果は、概要・仕組み・お金・集客・運営・経緯の中でその話に一番合う位置に書く。別章で同じ説明を繰り返さない。

`src/shared/case-article.ts` の `CASE_ARTICLE_TOPIC_IDS` は上の本文6分類のみ。`src/features/company-inspector/ui/CaseArticleView.tsx` が最後に「出典」を追加して表示する。分類ラベルと順序は固定だが、各章の内部ブロック数・話題・小見出し・文章量・図表数は固定しない。

既存の旧記事 `case-page` は変更しない。記事別に独自のHTML/CSSや別の目次を実装しない。既存暗色テーマ・罫線・章見出し帯・フォントの序列・情報密度・スマホ対応を維持する。

## 2. 調査→記事の作り方

1. 実在する事業を理解する。商品、客、料金と収益構造、最初の顧客獲得、伸びた転機、独自の工夫、実績を公式発表・本人ブログ・取材・公開資料等から調べる。
2. **初めから読者向けの原稿を想定**し、何が一番面白いか、どんな見出しなら商品の姿と成功した方法が一目で分かるか考える。
3. 仮見出しや短い文章を同時に書く。「何の数字？」「何に使った資金？」「最初の客はどう来た？」と意味が足りなければ、必要な分だけ追加調査する。調査メモの短文を最後に機械的につぎはぎしない。
4. セクションごとに、その事例で重要な具体的な情報を配置。概要→仕組み→お金→集客で同じことを繰り返さない。成功要因の名で独立章を再発明しない。
5. 見出し・一文の要点・箇条書き・番号付き手順・表・年表・図から一番分かる表示を選ぶ。空章を埋めたり図をノルマで作ったりしない。
6. **読者価値を最終編集**：すべての表示項目について「その一行で、この事業を新しく理解できるか」「固有の事実や実際の行動があるか」「重複していないか」「削ったら理解が減るか」「普通の日本語として意味が通るか」を確認。価値を増やさない項目は読者向け原稿から外す。理由と元情報は内部記録に残す。
7. 記事の数字・期間・出典・図解の内容だけ、自然な記事を書くための通常の確認をする。過度な警告や多段監査を画面へ流し込まない。

**意味のない文章の具体例（本文へ出さない）**：

- 「103万ドルは利益ではない」「誰でも同じように稼げるとは限らない」
- 「売上構成比は調査記録に残す」「確認できなかったので記事には載せない」
- 「SNSを駆使して顧客を獲得した」「時代の追い風を生かした」だけの一般論
- 売上の数値を帯・表・箇条書き・見出しで意味もなく何回も再掲すること
- 成功の仕組みと関係の薄い事故の説明、返金の細かい条件、無意味な規約注記
- 役割がない図・何かをした事実が無い年表・質問形だけの調査見出し

**自然な説明の例**：「無料フォームに付いた『Made with Tally』を見た回答者がTallyを知り、次の利用者になった」「広告枠を1画素1ドルで販売し、約5か月で売上103万ドルに達した」。売上を利益と誤称しないが、わざわざ否定注記を付け加えない。

事例によって知りたい内容は違う。SaaSでは課金・集客、物販では商品・販路、仲介では買い手／売り手／手数料が主役になり得る。章を全件均等に埋めない。

## 3. 記事の画面要素（現実のコードに合わせる）

| 項目 | データ | 表示と編集の役割 |
| --- | --- | --- |
| 一覧用の1行 | `listLine` | 何の商売かと特徴を端的に伝える。文字数を揃えるのが目的ではない |
| 詳細の見出し | `headline` | 商品・工夫・実績など、その事例の読む価値を示す |
| 導入 | `lead` | 見出しとは違う具体的な情報を足す |
| 代表的な数字 | `kpis`（最大4個） | 意味がある時だけ。重複や重要でない数字を入れない |
| 本文セクション | `topics` | 上記6分類の有効な部分集合だけ。中身・量・順序は柔軟 |
| 出典 | `sources` | 画面側が最後にまとめて表示 |
| 図解 | `figures` | 本文から図のIDを参照、実SVGは別ファイル |

共通ブロック：`facts`（ラベル付き短文）／`paragraph`（普通の段落）／`steps`（順序のある説明）／`rates`（料金と数値）／`table`（列比較）／`timeline`（年表）／`list`（箇条書き）／`subheading`（小見出し）／`figure`（オリジナルSVG）。全部のブロックを一つの記事へ使う必要はない。

- `list`の`lead`は「最初の400画素」「Product Hunt」等、具体的で内容がある場合に使う。抽象的なAI評価名を見出しにしない。
- `rates.bars=true`は定義・期間・単位が比較可能な数値にのみ使う。
- 横表が読むのに最適な時は`table`を使ってよい。スマホで読みにくい場合は`rates`等に変える。表の使用を一律禁止する旧文書より内容の伝わりやすさを優先。
- 年表は意味のある出来事のみ。単なる全部の年を穴埋めしない。
- 円換算は必要な場合に自然に添え、金額・期間・単位の意味を壊さない。数字の帯と本文の円価値を食い違わせない。
- 第三者の実製品・サービス画面を載せるなら別途適切な利用根拠が必要。権利が確認できない画像を単にコピーしない。
- 図解は何が買われ、売られ、どこで売上が発生するか等を本当に説明する場合だけ。SVGの実文字列を保持し、PC/スマホ両方で読めること。

## 4. 研究原本と記事原稿を別に残す

`data/case-articles/<事例ID>/` の下に、次を持つ。

| ファイル | 役割 |
| --- | --- |
| `research.json` | 元の調査記録（事実、出典、日付、通貨、未確認、権利など）。編集によって上書きしない |
| `article.json` | 読者向けの日本語原稿、本文ブロック、出典番号、`recordKeys`、図の参照、編集変更履歴 |
| `figures/*.svg` | 必要な時だけ作る、自分たちの図の実体 |

`article.json` の`basedOn.packageId`と`basedOn.submissionSha256`は`research.json`の実体を指す。元の資料と本文の関係は`recordKeys`で結ぶ。読者向けのビルドデータからは`recordKeys`、`sourceKeys`、`editorialChanges`等の内部フィールドを除く。

**実際に記事から外した内容は`editorialChanges`の`withheld`等に残し、研究JSONそのものを消さない。** 収集原本の形式はPR #228で統一した`makemoney.r2.case-research-article-bundle.v1`を基に、受取側で本形式へ展開する。過去の別形式は元のまま保持して受取側で変換する。

## 5. 2026-10-15：既存5記事とセクション統一

元の5記事（Tally、Plausible、Gumroad、The Woobles、Flightradar24）は独立した`reasons`章を持っていた。今回、他章にすでに説明がある内容を再掲しないよう整理し、**本文6分類＋出典の最大7分類**にした。読者にとって不要な事故・細かな規約・調査の注意書き等は原稿から外し、元調査データを保存。編集の変更は`article.json`の編集履歴に追加した。

- **Tally**：無料フォームの利用による拡散、有料プラン、顧客獲得を主役にする。事故の詳細を主題にしない。
- **Plausible**：記事・検索による顧客獲得、Google Analyticsとの差、月額で売れた実績を中心に。自己資金に関する意味が不明瞭な短文は表示しない。
- **Gumroad**：デジタル商品の決済・納品代行、売り手が購入者を連れてくる仕組み、手数料収入を中心に。
- **The Woobles**：編み始めを済ませたキット、買った後の学び方、小売・キャラクター展開を中心に。
- **Flightradar24**：協力者の受信網、広告／会員／法人向けデータ販売、成長を中心に。

元原稿の文やresearchを勝手に改竄して成功に見せるのではなく、掲載する主役を選び直した編集変更。公開承認を与えたことではない。

## 6. コード・受入・公開の境界

- `pnpm case-articles:build`：原稿を検査して`data/case-articles.json`を生成する。`pnpm lint`には`--check`が含まれる。見出しと本文の意味・価値までは機械判定できないので、発見した問題は原稿で修正する。
- `node --import tsx scripts/prepare-catalog-release.ts --preview-articles`：未公開プレビュー生成。
- `CATALOG_RELEASE_DIR=$PWD/.catalog-release-preview pnpm dev`：既存Next.js UIで未公開原稿を見る。
- 本番版への取り込みは`reviewState === approved`が必要。それ以外の記事は現在の公開版へ反映しない。今回の編集は承認・公開・課金・デプロイではない。
- ZIPを使う一括取込の候補は`feat/case-batch-intake-20261014`。実際のプレビュースクリプトはR2へ書かず、Driveからの自動取込も未実証。別途E2E確認が必要。

**合格の中心**は、既存のUIに表示された記事を初めて読む人が、その事業の商品、買い手、売り方、初期顧客獲得、成長の独自性を自然な日本語と必要な図表から理解できること。形式検査やPR作成だけで完了と報告しない。
