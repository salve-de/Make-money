# 既存R2データから高密度UIへ — 実行・編集契約

更新日: 2026-09-10。これは実装の完了報告ではなく、今後の収集・補強・投影・表示の契約である。

## 1. 目的と正本

既存R2に蓄積した情報を使い、会社ごとの商売の仕組み・顧客・初動・数字・失敗を具体的に読める、既存の高密度一覧と右詳細を完成させる。保存件数や一律の項目充足を目的にしない。

共有の収集範囲・意味・保存は [Foundation統合契約](https://github.com/salve-de/universal-foundation/blob/main/docs/BUSINESS_RESEARCH_AND_R2_CONTRACT.md) が正本。特に第8.1〜8.5節を読む。本書はMake-Moneyの表示・編集を定め、既存schemaやR2方式を追加しない。文書内の古い「全件強制補完」「個人手残り実額の逆算」「全量公開・0秒保証」等と衝突する場合は統合契約と本書を適用する。

## 2. 何を集めるか

会社・人物・商品、顧客と支払者・痛み・用途、価格、売上・費用・利益・資金の流れ、初期/現在の集客、運営・人員・ツール、競合と依存、失敗・撤退・ピボット・時系列、出典・不確実性を対象とする。初動、大手の制約、支払う動機、費用構造、プラットフォーム依存、移行負担、紹介報酬、前払い、過去の失敗も調べる。

公式資料だけに限定せず、創業者、報道、顧客レビュー、コミュニティ、過去ページ、市場シグナルまで必要な範囲で確認する。既定の項目にない有益な事実も既存Journal/observationsへ保持する。広い調査範囲は全社同じ項目を埋める義務ではない。

## 3. 既存データを使う順序

1. 実際の作業ブランチ・稼働URL・データ版・読込経路を確認する。別ブランチや他AIの未コミット変更を巻き戻さない。
2. 保存済みbundle/Journal/typed情報を会社ごとに結びつける。記事タイトルを企業名にしない。別名・同名異社・時期違いを確認する。
3. 「保存済みだが未表示」「資料にはあるが未抽出」「情報源が不足」を区別する。順に投影修正、再抽出、追加調査で対処する。
4. 読む価値を増やせる問いだけを追加調査する。費用や利益が不明でも、具体的な顧客用途や初動を活かせる。承認済み実行予算内で検索/取得・並列数・再試行に上限を設け、結果と再開条件を残す。
5. 元情報を残したまま表示用の短文・セクションを生成する。既存の豊かな編集を低品質の自動文で一括置換しない。出典・時期・確度で項目ごとに採否を説明できるようにする。

名前・URLだけの候補は保持するが、完成した公開用事例数に数えない。初動だけでも有益なら表示する。全社に売上・利益・堀を要求する足切りや、会社ごとの固定Tier分けはしない。保存オブジェクト数、記事数、ユニーク会社数、公開用事例数、追加調査待ちを分けて報告する。

## 4. 現行Stripeを基準にする画面と文章

ユーザーが提示したStripe一覧・インスペクターを基準とする。確認時の参照は `refactor/terminal-architecture-cleanup` のコミット `5bce70b` と次のコード。実装時には最新を再確認する。

- `src/platform/data/mockLedgerData.ts`: `ent_stripe` の編集形。
- `src/platform/components/grid/InstitutionalDataGrid.tsx`: 一覧。
- `src/platform/components/inspector/CompanyInspectorPane.tsx`: 詳細、`parsePunchline`による見出し/本文の分離。

mockの数字・因果・心理・移行不能等の主張を検証済み事実として引き継がない。参考にするのは形式・短さ・具体性・密度である。

| 場所 | 編集・表示要件 |
| --- | --- |
| 一覧 | 社名を確保し、短い特徴タグ、判明した創業年、1行リード、意味を揃えた数値列を維持 |
| リード | 痛み・具体的な仕掛け・商売上の帰結から根拠のある要素を凝縮。説明書風の概要や記事タイトルで終わらせない |
| 詳細冒頭 | 凝縮リード、情報の時期、根拠のある状態・タグ。取得年を創業年にしない |
| 事業DNA | 「何屋か／誰の財布／切除する苦痛」の短い3行テーブルを基本に、分かる内容を具体的に記す。未知欄を一般論で埋めない |
| 業界の盲点・参入障壁等 | 核心を突く短い見出し＋短い解説。出来事・仕組み・効く理由を凝縮し、長い書評やAIの作業説明を混ぜない |
| 財務・稼働 | 公開値と条件付き推計を区別。通貨・対象期間・指標・計算根拠を確認可能にする |
| Playbook | 実際の行動・順序・経路・費用・結果を、既存の短い解説や手順表示で見せる |
| 考察・時系列 | 条件や環境の変化、応用の可能性を根拠付き分析として示す。成功や現在の再現性を自動保証しない |
| Stream・追加内容 | 枠外の有益な観測・顧客・ツール・失敗等を探索可能にし、同じ事実を無意味に重複表示しない |

編集目安はリード約60〜90字、見出し約20〜40字、解説約80〜130字、見出し＋解説で概ね150字前後。これはコードの固定上限・唯一の黄金比ではない。正確さと実画面の収まりを優先し、端末幅・日本語折返し・社名やタグの欠けを確認する。詳細や出典から完全な内容に到達できるようにし、長さのために元情報を破棄しない。

強い表現は具体的な事実と分析から作る。「絶対に逃げられない」「広告費ゼロ」「数学的に証明」等を迫力のために加えない。料金ボタンのクリックを購入実績に変えない。推計を実額や個人手取りに変えない。本文は読みやすく保ち、分析区分・出典・時期はバッジや展開先でも確認できる形にする。

## 5. 柔軟に変える部分

維持するのは高密度の操作・見た目・表現部品。各社の論点、見出し、順序、量は変えてよい。一社に複数の論点を持たせ、後から増やせるようにする。

| ある情報 | 詳細で厚くする内容 | 新情報が増えたとき |
| --- | --- | --- |
| 初期LP・価格テスト・初課金 | 初動の突破口、検証から販売までの経緯 | 費用資料が追加されれば財務も追加 |
| 実際の導入顧客・用途 | 「これを使う顧客」、導入前後の作業 | 顧客別の用途比較を追加 |
| 売上・費用・人員 | 財務・稼働、費用構造、少人数運営 | 期間が増えれば推移を追加 |
| 撤退・失敗・ピボット | 行き詰まった理由、変えた条件 | 後の事業と関係づける |
| 特殊な紹介制度・ツール・顧客の使い方 | 内容に合う固有見出し | 一般化できたら再利用可能な表示部品にする |

この表は事例の固定分類でも収集上限でもない。「顧客」セクションを追加する場合は、既存customer/relationship/claim/observationsから投影する。想定するターゲットと実際に使った顧客を区別する。新セクションがない会社にも作成を強制しない。

比較用の同じ列は同じ指標・単位・期間で比較する。価格、ARR、月商、顧客数を同じ売上列へ混ぜない。別の有用指標を出す場合は専用ラベルを付け、売上ソートや利益率計算から分ける。

## 6. 保存・配信・更新

原情報と根拠は既存Foundationへ保持し、製品用コピーと表示選択は再構築可能な投影にする。新しいschema・独自R2ルートindex・保存方法を作らない。既存Universal/EDINET/Investraderを変更しない。

通常閲覧で全R2オブジェクトやLLMを毎回呼ばず、既存の投影とアプリキャッシュ、必要に応じ登録済みのserving viewを使う。一覧要約をページ分割し、詳細は遅延取得・キャッシュする。データ追加/訂正は差分再構築し、失敗時は前版と鮮度表示を維持する。10万件の全文を一度にブラウザへ送らない。費用・遅延・メモリは実測し、永久無料や0秒を約束しない。

## 7. 完了条件と引継ぎ

- 文書、データ補強、表示用生成、API、実機表示のどこまで完了したかを別々に報告する。
- 豊富な事例、部分的に有益な事例、顧客用途、失敗、未知数値、別名重複、矛盾する資料、既存観測の未表示を確認する。
- 一覧リード・3行テーブル・見出し/短文が実画面で収まるか、既存良質表示が劣化しないか、出典へ辿れるかを確認する。
- 新しい任意セクションを、元データの書換えや全件再収集なしに追加できることを確認する。
- 実行対象のbranch/commit、URL、データ版、件数、追加調査の結果、未解決事項、遅延とR2/API呼出数を記録する。
- GitHub更新はR2説明オブジェクトや公開サイトの更新と同義ではない。R2のみから復旧するときも既存descriptorのauthorityを辿ってFoundation mainの最新契約を読む。R2本体への反映を行ったと主張するには別途write/readback証拠が必要。

この契約更新はUI実装・収集バッチ・R2データ補強の完了を意味しない。
