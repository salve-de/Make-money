# 事例の文の書き方（詳細・一覧の画面に出る文）

> 2026-10-07 オーナー決定。今回だけでなく、今後つくる全事例でこの形を守る。事例を集める人・AIは、文を書く前にこの1枚を読む。守れているかは `pnpm case-text:verify`（lint に組み込み済み）が機械で見る。

## 読む人は誰か
「俺も稼ぎたい」と思って来た人。成功している人が、どうやって稼いでいるかのヒントを見に来ている。長い物語を読みに来たのではない。拾い読みで、各章の答えが1行でわかる文にする。

## 型（全章共通）
- 1項目に答えは1つ。1行目は「見出し＝答え」の言い切り（`answer`、60字以内）。補足は2行目に小さく（`note`、120字以内）。
- 同じ数字・同じ出来事は1か所にだけ書く。数字は上の数字の帯、人物の経歴は「着想」の章、経緯は年表。
- 「本人は〜と語る」「〜と説明している」を答えに入れない（出典の印で足りる）。補足でも多用しない。
- **分からないことは書かない**: 「未確認」「材料に書かれていない」「公開されていない」「不明」など、無いと言うだけの文は画面に出さない（2026-10-07 オーナー指示）。無い項目は、載せずに消す。画面側も、そうした文は自動で落とす（src/shared/absence-text.ts）。
- **出どころの印は、答えの側にも残す**: 本人の申告・公式の主張・推測は「（本人申告）」「（公式の主張）」「（推測）」「（推論）」を答えか数字のそばに付ける。答えだけを読む人に、申告が事実に見えてはいけない。「（本人が語る）」型の長い言い回しではなく、短い印にする。
- 数字には、いつ時点か（年・年度）を付ける。現行の値と当時の値を混ぜない。
- 集客・勝因・失敗の原因は、元の文が言う範囲で書く。「中心」「最大」「すべて」など、元に無い強めは足さない。
- 真似の手順は書かない。事実と、推測の印つきの推論だけ。

## お金の書き方（必須）
読む人は日本人。外貨・外国の単位は、そのままでは伝わらない。円に直して「約◯万円」を必ず添える。
- 為替は固定の概算で換算する: 1ドル=150円、1ルピー=1.75円、1ユーロ=165円、1ポンド=195円。換算したことが分かるよう「約」「概算」を付ける。
- 「ラック」は10万、「クロール」は1,000万。「12ラック・ルピー」ではなく「120万ルピー（約210万円）」と書く。
- 期間を必ず添える: 月商・年商・累計・MRR（月ごとの定期収入）など、何の期間の数字かを書く。
- 「区分」「幅」のような数字は、「500万〜1,000万（通貨不明）」と、不明なことをそのまま書く。

## 章ごとの形
| 章 | 見出し＝答え | 補足 |
|---|---|---|
| 客 | 客＝誰が買うか | 有名どころ2〜3社 |
| 客の痛み | 痛み＝何に困っているか | 創業者の見方など |
| 着想 | きっかけ＝なぜ始めたか（材料に無ければ、その項目は載せない） | 最初にやったこと |
| 最初の客 | 最初の客＝誰、何人 | どう取ったか（事実だけ） |
| 集客 | 中心の取り方＝◯◯ | その他の経路 |
| 事業の形・前金・費用・元手 | 料金・払い方・元手＝◯◯ | 内訳 |
| 勝因・競合・依存 | 強み／競合／弱点＝1行 | 理由 |
| 経緯 | 年表（`年: 出来事。` の形で書くと行に分かれる） | — |

## 置き場所と仕組み
- 画面用の編集文は `data/detail-lines.json`（詳細の各章）と `data/list-lines.json`（一覧の1行）。事例データ本体（ハッシュ保護）には触らない。
- 各文は元の文の指紋（`textHash` / `factHash`）に結ばれる。元の文が変わると使われず、元の文のまま出る。→ 元の文を直したら、編集文も作り直す。
- 将来、事例データを作る段階で `answer` / `note` を直接持てるようになったら、この2ファイルは不要になる（移行は指揮チャットと相談）。

## 項目名と答えは1対1（2026-10-07 オーナー指示・自動化しても守る）

**起きた事**: 項目名（客の痛み・競合・資本と人数・集客経路…）の下に、別の話の文が入っていた
（例: 「競合」の下に手数料の計算例、「集客経路」の下に申込ボタンの改善、「資本と人数」の下に「全部自作した」）。
**原因**: 推論の文を作る時に「この項目名は何を問うか」の約束が無く、材料の近い文をそのまま入れていた。検査も、字数と円換算しか見ていなかった。

**約束（data/item-contract.json）**: 項目ごとに「問い」と「答えに必ず入る語」を持つ。答え＋補足のどこかに必須語が1つも無ければ、`case-text:verify` が落ちる。
自動で文を作る場合も、保存の前にこの契約を通す。通らない文は、別の項目へ移すか、書き直すか、材料が無ければ項目ごと出さない
（detail-lines の `hidden: true`。「分からない」とは書かない）。

| 項目名 | 問い（答えはこれに答える） |
|---|---|
| 客の痛み | 客が何に困っているか |
| 最初の客 | 最初の客は誰で、どう取ったか |
| 集客経路 | 客を集めた経路（何で知らせたか） |
| 事業の形 | 何をどう売って稼ぐか |
| 費用 | 何にいくらかかるか |
| 資本と人数 | 元手と人数 |
| 競合 | 競合は誰で、どこが違うか |
| 依存先 | 何に頼っているか |
| 前金 | 客の金が先に入る仕組み |
| 紹介の報酬 | 紹介の報酬の仕組み |
| 客が抜けにくい仕掛け | 解約しにくい理由 |
| 方向転換 | 何から何へ変えたか |
| 失敗の原因 | 何が悪かったか |

契約の語は粗い検査（その項目の話をしているかの最低線）。最終の判定は、独立した確認役が「この答えは、この項目名の問いに答えているか」を1行ずつ見る。

## 運用の約束（2026-10-07 オーナー決定: 今後100年・自動で作る場合も同じ）

事例画面の文は、次の3つの検査を**全部**通ったものだけを出す。人が書いても、AIが自動で書いても同じ。

1. **機械の検査（`pnpm case-text:verify`、lint に組み込み済み）**: 字数、円換算、出どころの印、「分からない」系の文の禁止、項目と答えの契約（`data/item-contract.json` の `must` / `mustAll` / `mustNot`）、成功の秘訣の形（3〜5点、見出し40字・本文140字、命令形なし）、仕上げ済みの事例で画面の分析欄に出る推論に編集文（`data/detail-lines.json`）が結ばれているか（無い欄は事例名と項目名を挙げて落ちる）。
2. **独立した確認役**: 文を作った者とは別の者が、1行ずつ「この答えは、この項目名の問いに、そのまま答えているか」「材料に無い事を足していないか」を見る。作る者が自分で確認しない。
3. **画面の確認**: 実際の画面（または描画した文字）で、項目名と中身が1対1か、読者が「ん？」となる所が無いかを見る。

**新しい事例を足す時の順序**: 材料（facts / metrics）→ 項目ごとの行（契約を見ながら）→ 成功の秘訣（根拠の factId つき）→ 機械の検査 → 確認役 → 画面。
**材料に無い項目は、その行ごと出さない**（`hidden: true`）。「分からない」と書かない。
**契約を変える時**は、オーナーの指示が元。理由と日付をこの文書に残す。
