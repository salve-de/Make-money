# 事例の文の書き方（詳細・一覧の画面に出る文）

> 2026-10-07 オーナー決定。今回だけでなく、今後つくる全事例でこの形を守る。事例を集める人・AIは、文を書く前にこの1枚を読む。守れているかは `pnpm case-text:verify`（lint に組み込み済み）が機械で見る。

## 読む人は誰か
「俺も稼ぎたい」と思って来た人。成功している人が、どうやって稼いでいるかのヒントを見に来ている。長い物語を読みに来たのではない。拾い読みで、各章の答えが1行でわかる文にする。

## 型（全章共通）
- 1項目に答えは1つ。1行目は「見出し＝答え」の言い切り（`answer`、60字以内）。補足は2行目に小さく（`note`、120字以内）。
- 同じ数字・同じ出来事は1か所にだけ書く。数字は上の数字の帯、人物の経歴は「着想」の章、経緯は年表。
- 「本人は〜と語る」「〜と説明している」を答えに入れない（出典の印で足りる）。補足でも多用しない。
- **分からないことは書かない**: 「未確認」「材料に書かれていない」「公開されていない」「不明」など、無いと言うだけの文は画面に出さない（2026-10-07 オーナー指示）。無い項目は、載せずに消す。画面側も、そうした文は自動で落とす（src/shared/absence-text.ts）。
- **出どころの印は、答えの側にも残す**: 本人の申告・公式の主張・推測は「（本人申告）」「（公式の主張）」「（推測）」「（推論）」を答えか数字のそばに付ける。答えだけを読む人に、申告が事実に見えてはいけない。「（本人が語る）」型の長い言い回しではなく、短い印にする。
- 数字には、いつ時点か（年・年度）を付ける。現行の値と当時の値を混ぜない。
- 集客・勝因・失敗の原因は、元の文が言う範囲で書く。「中心」「最大」「すべて」など、元に無い強めは足さない。
- 真似の手順は書かない。事実と、推測の印つきの推論だけ。

## 日本語の自然さ（2026-10-07 オーナー指示。今後ずっと）
日本語を母語とする一般の読者が、声に出して読んで一度も引っかからない文にする。「約9か月、非公開版で回した」の「回した」のような仕事場の話し言葉は、意味が通っても不合格（→「運営した」）。
- **機械の関門1（辞書）**: `data/natural-japanese.json`。話し言葉（回す／刺さる／〜してる／〜みたい／ガチ／バズる…）、業界用語（初動／突破／マネタイズ／トラクション…）、直訳調（〜することができる／〜にフォーカス）、説明のない英字の略語（GST・SSO・HN…）。語ごとに言い換えの候補を持ち、`case-text:verify` が「何に直すか」まで出す。「資金が回る」「利益を広告に回した」「1万人を突破」など正当な使い方は `allow` で外す。
- **機械の関門2（textlint）**: `.textlintrc.json`。ら抜き・二重否定・冗長な言い回し・誤用・接続詞の連続など、文法の誤りだけ。助詞の重複・文の長さ・句点の規則は、見出し型の短文で誤検出ばかりだったので入れない。
- **AIの関門（独立レビュー）**: `pnpm display:build` の確認役が、くだけた動詞・業界用語・直訳調・名詞止めの連続・主語の抜け・同じ文末の3連続を理由つきで差し戻し、作り直させる（上限3回）。確認役が挙げた語は `data/pipeline/natural-japanese-candidates.jsonl` に残り、`pnpm natural-ja:report --candidates` で辞書がまだ拾えない語が多い順に出る。2回以上出た語は辞書と `scripts/architecture/natural-japanese.test.mjs` に足す（辞書が育つ）。
- **今ある文の直し方**: 1件ずつ手で直さない。`pnpm display:build` が最初に、関門に落ちた行だけを AI に直させ、同じ行の位置に差し替える（紐付け・出典・他の行は変えない。層ごと作り直すと問題の無い行まで減るので、そうしない）。機械の検査と別のAIの確認を通った時だけ反映する（`--repair-only` で直しだけ）。

## 意味が取れる文（2026-10-07 オーナー指示。今後ずっと）
出典と事実が合っていても、初めて見る人が1回読んで意味が取れなければ不合格。起きた事: Practical Typography の「Cool Tools経由はよく払い、Reddit経由はほぼ払わなかった」（「よく払う」が日本語として意味が取れない）、「広告のない、読者の支払いで支える、組版の本」（修飾の3連）、「…を買う、直接支払う、…を買う、の3つ」（誰が何のために払うか不明）。既存の検査はどれも通っていた。
- **規則の正本**: [`.claude/skills/natural-japanese/SKILL.md`](../.claude/skills/natural-japanese/SKILL.md)（主語・述語・対象を書く／直訳調にしない／程度は人数・割合・額で言う／修飾語を3つ以上連ねない／1文1つの事実／「〜の3つ」なら先に何の数かを言う／誰が誰に何のために払うか・何が無料か／固有名詞と専門語は初出で説明／出典の事実は変えない、と悪い例・良い例・自己点検）。人も AI もこの1枚を読む。display:build の生成役・直し役・確認役・読者役のプロンプトは、この1枚をそのまま読み込む（規則をプロンプトに写さない）。
- **機械の関門**: `data/reader-clarity.json`（語の規則。1件ずつ足す）と `scripts/architecture/reader-clarity.mjs`（修飾語の連なり・「、の3つ」・名詞の矢印など形の規則）。`case-text:verify`（lint）が見て、`display:build` の直しの対象にもなる（今ある文を直し終えるまでは警告。直し終えたら `check-case-text-standard.mjs` の `CLARITY_BLOCKING` を true にして落とす）。規則を足したら `reader-clarity.test.mjs` に悪い例と正しい例を足す。
- **AIの読者役**: `pnpm display:build --repair-only --reader`。作った者と別のAIが、何も知らない読者として全行を読み、意味が取れない語句をそのまま引用して理由を書く。指摘が出た行だけをさらに2回読ませ、3回中2回以上で採用。採用した行は作る側のAIが直し、確認役が「元と同じ事実か・意味が取れるか」を見てから反映する。通らなければ反映せず保留（`data/pipeline/display-build-failures.jsonl`）。呼び出し回数・秒・費用は `data/pipeline/reader-pass.jsonl`。

- **導入した外部の道具**（入れる前に、導入時に動くスクリプトが無いこと・ライセンス・保守を確かめ、公開10件の文で当たりを測った。1行に1つ）:
  - `textlint-rule-max-ten`（textlint-ja、MIT、週約14万回の取得）: 1文の読点4つ以上を落とす。603行で当たり1行、それが (C) の「…を買う、直接支払う、…を買う、の3つ」だった。
  - `@textlint-ja/textlint-rule-preset-ai-writing`（textlint-ja、MIT、週約3.7万回、2026-05 更新）: 「ゲームチェンジャー」などの誇張や太字の前置きなど、AIの書き癖を落とす。今の603行では当たり0行で、これから作る文の歯止め。
  - 上の2つは、公開10件を直し終えるまで警告（`check-case-text-standard.mjs` の `CLARITY_BLOCKING` と一緒に関門へ上げる）。
  - 試して入れなかった物: 助詞の重複・文の長さ・弱い表現（理由と件数は `scripts/architecture/textlint-japanese.mjs` の先頭）。外部のスキル2つ（coji/natural-japanese、Forest-Project-Lab/jp-writing-skills、どちらも MIT）は、プログラムを持ち込まずに見方だけを `SKILL.md` の5章に取り込んだ。

## 欄ごとに読む人が知りたいこと（それ以外はノイズ。2026-10-07 オーナー指示）
事実でも、読む人がその欄で知りたい事でなければ書かない。
- **料金**: いくらで何が使えるか。月額・年額と、人数・回数の上限を1〜2文（例「10人まで使えて月約8,750円から（年払い）」）。プラン名は Free・Pro・Team・Business・Enterprise のように意味が通る時だけ。固有の呼び名（Sedan・SUV・Operator など）は人数・回数・機能に言い換える。税・別料金・返金などの付帯条件は書かない。日付の履歴は章の「価格の変遷」だけ。機械の検査は、料金の欄のプラン名と付帯条件（返金・税・GST・別料金）を落とす。
- **規模（提案・未実装）**: 何人が使い（買い）、いくら売れているか。「約◯万人が利用。年商約◯円」を1〜2文。取れていない項目は書かない。画面の欄としての追加は別の変更で行う。
- **売り方**: 誰から何の代金を受け取るか。料金表の細部は料金の欄に任せる。
- **客**: どんな人・会社が買うか。社名の羅列は読む人が知っている名前だけ。
- **成功の秘訣**: その事業がやった事と、効いた根拠。料金表・付帯条件・社名の羅列は入れない。
- 意味の通らない固有名詞・略語は、説明なしで出さない（言い換えるか、要らなければ消す）。

## お金の書き方（必須）
読む人は日本人。外貨・外国の単位は、そのままでは伝わらない。円に直して「約◯万円」を必ず添える。
- 為替は固定の概算で換算する: 1ドル=150円、1ルピー=1.75円、1ユーロ=165円、1ポンド=195円。換算したことが分かるよう「約」「概算」を付ける。
- 「ラック」は10万、「クロール」は1,000万。「12ラック・ルピー」ではなく「120万ルピー（約210万円）」と書く。
- 期間を必ず添える: 月商・年商・累計・MRR（月ごとの定期収入）など、何の期間の数字かを書く。
- 「区分」「幅」のような数字は、「500万〜1,000万（通貨不明）」と、不明なことをそのまま書く。

## 置き場所と仕組み
- 画面用の編集文は `data/detail-lines.json`（詳細の各章）と `data/list-lines.json`（一覧の1行）。事例データ本体（ハッシュ保護）には触らない。
- 各文は元の文の指紋（`textHash` / `factHash`）に結ばれる。元の文が変わると使われず、元の文のまま出る。→ 元の文を直したら、編集文も作り直す。
- 将来、事例データを作る段階で `answer` / `note` を直接持てるようになったら、この2ファイルは不要になる（移行は指揮チャットと相談）。

## 項目名と答えは1対1（2026-10-07 オーナー指示・自動化しても守る）

**起きた事**: 項目名（客の痛み・競合・資本と人数・集客経路…）の下に、別の話の文が入っていた
（例: 「競合」の下に手数料の計算例、「集客経路」の下に申込ボタンの改善、「資本と人数」の下に「全部自作した」）。
**原因**: 推論の文を作る時に「この項目名は何を問うか」の約束が無く、材料の近い文をそのまま入れていた。検査も、字数と円換算しか見ていなかった。

**約束（data/item-contract.json）**: 項目ごとに「問い」と「答えに必ず入る語」を持つ。答え＋補足のどこかに必須語が1つも無ければ、`case-text:verify` が落ちる。
自動で文を作る場合も、保存の前にこの契約を通す。通らない文は、別の項目へ移すか、書き直すか、材料が無ければ項目ごと出さない
（detail-lines の `hidden: true`。「分からない」とは書かない）。

| 項目名 | 問い（答えはこれに答える） |
|---|---|
| 客の痛み | 客が何に困っているか |
| 最初の客 | 最初の客は誰で、どう取ったか |
| 集客経路 | 客を集めた経路（何で知らせたか） |
| 事業の形 | 何をどう売って稼ぐか |
| 費用 | 何にいくらかかるか |
| 資本と人数 | 元手と人数 |
| 競合 | 競合は誰で、どこが違うか |
| 依存先 | 何に頼っているか |
| 前金 | 客の金が先に入る仕組み |
| 紹介の報酬 | 紹介の報酬の仕組み |
| 客が抜けにくい仕掛け | 解約しにくい理由 |
| 方向転換 | 何から何へ変えたか |
| 失敗の原因 | 何が悪かったか |

契約の語は粗い検査（その項目の話をしているかの最低線）。最終の判定は、独立した確認役が「この答えは、この項目名の問いに答えているか」を1行ずつ見る。

## 運用の約束（2026-10-07 オーナー決定: 今後100年・自動で作る場合も同じ）

事例画面の文は、次の3つの検査を**全部**通ったものだけを出す。人が書いても、AIが自動で書いても同じ。

1. **機械の検査（`pnpm case-text:verify`、lint に組み込み済み）**: 字数、円換算、出どころの印、「分からない」系の文の禁止、項目と答えの契約（`data/item-contract.json` の `must` / `mustAll` / `mustNot`）、成功の秘訣の形（3〜5点、見出し40字・本文140字、命令形なし）、仕上げ済みの事例で画面の分析欄に出る推論に編集文（`data/detail-lines.json`）が結ばれているか（無い欄は事例名と項目名を挙げて落ちる）。
2. **独立した確認役**: 文を作った者とは別の者が、1行ずつ「この答えは、この項目名の問いに、そのまま答えているか」「材料に無い事を足していないか」を見る。作る者が自分で確認しない。
3. **画面の確認**: 実際の画面（または描画した文字）で、項目名と中身が1対1か、読者が「ん？」となる所が無いかを見る。

**新しい事例を足す時の順序**: 材料（facts / metrics）→ 項目ごとの行（契約を見ながら）→ 成功の秘訣（根拠の factId つき）→ 機械の検査 → 確認役 → 画面。
**材料に無い項目は、その行ごと出さない**（`hidden: true`）。「分からない」と書かない。
**契約を変える時**は、オーナーの指示が元。理由と日付をこの文書に残す。
