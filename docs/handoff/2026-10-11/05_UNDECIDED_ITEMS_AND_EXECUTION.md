# 05｜未決事項・実装の優先順・受入条件

2026-10-11のこの長大チャットに基づく**最新の作業台帳**。PR #221の契約・制作・採算の未決78項目と競合しないように、**現フェーズの世界の需要・成功のエッセンス・最新情報のUX**に絞る。

## 0. 完了／未完了の境界

| 作業 | 完了・確認できた範囲 | 残っていること |
|---|---|---|
| オーナーの目的と禁則の整理 | 会話とこの引継ぎに記録 | 次のモックをユーザーが最終承認したかは未確認 |
| 需要を第一階層とする情報設計 | 複数の案とモックを会話で提示 | 実利用者の初見テスト／有料支払意思 |
| 事例横断の成功エッセンス | PR #220の35件前後の資料をもとに編集例を作成 | 全収録母集団の系統的な分析、失敗事例との対比 |
| 世界の最近の需要情報 | Google Trends、Pinterest、Etsy、Stack Overflow、Google Ads等を候補として調査し、一部公式資料を静的モックへ | 商用API・自動収集・再配信許可・継続的な実データ |
| 日本・海外の地域別カテゴリ | 大分類と複数タグの候補 | 多言語データでの分類精度、同義語・季節調整 |
| モック操作 | 過去回答ではHTML／PNG／ZIPと画面試験を報告 | HTML本体のGitHub版管理、統合先選定、本番UIの独立試験 |
| AI分類・鮮度・未読・監視 | 詳細方針と静的UI例 | 実際のジョブ・DB・API・通知、観測差分の持続 |
| 公開先の権利 | 公的統計の一部の条件・外部候補を調査 | **ソースごとの商用再配信契約の読込・サインオフ** |
| 本番課金・公開・外部API支出 | **本会話で何も実施していない** | 別の明示的承認と契約／QA |
| 外部AI制作・マーケット | PR #221などに多数の案・監査資料 | 今フェーズ外。採用provider／責任境界／本人契約E2E未決 |

## 1. P0／P1／P2で進める

### P0：まず情報の商品価値を検証する（デザインより先）

**P0-1：全資料の現在地**
- mainのOWNER_INTENT／PRODUCT_FINAL_PLAN／収集権利ゲート、PR #221の最新訂正と未決、PR #220の事例本文、現在の公開API/UIを**読み取りのみ**で照合。
- 事例カタログ件数、公開可能数、商用権利の分類、既存の収集スケジュール／停止理由を当日の事実で記録する。昔の「3,380件／公開33件」を無条件に現在数としない。
- 既存ケースの完成画面を壊さず、どこから新しい傾向のページへ情報を供給するかを決める。

**P0-2：実際に人が欲しがる情報のサンプル**
- 少なくとも**20〜30件程度の独立した「需要の発見」**を候補として収集。件数はUX検証のための目安であり、架空の成功基準・公開ノルマではない。
- 特定企業の名前をトップに並べるのではなく、需要や支払行動が何かを一般の人が分かる題名にする。
- 国内・海外、法人・個人、継続需要・趣味娯楽、ソフト・物販・実業など複数分野を網羅。ジャンルに無理な上限を設けない。
- 各候補に「誰の」「何のため」「検索／購入／支払い／発注／課題のうち何が事実か」「国」「観測期間」「増減の分母」「出典」「未確認」「商用表示許可」を記録。
- AIで候補を量産する前に実在の原典で裏付ける。**検索増＝購入増としない。**
- 最近の検索関心と古い事例の新しい発見は、**別の表示枠**で評価する。

**P0-3：有料で商用表示できる情報源を実証**
- 最初の候補：Google Trends（正式アクセス条件）、Google Adsキーワード指標（承認と再配信）、DataForSEO（契約・原価・派生利用権）、Pinterest/Etsyの公式公開レポート、正規ライセンスの購買・広告・調達データ。
- 「閲覧可」「APIあり」「社内分析に利用可」「会員サイトで再表示可」「データそのものを再販可」を**5つ別々の欄**で判定。
- 未許可の生データを取り込んだ大量商用DBを本番公開しない。正確な出典と必要な帰属を保持。
- 日本政府統計・Eurostat等は背景の補助に使う。**日本のマクロ指標をトップ需要の代用品にすることは禁止**。

**P0-4：競合より魅力的な情報価値の判定**
- 「成功した会社が1社ある」ではない、新しい発見・現在の検索や購入・関連する成功構造を示す。
- 既存のExploding Topics／Trends.vc／Similarweb／Starter Story等の有料価値と比較し、「なぜこの情報をここで見たいか」を明確にする。
- 価値が確認できなければ、カードや図やランキングを増やすだけの実装には進まない。

### P1：公開可能なデータを再現性のある経路で届ける

**P1-1：ソース契約レジストリ**
- ソースID、ライセンス版・取得者・許可行為、料金・レート・最大保存期間、公開指標、帰属、停止条件を登録。変更履歴・確認URL・審査者・確認日を保持。
- ソースごとの価格・月額コスト上限と支払停止／通知を設計。
- MAKEMONEY既存の品質・権利ゲートと整合し、「新しい収集」だけ異なる安全基準にはしない。

**P1-2：ソースごとのデータコネクタ**
- 少数ソースで小さいE2Eを作って実証。初回から数十APIの同時導入はしない。
- 取得→原本の適法保存→観測票の作成→重複排除→時間比較→AI分類→出典照合→権利公開判定→通常の公開データストア→API→ブラウザ表示を通す。
- 既存の収集スケジュールやR2を勝手に直書き・上書きしない。先に権限と保存・公開の正式な契約を照合。
- **新情報がない日の「最新ニュース」生成を禁止**。イベントの観測と記述を区別する。

**P1-3：需要テーマの同定・多言語の分類**
- 英語・日本語のキーワード同義語、重複する記事、部分的に重なる需要をテーマIDに整理。
- 既存の大分類（売上・集客、業務効率、費用・資金、リスク・安全、制作・販売、学習、生活・健康、趣味娯楽、金融資産）を軸に複数タグ分類。
- 人が監査した正解データで分類精度を評価。未確認・曖昧・季節性の強いものは公開前の保留へ。
- 将来新しい分類を追加できる拡張性を持つ。新しい需要が出ても古いカテゴリのタグを機械的に変えない。

**P1-4：最近の変化の計算と公開**
- 時点・地域・観測対象・単位が揃った値だけで増減を計算。表示は出典URL、変化を測った期間、絶対数が不明かどうかも含める。
- 項目ごとに「最近実際に変わった／最近新しく発見した／長期の構造」の3状態を持つ。
- 成功のエッセンスの主張は、複数のケースと反例・成立条件に結びつける。もともと成功例のみの標本なら成功率や因果主張は出さない。

**P1-5：利用者向けUI（必須）**
- 最初の1画面に需要の種類・最近の発見・地域・比較期間・実データを配置。企業名だけ・アナリスト用説明だけ・「今日やること」だけで埋めない。
- 「最新」「需要を探す」「成功のエッセンス」「市場の変化」「監視／保存」の導線候補を実データで検証。ただしタブ名称・数はまだ最終決定ではない。
- 実行していないAPI／本番更新／AI分類を「現在の完成機能」に見せない。
- 出典確認→詳細→類似する収益構造→アイデアというクリック導線。事例ページを複製せず、必要になったときだけ個別事例へ。
- 作り込み時に不要な専用比較画面、長いコンセプトコピー、無意味な背景装飾や架空の指数を入れない。

**P1-6：QA**
- PC/スマホ360、390、768、1024、1440px等の実際のレンダリング。
- フィルタ／検索／未読／保存／日付／比較不能表示／データ不足／撤回・修正／ソース停止を操作。
- UIが表示できても、情報の本当の価値と課金継続は利用者テストと継続データで別に検証。

### P2：継続利用・収益化・長期構想

- 有料にするのは汎用的な事例の件数でなく、権利確認済みの深い需要情報、独自分析、条件別の監視、再現可能性判断、実際の機会。何を無料公開するかは検証で決める。
- 課金単価・継続率・利用単価・原価・API契約の損失責任・運用人件費を測り、**オーナーの実質利益を最大化**。
- 「アイデア」は見るだけの人にも楽しく、深掘りする人にも役立つ。まだ作らない人へ本番SaaS制作を強制しない。
- Build／Launch／Market／Affiliate／Stripe等の長期機能はPR #221の未決ゲートをクリアした後に再検討。個人SaaSホスト責任をMAKEMONEYへ無条件に戻さない。

## 2. 本当に未決の事項と担当の合格条件

| 未決 | 現在の状態 | 次に確認する一次情報／実測・合格条件 |
|---|---|---|
| Google Trendsの商用定期取得 | 公式の限定API／公開UI等、別ルートの権利は未確定 | 契約で有料会員表示と保存が可能・日本運営者の利用可否が明確 |
| DataForSEOの正式採用 | 料金・APIの存在は調査。MAKEMONEYでの再配信権は未確認 | 日本でのB2C SaaS用途に限る見積・配布許可・保存条件・費用試算 |
| Pinterest/Etsyの定期・商用データ | 公式の傾向記事で具体例は確認。フルAPI／転載許諾未決 | 自動取得・再利用・表示の権利／入手頻度／数値の再現が確認できる |
| Reddit/X/TikTok/レビューの課題データ | シグナル候補。商用データ契約が必要となり得る | 公式許諾／原発言の利用範囲／個人データ保護を確認 |
| 国・言語の拡張順 | 日本だけに限定しない要望は明確。具体国別の優先度は未決 | 検索需要、販売単価、権利、競争、データコストと読者の価値で判定 |
| 需要テーマの正式分類 | 9大分類＋複数タグの暫定案 | 実データの手動ラベルで粒度・重複・新分野への対応を確認 |
| AIモデル・抽出方式 | 安価な分類は可能だが精度は未測定 | 価格・日本語／英語正解率・偽陽性・根拠抽出・運用コストを評価 |
| 監視頻度 | 日次/週次/発表時の案のみ | ソース更新頻度、権利、原価、ユーザー価値に合い、空更新を作らない |
| 需要急増と「稼げる機会」の接続 | 複合シグナルの仮説 | 支払意思・競争・販路・原価の根拠を複数確認 |
| 成功のエッセンスの集計 | 少数のPR #220資料による編集見本 | 全収録範囲を母集団として定義、業種と失敗を含む偏りを可視化 |
| 本番UIデザイン | 多数のモック、採否未決 | 比較対象と実データを揃え、初見・発見・操作・再訪で評価 |
| 情報の商用表示・原典画像 | 権利ゲートは存在、各データの追加審査が必要 | 収集契約・出典・短文・画像・派生データを個別に公開可判定 |
| PRO価格・無料枠・価値提案 | PR #221の料金案、最新の観測データ原価未反映 | 利用者への価格検証・API費用・実利益計算 |
| 外部AI・SaaSホスティング | 長期の検討範囲、現フェーズでは対象外 | PR #221の未決E2E、本人契約、責任・補償などを別の意思決定へ |

## 3. 次の作業者が**勝手にやってはいけない**こと

- 既存事例のレイアウト、行構成、タグ、絞り込み、本文、画像ギャラリーを無断変更。
- 本番のR2/D1/Universal Foundation、EDINET正本、既存収集タスクのスケジュール・品質ゲート・権利ゲートを無断修正。
- 新しい定期実行タスクやGitHub Actionsを、設計のために勝手に起動／配置する。
- APIの実費課金・外部サービス契約・ユーザーアカウント・外部公開・本番デプロイ・送金・本番決済を、試作の延長で自動実行。
- スクレイピング禁止を回避する手段、権利確認を後回しにした転載、需要スコアや成功率の創作。
- Providerが実際には許可していない「本人契約のままMAKEMONEY内で完全操作可能」を保証。
- 今まで「最終」と書いてある文書を、現在も承認済みの現行仕様だと宣言。
- 「需要」という曖昧な単語を使って、人口構造の変化やマクロ景気統計を直接の購買ニーズへ変換する。
- UIで抽象的コピー・設計思想の説明・表面的な教訓を大量に出す。
- 成功事例数が多い＝高い成功確率と誤解させる。

## 4. 最小の良いE2Eの完了定義

**次の担当者へ推奨する小さな実証：**

1. 少なくとも1つの正式に許諾された検索／購買に近い世界のデータ源と、補助ソースを選定。実費と公開権を先に確認。
2. 日本・英語圏の一部地域、2〜3のカテゴリで、公表日・観測対象期間付きの実データを取得。
3. 類義語と重複を整理し、最新の変化の事実だけをDBへ。標本の分母が不明な％はそのまま「不明」と記録。
4. 成功のエッセンスの根拠となるPR #220等の事例へ、対象需要が一致する場合だけ接続。
5. 権利・品質・出典のゲートを通った情報だけ、正式な通常公開経路からブラウザで確認。
6. 不明な権利・古い情報・市場が未確認な場合のUIを実際に触って確認。
7. クリック・保存・再訪・新着の価値を第三者がテストして、有料化判断の資料にする。
8. 以上に未完了があれば「設計完成」や「完全実装」「本番稼働」と呼ばない。

## 5. 後のチャットから再開する場合の一文

> MAKEMONEYは、直近フェーズで実在事例＋世界の最新の需要・購買・検索シグナル＋成功のエッセンス＋アイデア発想を価値の中核にする。まず docs/handoff/2026-10-11/README.md の関連文書とPR #221/#220を読み、最新の禁則・未決・商用データ権利を守って、事実の収集・公開可否・UIを実証せよ。古い制作・販売・料金案の自動採用や、本番変更をしない。オーナーが本当に欲しい情報が最初の画面で分かるかを優先する。
