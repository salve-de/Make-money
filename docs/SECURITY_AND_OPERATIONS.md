# Security, Moderation, and Production Operations

## 1. Principle

GOLDMINE RADAR handles untrusted URLs, user claims, financial figures, promotion money, and behavioral data. A record must not become public merely because it was submitted or generated by AI.

```text
Untrusted submission → automated checks → human review → publish / reject / request changes
```

## 2. Trust boundaries

### Browser

The browser may hold only public configuration and user-scoped tokens. Never expose:

- Supabase service role key
- moderation secrets
- claim challenge hashes
- private source files
- Stripe secret keys

### Route handlers / server actions

The server validates and normalizes input before database writes. Production endpoints require:

- body-size limits
- schema validation
- rate limiting
- origin and CSRF controls for state-changing browser requests
- authenticated user binding
- audit events for moderation and promotion changes

### URL ingestion worker

Do not fetch a submitted URL directly inside the public request lifecycle. Queue it for a restricted worker.

Reject:

- localhost and loopback
- RFC1918/private networks
- link-local and metadata endpoints
- non-http(s) schemes
- excessive redirect chains
- redirect from public to private IP
- oversized responses
- executable/binary payloads when HTML is expected

Resolve DNS again after redirects and before connection. Set strict time, byte, and content-type limits. Sanitize extracted HTML. Do not execute arbitrary page JavaScript in the first production release.

## 3. Submission moderation

Automated checks:

- URL and domain normalization
- duplicate domain and duplicate claim detection
- malware/safe-browsing check
- prohibited category screening
- suspicious revenue language
- amount-type completeness
- source availability
- affiliate-link disclosure
- paid-promotion disclosure

Human review:

- Does the source support the exact claim?
- Is the amount revenue, profit, MRR, ARR, GMV, funding, contract ceiling, actual spend, asking price, or estimate?
- Is the time period visible?
- Are payer and recipient correctly identified?
- Is the evidence grade justified?
- Is the opportunity inference separated from source fact?
- Are risks and unavailable facts shown?

## 4. Evidence grades

- **A:** primary official, statutory, confirmed transaction, audited material
- **B:** direct party disclosure with corroboration
- **C:** credible third-party estimate
- **D:** unverified self-report
- **DEMO:** fictional value used only to test UI and structure

Never display `metrics_connected` as `audited`. Never label a third-party estimate as confirmed revenue.

## 5. Claim ownership

Supported methods:

1. domain email
2. DNS TXT challenge
3. HTML meta challenge
4. manual company-document review

Challenges must:

- expire
- be stored as a hash where possible
- be single-use
- be bound to product, claimant, and method
- be revocable
- generate an audit event

A successful Claim grants profile editing and analytics access. It does not validate revenue claims automatically.

## 6. Organic and paid separation

Promotion data lives in `promotions`. Organic ranking is calculated from evidence, freshness, momentum, accessibility, competition, and quality-adjusted reactions.

The organic ranking view must not join:

- promotions
- campaign budget
- vendor plan
- affiliate payout
- direct commercial relationship

Paid placement must always show a disclosure label such as `プロモーション`. Promotion eligibility is a separate moderation decision from organic quality.

## 7. Database access

- Enable RLS on every user or moderation table.
- Public users read only published/accepted records.
- Users read and change only their own reactions and claims.
- Submissions are untrusted and private until approved.
- Editors/admins operate through explicit role checks.
- Service-role operations run only on the server.
- Moderation actions are immutable audit records.

The migration in `supabase/migrations/0002_goldmine_core.sql` is the implementation baseline.

## 8. Personal data

Collect the minimum required data.

Initial production data:

- account identifier
- handle/display name
- contact email for a submission
- saved/reaction state
- claim verification state
- consented analytics events

Do not sell identifiable browsing history. Do not expose an individual user's Opportunity interests to vendors. Vendor analytics should begin with aggregated, thresholded reporting.

## 9. Analytics guardrails

Vendor analytics may show:

- aggregate views
- saves
- comparisons
- external clicks
- referring Opportunity
- broad geography/device/category when thresholds are met

It must not reveal:

- named users without explicit consent
- small cohorts that allow re-identification
- private MY GOLDMINE contents
- email addresses as leads unless the user explicitly submits an inquiry

## 10. Incident handling

Severity examples:

- **SEV-1:** credential exposure, unauthorized private-data access, promotion contaminating organic rankings at scale
- **SEV-2:** false financial claim broadly distributed, claim takeover, moderation bypass
- **SEV-3:** isolated incorrect record, broken source, spam wave

Response:

1. contain and disable affected path
2. preserve logs and audit state
3. revoke credentials/challenges
4. correct or unpublish records
5. notify affected users when required
6. document root cause and prevention

## 11. Launch security checklist

- [ ] production environment variables configured outside Git
- [ ] RLS tested with anon/member/editor/admin roles
- [ ] rate limits on submission, reaction, claim, login
- [ ] URL worker SSRF tests
- [ ] content sanitation tests

- [ ] audit log retention defined
- [ ] privacy policy and terms published
- [ ] promotion disclosures tested on mobile
- [ ] DEMO records excluded from production index
- [ ] robots/indexing enabled only after real-data review
