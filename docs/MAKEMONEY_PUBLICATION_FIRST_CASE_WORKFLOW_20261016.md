# MAKEMONEY｜UIで読める記事を調査と同時に制作する実務基準（2026-10-16）

> 適用対象：ChatGPTの毎時記事制作、単発の取材、他AIによる事例執筆、Codexの受入・非公開プレビュー。これは**制作・編集基準**であり、公開・課金・deploy・新Cron・R2/Drive/GitHubの定期書込の承認ではない。
>
> 優先順位：2026-10-16の `MAKEMONEY_OWNER_GOALS_AND_CODEX_HANDOFF_20261016.md` とオーナーの最新指示を守る。PR #224のPlausible Analytics記事・UIを品質・表示の**参照例**とする（全数値・R2原本の独立検証済みと誤認しない）。PR #225の古い固定的・過剰厳密なルールは最新方針に読み替える。

## 1. 一文で表す目的

**UIで何を伝えるかを考えてから調査し、調査中に見出し・説明・表・図を作り、不足した情報を追加調査して、日本語の読者向け完成記事と広範な研究原本を同時に残す。**

禁止する流れ：事実を項目ごとに大量取得 → 先にJSON化 → 後工程で断片の自動連結・定型要約 → UIへ流し込む。これは「正しい断片」でも肝心の商売の過程が分からない記事になる。

採用する流れ：候補比較 → 読者が持ち帰る固有の発見の仮説 → 公式・創業者・一次記録を調査 → 仮の掲載見出しと本文・使う図表を作る → 主語・行動・理由・反応・結果の欠落部分を再調査 → 編集・出典照合 → **記事全文**と研究原本を保存 → Codexが意味を改変せずに既存UIへ取り込む。

## 2. 最初に選ぶ事例

国・規模・分野を限定しない。個人SaaS、AI、物販、製造、食品、媒体、広告、店舗、現場サービス、仲介、プラットフォーム等から探す。会社規模や一般的な有名さより、商品の独自性、最初に売れた行動、拡大の実際、収益の仕組みを**具体的な資料で説明できるか**を優先。既存の完成・未完成記事、モック、旧研究原本、別名と公式ドメインと改訂版を、アクセスできる範囲で重複確認。全資料が見えない場合は照合範囲を内部に残す。

候補段階で原典により「何を、誰に、なぜ、どう売れ始め、何を変えて、どう広がったか」が全く追えない場合、薄い完成記事を無理に出さず別候補を探す。例外的なビジネスの仕組みが詳しく分かる場合は売上額・初客名が不明でも有用な事例になり得るため、固定項目の足切りにはしない。

## 3. 常に持つ二つの成果物

**A：UIへ表示する日本語の完成記事。** 具体的なタイトル、1〜2文のリード、最小限の代表実績、実際に読んで理解できる本文、関連する出典。標準の本文分類は **概要／仕組み／お金／集客／運営／経緯／成功の理由** の7種類、最後に別枠の出典。種類と順序を共通化するが、材料のない任意章は非表示。章内の小見出し・文章量・箇条書き・表・年表・SVGは事例別に自由。読者向け本文に制作メモ・規約チェック・空欄の言い訳を入れない。

**B：UIの外側の広範な研究原本。** 正式名・別名・公式ドメイン・事例ID・出典URL・掲載日・調査日・引用箇所・主張の根拠・数値の期間・通貨・対象範囲・発見した別の資料・初期資金・人脈・競合・仕入れ・採用・外注・失敗・依存・権利・画像候補・未確認点・修正履歴等。記事に使わない有用な情報も捨てない。将来の比較・検索・成功の共通構造・機会発見・記事改訂に再利用する。

AとBを順番に別担当で作るのではなく、一つの取材・執筆プロセスで往復する。Bに事実が記録されたことをAの品質合格とは呼ばない。Aが完成していてもBに根拠が無ければ掲載合格ではない。

## 4. 取材中に何を明らかにするか

- **商品・顧客**：実物／利用場面、利用者・支払者、購買理由、競合との違い、当時の商品と現在の商品。
- **収益**：顧客が何にいくら払い、誰が受け取るか。課金単位、料金の変遷、初期売上、継続購入、GMVと会社売上の区別。公表された実績は時点・期間・定義付きで。
- **開始条件**：創業の動機、創業者の技能・前職・人脈、既存顧客、初期資金、製造・開発に使った設備と時間。ゼロから始めたと決めつけない。
- **最初の顧客**：誰をどこで見つけ、どんな製品や訴求を提示し、どんな反応・購入があったか。SNS/SEO/営業等の単語だけで終わらない。
- **拡大と転機**：投稿、報道、検索、口コミ、紹介、販売店、広告、提携、調達等の具体的な接点と行動 → 顧客側の反応 → 可能なら数量・収益・時期。成功の理由を後知恵で創作しない。
- **運営**：開発・物流・製造・サポート・仕入れ・人数・費用・外注・必要な権限や規制。商品が現実にどう届いたか。
- **業種固有の事実**：消耗品の再購入、仲介の売り手・買い手両側、プラットフォームの供給獲得、媒体の読者と広告主、店舗の立地と人員、ソフトの無料/有料転換等。

列挙は収集の入口であって、全項目の機械的な穴埋め義務ではない。予定外の重要な発見は取り逃がさずBへ入れ、価値があればAの見出し構成も変更する。

## 5. 読者向け原稿の編集

- 書き出しは事業固有の意外な行動・売り方・実績を正確に示す。会社紹介や抽象的なスローガンで始めない。
- 大見出しは共通分類、小見出しは質問ではなく**具体的な答え**（例「競合の不満を扱った記事から無料体験へ誘導」）。無意味な重複見出しを避ける。
- 「SNSで集客」「ネットワーク効果」「顧客中心」などの説明停止語を使わず、実際の行動・接点・反応・仕組みに分解する。
- 記事に載せるのは、その文を読むことで商品・支払・初客・拡大・仕事の実像が新しく分かる情報。空欄埋め、意味の薄い注意書き、無関係なリスク・損失、同じ内容の再掲は本文から除きBへ残す。
- 文章は日本語として自然に繋げる。読者が初めて見る固有名詞・専門語には必要な説明を添える。短くすることだけを目的にしない。
- 推論は元事実と区別し、有意義な根拠と限界をBに残す。根拠があれば分析もできるが、計測されていない因果・売上・初客を事実として作らない。
- 文章だけでは分かりにくい関係は、順序付き工程、箇条書き、料金表、時点の揃った年表・実数推移、元資料に忠実なオリジナルSVGを選ぶ。図の枚数ノルマはない。第三者の製品画面・写真は出所、権利者、転載条件、用途を確認し、許可根拠なしにコピー・同梱しない。

## 6. Plausible Analyticsから再現すべき「品質」であって、固定テンプレではないもの

PR #224 の `data/case-articles/ent_plausible/article.json` を参照。無料のGoogle Analyticsと何が違うか、2019年の初期利用者60人、有料化、2020年の訴求変更、記事経由の訪問・無料体験、料金と2022年6月の月次売上、少人数の運営を**それぞれ具体的な段階**として描いている。これを「9出典を集める」「全社同じ数の箇条書き・金額・SVGを描く」と取り違えない。情報の正確さは掲載前に別途原典照合する。

旧Rightmove r1のように2025年決算・会員数・一般的な両面市場の説明だけ詳しく、2000年前後の設立、2002年の課金転換、初期の物件・仲介事業者獲得方法が薄い場合は、**保存できても編集未合格**。追加調査と原稿修正を優先する。Who Gives A Crapの初期予約販売と口コミ・定期購入の筋道は良い参考だが、各数値の原典・権利の独立検証は別。

## 7. 成果物を既存UIへ渡す契約

ChatGPT：完成原稿 `article.md`、出典・研究記録 `research-rights.json`、必要な `figures/*.svg`、画像参照/権利記録、事例ID・公式ドメイン・改訂番号を用意し、保存できた実物だけを納品と呼ぶ。形式の変換やR2/GitHub/Drive書込を記事完成の必須条件にしない。

Codex：Libraryの累積ZIP・個別ZIP・古い形式の実ファイルを受け取り、**原文と研究原本を保全**。ZIP・SHA検証／重複・改訂照合／UI用 `case-article.v2`、`research.json`、`identity.json`、SVG等への変換／非公開一覧・詳細への表示／PC1440・タブレット768・スマホ390のブラウザ確認を担当する。すべての改訂は非破壊。変換で根拠のない文章追加や強制要約をしない。記事の価値を見て要編集ならdraftに保留し、未確認画像は掲載しない。

UIの共通部品：`facts`、`paragraph`、`steps`、`rates`、`table`、`timeline`、`list`、`subheading`、`figure`。本文分類と末尾出典を固定し、中身は可変。初期の編集担当が文章・表・図を考え、Codexは意味を崩さず該当部品へ移す。**技術形式が正しくても編集PASSにはならない。**

保存実績（2026-10-16午前）：ChatGPT Library「Make money」の2事例累積ZIP＋個別ZIP。累積ZIPが毎時欠損なく更新されることは未実証。Codexに正式なLibrary直接一覧・取得機能があるとは仮定しない。現実的な暫定運用は、ユーザーが必要時に累積ZIPまたは複数個別ZIPをダウンロードしてCodexの受信フォルダに置き、一言で取り込ませる方式。以前に失敗したScheduled Task→R2/GitHub/Drive書込を無検証で再提案しない。

## 8. 検査と合格条件

**編集検査（最重要）**：初見で何を売り誰が払うか分かる／実際の最初の客・販路と後の成長が可能な限り具体的／主体・行動・反応・結果の関係が伝わる／売上と利益等の数値の意味を誤認させない／不自然な翻訳と重複・一般論がない／資料不足は調査や候補変更で解決を試みる。記事を実際に通読して判断。

**根拠検査**：出典URL・発行日/取得日・原典箇所が実在、主張と対応する。公開資料の範囲を越える推測や架空の数字を入れない。機械での引用キー整合だけでは原文の真偽は証明しない。

**技術検査**：ZIP実物の読戻し・hash・manifest、旧原本不変、複数ZIP・累積ZIP・改訂版、同じZIPの二度目は追加0、構造化時の情報損失検知、SVG安全性、非公開UI表示の実画面確認。実測なしにPASSと報告しない。

**公開検査**：商用画像・転載権利、オーナーによる記事承認、本番目録/R2/デプロイ/課金は別工程。今回の調査・受入・非公開プレビューから自動昇格しない。

## 9. 運用上の優先順位

1. 既存の毎時収集は維持。出力件数より記事品質を優先して内容を改善する。**毎回の完成を保証できない場合は未完成と報告し、保存やZIP統合に成功しただけで記事完成と言わない。**
2. 内容改善・追加調査はChatGPT側。Codexは技術受入と非公開表示側。低品質記事を自動整形で「完成」と偽らない。
3. まず実ファイル（Rightmove／Who Gives A Crap）で受取・変換・非公開UIを検証し、ユーザーの手間を「ZIP渡し→未取込を取り込んで」まで減らす。
4. 旧34件、別パッケージ、50件モックは新累積ZIPの全件に含まれたとは数えない。研究メモと掲載可能な完成記事を混同しない。
5. 完全自動でR2へ連続納品したい理想は残すが、正式に動作検証しユーザーが承認するまでは未採用。


## 10. 収集設計の詳細：何を、どの観点で、どう集めるか（2026-10-16追補）

### 10-1. 研究の目的と成果の3層

収集は「企業名と数値を集めて最後に文章化する作業」ではなく、①読者に価値を提供する完成記事、②それを裏付ける広範な研究原本、③後の比較と発見に使う横断索引の3層を同じ調査から生み出す作業とする。

- **読者向け記事**：この企業特有の「何を誰に売り、なぜ買われ、どう初客を得て、何を変え、どう拡大したか」を、日本語の自然な順序と意味のある表・写真・図で説明。後工程に機械的な要約・つぎはぎを委ねない。
- **研究原本**：記事に出さなかった競合、失敗、契約、資金、価格推移、当事者の背景、製造・配送、顧客反応、技術、証拠、取得できなかった項目、権利・確認情報も残す。ただし著作権保護表現の不必要な全文複製は行わず、事実・短い根拠・リンク・出典箇所で保持。
- **横断索引**：確認できた属性だけをタグ・数値・時点付きで保持。顧客タイプ、収益モデル、集客起点、拡大メカニズム、運営・初期資源・業種・地域・事業段階を検索・比較可能にする。これを元に記事を自動生成しない。

### 10-2. 調査観点（漏れを検知するための探索領域。全項目表示・空欄埋め義務ではない）

| 領域 | 実際に調べて説明できるようにすること |
| --- | --- |
| 1. 身元と事業範囲 | 正式法人／商品／サービス／ブランド／別名／公式ドメイン。誰の業績か、買収や改称で混同しない。 |
| 2. 商品・使い方 | 顧客が目で見て理解できる実物・画面、商品価値、購入から利用・納品まで、無料と有料の違い、販売当初と現在の違い。 |
| 3. 需要と購入心理 | 誰がどの状況で何に困り、代替手段と比べ何が改善し、なぜ対価を払うのか。観察と推論を区別する。 |
| 4. 顧客・支払者・参加者 | 利用者と支払者、企業の決裁者、売り手・買い手・広告主、誰が何を提供し何を受け取るのか。 |
| 5. 料金と売上構造 | どの商品・成果・広告枠・利用量に対して単発/定期/手数料をいくら支払うか、プラン・販路・価格変遷・割引・解約。 |
| 6. 経済性 | 原価、仕入、物流、決済、広告、労働、運営費、粗利・営業利益・資金繰り・分配。数字が不明なら作らず、利益を事実として扱わない。 |
| 7. 創業者と初期資源 | 創業理由、本人の技能・職歴・人脈・資金・時間・既存ファン・設備・取引先。背景なしの創業だと決めつけない。 |
| 8. 企画から初販売まで | どの仮説を試し、何を作り、どう売り込み、誰に提案し、何を反応として得て、有料の最初の客・注文・供給者をどう得たのか。 |
| 9. 集客・広まり方 | 投稿/検索/広告/紹介/営業/報道/口コミ/卸/店舗/プラットフォームの**実際の接点、表現、行動、相手、反応、結果、時点**。施策名だけで終えない。 |
| 10. 購入・継続・自然拡散 | 発見→体験→購入→再購入・紹介・解約の実際。無料から有料・反復注文・口コミ・供給者獲得など、存在する経路だけ記録。 |
| 11. 成長の転機と過程 | 価格や製品の変更、販売チャネル追加、著名人・報道・提携、競合の変化、市場変化、規制・技術の変化、人数・売上の前後関係。 |
| 12. 実際の運営 | 人数と役割、調達、開発、製造、在庫、配送、サポート、外注、設備、運営時間、契約・許認可、外部依存。 |
| 13. 競争と独自性 | 顧客が代替商品ではなく当該商品を選ぶ理由、差別化、模倣障壁、ブランドや販路、既存プレイヤーとの差とその時点。 |
| 14. 成果と事業の現況 | 年月ごとの売上・利益・MRR・ARR・GMV・取引数・有料顧客・販売個数、買収・撤退・事業売却・現存状況。混同しない。 |
| 15. 試行錯誤・限界 | 試したが売れなかった商品・告知・契約、方向転換、資金・供給の不足、失敗から成功への実際の変更。無関係な失敗は研究原本へ。 |
| 16. 出典・権利・来歴 | 各主張の原資料URL、発表主体、資料公開日、事実発生日、確認日、原典箇所、証言／監査値／推定の区別、画像・図の権利と版履歴。 |
| 17. 事例固有の予定外の発見 | 発掘途中で見つかった新しい取引慣習、販売の仕掛け、人の行動、外部契約や偶然の露出等。既存分類に押し込めず保存し、読者価値が高ければ記事構成を変更。 |

優先順位は常に「その事例の売れ方を解明するため何が足りないか」。共通分類は漏れの点検器であり、何項目が埋まったかで記事合格を決めない。

### 10-3. 業態別の追加取材

- SaaS／アプリ／AI：無料・試用→課金、継続と解約、サーバーや推論コスト、配布元、初期ユーザー、顧客の乗り換え理由、創業者が担当した仕事。
- 物販／食品／D2C：企画・製造・仕入れ・最小ロット・在庫・粗利・梱包・配送・卸条件・店頭販売・再購入。卸売上と小売価格を混同しない。
- 仲介／マーケットプレイス：売り手・買い手それぞれの最初の参加者、在庫・出品・供給をどう確保したか、成立する取引、決済/手数料、どちらが先に集まったか。
- メディア／広告／ニュースレター：最初の読者をどこから得たか、配信・共有・継続読者、広告主に売るもの、契約と広告料金、媒体収入と購読料。
- 店舗／現場サービス：立地・商圏・既存客・看板/紹介・予約/見積・人件費・作業能力・仕入れ・リピート・地域や許認可の条件。
- コンテンツ／IP／教育：何を完成品として届け、誰が発見し、どのように購入・更新・紹介するか、制作工数・流通手数料・権利と継続販売。
- 高規制・金融など：資格、契約相手、実際に必要なライセンス、制約が市場参入・収益・業務に直接作用する部分。無関係な規制の羅列は避ける。
- 複合型・例外：取引を複数に分け、誰が誰に何を支払うかと収益の帰属を間違えない。

### 10-4. 調査・執筆を一体化する具体的な反復手順

1. 過去の掲載・未掲載・下書き・改訂版・Researchから企業名、公式ドメイン、サービス名、統合前後の別名を照合。重複状況を記録。
2. 複数候補を横断して、読者の新しい発見・商売の実体・初動や成長の追跡可能性・原資料の質で選ぶ。有名さ・資金調達額・記入可能なセル数で選ばない。
3. 公式商品、料金、創業者の直接発言、当時の記録、実績開示、独立取材から、何をどの立場の顧客に売るのかを解明。
4. 記事の仮タイトル・本文見出し・主要数値・読むべき順序と図表案を**ここで書く**。例：『最初の7店舗はどう獲得したか』と分かったら電話・商談・試着・注文という実行の流れを原典へ戻って追う。
5. 下書きを書き始め、各主張が「誰が／何を／どこで／どう／なぜ／どんな結果」を満たすか検査。欠けた箇所は記事を後回しにせず同じ工程で追加調査。未知の数字は作らない。
6. 行動→反応→結果を区別し、根拠のある観測と妥当な推論を明示的に分離。根拠不足なら主張を弱める・追加調査する・別候補に切り替える。因果を事後的に確定しない。
7. 必要な文章・箇条書き・工程・表・年表・SVG・実写真の参照と権利記録を最適配置。媒体は手段であり点数や枚数を固定しない。
8. 記事全体を読んで日本語を推敲。同義反復、意味不明なビジネス用語、内部免責の羅列、薄い一般論、数字の時点混同を取り除く。
9. 完成記事と研究原本に安定ID・版・出典対応を付けて非公開で保存し、Codexに渡す。読者向け文章が意味的に確定してから形式変換し、元の文章を保存・照合する。

### 10-5. 読者が見る画面の設計起点

- 最初の一覧行と詳細の大見出し：独自の行動・売り方・成果が具体的に分かる。
- リード：1〜2文程度で正体と読む理由を伝え、本文を長々繰り返さない。
- KPI：本当に判断材料になる数値だけ（PR #224のUIは最大4件）。計測時点・対象・通貨・売上/利益/取扱高の意味は正しく。
- 本文：概要→仕組み→お金→集客→運営→経緯→成功の理由。7分類は表示順の契約であり7章全件必須ではない。出典は最後に独立表示。
- 小見出し：『集客方法とは？』ではなく『百貨店の仕入れ担当へ電話し、試着で7店舗の採用を得た』のように事例固有の答えを提示。
- UI部品：facts / paragraph / steps / rates / table / timeline / list / subheading / figure を意味に応じて使用。狭い詳細欄やスマホで読みやすい形を考えながら執筆する。
- 画像：実物の理解に有用なら権利・出典が確認された実商品写真や画面、または自作SVG。許諾不明の他人の写真を取り込まない。図を必須枚数にしない。
- 空章・未確認項目・内部作業説明は読者には見せない。ただし事実を誤認させる重要な条件、販売地域、料金対象時点、企業と子会社の区別などは必要なラベルに残す。

### 10-6. 一件の納品物と根拠リンク

- 人間が普通に読める日本語の article.md が表示内容の正本。研究と出典の内容で途中から機械再生成・短縮しない。
- research-rights.json等は自由な業態差を許容しつつ、事例ID、公式ドメイン、出典ID/URL/資料公開日/取得日、根拠となる短い具体箇所、主張の種類、数値の期間/通貨/対象、記事に未表示の価値ある発見、媒体権利、未確認事項、改訂履歴を持つ。
- 出典記録は、創業者や企業の自己説明、監査済み開示、独立した報道、顧客レビュー、分析上の推論を混同しない。原資料の存在確認と真偽の独立確認も別。
- figsは元資料に存在する数値・関係・時点と一致する自作SVGを必要分だけ持ち、記事内の表示位置、代替テキスト、典拠を保持する。
- index/manifest/ZIPの整形とSHAは後工程に委譲できる。Libraryに保存した場合の旧全件保存・上書き競合・再取得照合は別の技術的合格条件とする。
- 同じ会社の別製品や別の独立した商売、別期間の追跡、同事例の加筆修正版を誤って一つに潰さず、同一性・改訂関係を明示する。

### 10-7. 独立した5つの品質ゲートと失敗時の処理

| ゲート | 合格の根拠 | 不合格・不明なら |
| --- | --- | --- |
| 編集・読者価値 | 初見で商品・支払者・販売方法・最初の客/供給・拡大を理解し、少なくとも事例固有の新しい具体情報を学べる。全文の意味審査。 | 不明部分を追加調査し本文を改稿。それでも価値がないものを完成記事と偽らない。 |
| 根拠・数値 | 重要な主張が参照した原典と一致し、期間・指標・通貨・企業範囲の誤認や根拠なき因果がない。 | 該当記述を修正・保留。重大な矛盾なら編集待ち。 |
| 調査資産 | 出典、掲載外の研究、調査日、画像候補・権利、改訂が版とともに残っている。 | 不足分を追記。独立の比較・分析に再利用可能か確認。 |
| 技術・非公開UI | 実ZIP・ハッシュ・旧原本保全・重複/改訂処理が正しく、PC/スマホで表示崩れ・原稿欠落がない実測。 | Codex側で形式/表示を修復。原稿の意味は変えない。 |
| 公開・権利 | ユーザーによる明示承認、画像の用途別権利確認、公開用データ・運用の許可。 | 非公開のまま保持。保存や技術PASSを公開許可とみなさない。 |

空欄の数、出典の本数、文字数、図の枚数、固定評価点数だけで自動合格にしない。毎時1件は制作目標であり、実際に品質合格した1件の保証ではない。編集未合格は再取材・改訂待ちで保管できるが、完成件数に混ぜない。

### 10-8. 事例と世界需要・トレンドは別の観測

成功事例から顧客の困りごと・需要を学ぶことはできるが、一社の成功を現在の世界需要の増加として断定しない。地域と期間の明確な検索・購入・発注・求人・レビュー・市場行動等の**別の継続観測**を、別途許諾・原資料・時系列・収集手段を決めた独立系統として扱う。事例研究の蓄積は機会発見への入力になり得るが、需要監視の証拠そのものではない。

### 10-9. 現時点の実証範囲

Plausible Analyticsの既存UI・記事は品質と表示の参照例。Rightmove r1は初期の取材不足で編集未合格。Who Gives A CrapとSPANXのZIPは実在の原稿資料だが、独立照合・商用権利・新編集指示による毎時連続生成品質が完全に合格した証拠ではない。2026-10-16にはSPANX個別ZIPの存在を確認できたが、当時の累積2件ZIPには反映されていなかった。品質保証、保存、受取、非公開UI、公開の完了を混同しない。
