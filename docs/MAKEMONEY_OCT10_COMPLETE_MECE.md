## 1. 目的・成功の定義（O / D）

### 1-1. MAKEMONEY運営者が達成したいこと

1. **最重要は長期にわたり大きな事業利益を得ること**。事例数、機能数、PV、生成数、GMVは手段。外部原価・決済手数料・紹介報酬・問い合わせ・法務運用まで控除した実質利益を重視する。
2. 一回限りのAI制作・Bolt紹介報酬だけで終わらず、**制作された事業が販売・継続するほどMAKEMONEYにも収益が積み上がる**構造を作りたい。
3. 事業の情報収集、AI制作、作品管理、販売、紹介、実績還流を一体化し、多数の制作者・紹介者・購入者がそれぞれ得する場にする。
4. 一人／少人数で開発・運営可能にし、**他人が作った個々のSaaSの継続保守・サーバー管理・顧客対応を背負わない**。負担が膨らむ構成は避ける。
5. 既存の実装がv0だから、という理由で技術選定しない。**完成時の製品価値・合法な商用利用・費用・責任・移管性**でゼロベースで選ぶ。

### 1-2. 利用者が受け取る価値

- 実在する成功・失敗・撤退を含む事業事例、出典付きの価格・収益構造・顧客・初動・集客・費用・成立条件・今の需要を調べられる。
- 類似事例の共通項・商売の型・現在の機会を理解し、**自分が何を作って、誰に、どう売るか**まで考えられる。
- **MAKEMONEYから通常の制作操作で離脱せず**、AIに曖昧な指示を出し、SaaS・Webサイトを生成、自然言語修正、プレビュー、公開できる。
- 完成したものは**別の独立URL**で一般客が直接利用できる。MAKEMONEYに全購入者の登録を強制しない。
- 事業が公開されれば**MAKEMONEYの商品紹介ページが自動で用意**され、別途LPを作らず自分でX・ブログ等に投稿して宣伝できる。
- 自分で制作せず、他人の商品を紹介して報酬を得る参加方法もある。
- 自分のサービスを適法に所有・運営し、将来MAKEMONEYを解約しても資産を失わない設計を目指す。

### 1-3. 既存最新要件（10/09）との整合

- ユーザー主要入口は**「事例」「機会」「作る」「市場」の4つ**。これはユーザーが必ず順番に使う意味ではない。「作りたいものを書く」から直接作っても、外部で作った商品を市場に持ち込んでもよい。
- 無料事例、PROの完成済み調査・更新、個別AI調査/制作の利用枠、無料出品/紹介参加、取引手数料という骨格は10/09文書を維持。
- 「市場」の内部に、商品販売・他人の商品の紹介・自分の記事・広告等があり、巨大SNSやM&Aを中核に戻さない。
- 最終的な競争優位は生成AIそのものではなく、**「どんな実在事業があり、何が作られ、どの商品が売れ、継続したか」**の出典付き事実と独自の行動・取引データの循環。

## 4. ユーザー体験：端から端まで（O / P）

1. 無料事例やPRO機会を調べる。あるいは直接「これを作りたい」と入力する。
2. 共通の本人プロジェクトを生成。参考事例の引用と自分のアイデア、顧客、価格案、実装機能、注意点を保持。
3. MAKEMONEYの制作画面で「作る」と指示。裏側のAI制作APIへ、必要な部分だけ送信する。
4. 進行、失敗、再試行、AI生成結果、画面プレビュー、自然言語による修正、版履歴・ソース取得をMAKEMONEY内で扱う。
5. 「公開する」を本人が選択。外部基盤の契約・料金・権利・公開範囲・ストア掲載条件を明示し、本人の確認を得る。公開は外部ホスティングが処理する。
6. 公開URLが発行され、一般客が完成SaaSを直接利用。公開後の継続運用、顧客への役務提供は制作者本人が担当。
7. MAKEMONEYに非公開下書きとして保存済みの商品情報を更新し、条件を満たす一般公開作品を自動掲載。商品URLを共有できる。
8. 本人が料金・決済を設定すれば、制作者のStripeで月額販売が可能になる。MAKEMONEY経由の正式な取引からプラットフォーム手数料を受け取る。
9. 紹介許可された商品は、別ユーザーが専用リンクや記事で宣伝し、正常に決済されれば成果に応じ報酬を得る。
10. 同意済みの利用・販売実績を需要データに還流し、次の機会発見を改善する。

### 4-1. 「完結」の正確な範囲

- **画面内を目指す**：事業検討、制作、修正、プレビュー、作品管理、公開操作、商品ページ、販売状態、紹介状態。
- **外部画面が必要になり得る**：初回のVercel等へのログイン/OAuth、公開プロジェクトのClaim/移管、Stripe本人確認・銀行登録、独自ドメインDNS、規約同意。
- **外部事業者が実処理**：AIコード生成、公開サーバー・DB運用、カード決済、入金・払い出し。
- **実証前の留保**：外部契約移管後もMAKEMONEY画面で継続編集できるかは、当該APIの認証・編集権限の確認が必要。

### 4-2. 外部で作った商品の扱い

- MAKEMONEY経由で生成したもの：外部プロジェクトIDと本人IDを最初から記録できる。
- MAKEMONEYを通さずBolt等で作った商品：MAKEMONEYへの持ち込み・出品は許可するが、本人が公開URLと必要情報を登録・認証しない限り制作履歴を追跡できない。
- **「外部ツールを問わず自動掲載」**とは、MAKEMONEYの接続対象として把握できる制作・公開を共通形式で取り込む意味。外部のすべての利用者のプロジェクトを無断で監視できるという意味ではない。

## 5. 作品の情報取得と継続追跡（O / P / U）

### 5-1. MAKEMONEYに保存したい情報

| 種類 | 最小情報 | 理由 |
|---|---|---|
| 身元 | MAKEMONEY所有者ID、権限 | 他人の作品を操作させない |
| 系譜 | 元事例・機会ID、Build Spec版、外部制作ProviderとProject ID | 作った内容と根拠、商品を結び付ける |
| 制作状況 | 作成日時、最終変更、生成/修正/失敗の状態、版 | 制作の続きから再開 |
| 実体 | 商品名、説明、カテゴリー、主要機能、スクリーンショット、ソース参照（必要時） | 商品ページ・比較・検索に使用 |
| 公開 | デプロイID、所有者の公開契約ID、独立URL、公開/停止状態、最終照合 | 実際に利用できるか判断 |
| 流通 | ストア商品ID、公開条件、掲載許諾、販売者、共有URL | 自動掲載、宣伝 |
| 商取引 | 決済元、確認済み取引、継続/解約、紹介者、手数料 | 正確な販売・報酬 |
| 権限 | OAuth許可範囲、接続・解除状態、同期時刻と取得元 | 無断追跡や誤表示の防止 |

**保存しない原則**：完成SaaSの顧客パスワード、予約内容などの業務DB、カード番号、制作者本人の公開サーバーAPI秘密鍵の平文、無関係な外部口座・売上。

### 5-2. 外部変更をどこまで知れるか

| 変更経路 | MAKEMONEYの取得可能性 |
|---|---|
| MAKEMONEY内で行った制作指示・修正 | 自社記録と返却結果を保存できる |
| 連携した制作会社上で本人が直接変更 | 当該APIが提供し、本人が継続許諾した範囲で取得可能 |
| Vercel等の本人公開環境で再デプロイ | 許可されたデプロイ情報/Webhookで状態を把握可能 |
| 完全に別サーバー・別Gitリポジトリへ移管 | その先の接続がなければ自動追跡不可 |
| 本人が連携解除 | 将来の同期を停止。過去に取得済みの情報は保持条件・削除依頼に従う |

「公開URLが生きている」と「ソースや実装機能を正確に把握している」と「SaaSが安全に動く」はそれぞれ異なる主張。商品の機能説明は生成された文章を事実として無検証で断定しない。

### 5-3. 実装原則

- 共通の作品IDをMAKEMONEYで発行し、プロバイダー固有IDとは別に保存する。
- Provider Adapterで create / revise / status / preview / source / deploy / deployments / ownership / events 等を抽象化する。**各APIが未対応の能力は実装済みと見なさず capability=unsupported**。
- 通知を受けられる場合はWebhook署名検証・冪等記録。通知がない場合は適切な間隔の状態照合＋手動同期。
- API失敗を「作品削除」「公開停止」と短絡しない。unknown / stale / permission_revoked / suspended 等を別状態で保存する。
- 他人の作品IDを書き換えたり、外部接続解除後もAPIを叩き続けたりしない。

## 6. ストア自動登録・自動掲載（O / P）

### 6-1. 意図・双方の利点

- **制作者**：AIで制作した情報から商品ページが自動生成される。自分でLPを別途用意しなくても紹介URLを発行し、X・ブログ・記事等で宣伝できる。紹介者を募集できる。
- **MAKEMONEY**：制作された商品が自然に目録へ増え、制作者の宣伝でサイトへの流入が生まれ、販売・紹介・実績データにつながる。掲載数だけを成功指標にしない。
- **購入者**：制作方法ではなく、商品機能・価格・販売者・利用条件を比較して購入できる。

### 6-2. 状態と公開権限を必ず分ける

| 作品の状態 | MAKEMONEYの状態 | 一般閲覧 |
|---|---|---|
| 制作開始・未完成 | 商品の非公開下書きを自動作成 | 不可 |
| プレビュー | 本人の確認ページに反映 | 不可 |
| 本人がアプリの一般公開を指示 | URL・機能・掲載許諾・安全の最低限を検証 | 検査前は不可 |
| 検査を通り掲載条件に同意済み | **ストア自動掲載** | 可 |
| 決済未設定 | 「公開中／購入不可」等の区別 | 商品ページのみ |
| 正式な販売が有効 | 価格・購入・紹介導線を表示 | 可 |
| SaaS停止・権限喪失・違反通報 | 販売停止、必要なら掲載保留 | 条件次第 |
| 制作者が作品情報を更新 | 出典と状態を再確認し商品ページ更新 | 可 |

- **自動「登録」と、本人の同意なしでの「一般公開」は別**。
- 「MAKEMONEY経由で一般公開した作品はストア掲載を原則とする」条件を採る場合、制作開始時と最終公開時に明確に説明する。秘匿したいものには非公開の試作導線を設ける。
- 本人が公開を選んだことをもって、ソースコード・事業・ブランドの著作権をMAKEMONEYへ譲渡したものとは扱わない。
- 必要な画像・説明文・画面の掲載利用許諾は別に取得。著作権・商標・第三者素材、スクリーンショット内の個人情報に注意。
- 未完成品、詐欺的な商品、悪質なコピー、同一商品の大量投稿を「商品数が増えた」と評価しない。機械的検査、通報・非表示、再審査を用意する。
- MAKEMONEYがそのSaaSの公式運営者や安全保証者であるかのようなバッジは付けない。

## 8. 権利・所有・契約・費用の分離（O / P / U）

「制作物の権利」「事業の運営」「公開インフラの契約」「継続売上を受け取る権利」は混同しない。

| 対象 | 推奨帰属・契約 | 備考 |
|---|---|---|
| 生成コード等に成立する権利 | 制作者本人 | 外部Provider規約、OSSライセンス、AI生成物の著作物性に従う |
| SaaSの商標/ブランド/独自ドメイン | 制作者本人 | MAKEMONEYストア表示は必要範囲の許諾のみ |
| SaaSの購入者との契約 | 制作者本人 | MAKEMONEYを販売主体と誤認させない |
| SaaSの稼働・顧客サポート | 制作者本人 | 外部公開Providerは技術設備を提供 |
| SaaSの本番ホスティング/DBの契約 | 原則制作者本人 | MAKEMONEYが全員分を契約して永続負担しない |
| MAKEMONEYのアカウント・事例・企画記録 | MAKEMONEYが必要な範囲で管理 | 個人情報・機密等の管理責任を負う |
| 制作履歴・公開URL・ストア掲載情報 | MAKEMONEYが本人同意の範囲で保持 | 制作物の著作権譲渡ではない |
| MAKEMONEY経由の売上手数料 | 契約で発生 | 著作権を取らなくても可能。対象は正式に紐付く取引 |
| MAKEMONEY外の売上連動ロイヤリティ | 将来の独立契約の候補 | 契約対象売上の把握・監査・強制回収は別課題 |

**「著作権をMAKEMONEYが持てば当然に永久収益が得られる」は誤り。** 著作権だけでは会社持分・全顧客・全取引売上を自動取得しない。
**「著作権を持てば当然にSaaSの全責任を負う」も誤り。** 責任は契約上の役割・実際の行為・原因・法令による。

## 9. 責任の境界：A／B／C を明示（O / P / U）

オーナーは**「変な責任はなるべく負いたくない。個人開発だから管理には限界がある」**と繰り返し明示。一方、MAKEMONEY自身のストア運営や自社へ入力された情報の管理は当然引き受けると整理した。

### 9-1. A：外部AI制作会社との契約責任（最大の未解決）

- MAKEMONEYがAPI契約者として、外部AIの生成・修正機能を自社の利用者へ提供する場合、**ユーザーの禁止行為や第三者請求について、API会社から契約上の責任・補償を要求され得る**。
- 例：ある利用者がフィッシング目的の画面を生成する、権利侵害コンテンツを生成する、APIキーが漏れる、禁止用途で大量に利用する。利用者本人の責任とは別に、契約条件次第でMAKEMONEYにもAPI停止、調査、請求、第三者請求の補償が問題になり得る。
- **外部AI会社のCPUで作ったからMAKEMONEYは無関係**、とは言えない。逆に**ユーザーが作った独立SaaSの全バグ・全顧客事故が当然にMAKEMONEYへ移る**、という意味でもない。
- v0 API Terms の End User 条項は具体的な警戒例。Totalumのホワイトラベル契約もAPI契約者の責任を確認する対象。
- 採用ゲート：補償の対象・上限、直接/間接損失、規約違反時の対応、事故時通知、保険、管轄、個人名義/法人名義、利用者と締結すべき下流規約、停止権限を確認。**上限のない、または個人に過大な包括補償義務を負う構成は不採用候補**。
- 安全措置：規約同意、目的外/違法利用の制限、利用量の予約と上限、行為・リクエストの監査（プライバシー最小化）、通報窓口、アカウント停止。規約で無責任にできると主張しない。

### 9-2. B：MAKEMONEYストア運営の責任（引き受ける）

- 商品の掲載・検索・表示、適切な価格・販売者情報、レビュー/売上の虚偽表示防止、広告・PR表示、権利侵害・詐欺/違法商品への通報受付、必要な修正・非表示・停止。
- 一般公開の自動掲載では、公開前の同意と機械的検査を必須とする。商品数を増やすために未完成・違法・誤認の商品を放置しない。
- ただし、**ストア運営者であることだけで全出品者のSaaSの運営主体になるわけではない**。商品自体の顧客契約・役務提供・通常のサポートは制作者。
- 取引形態によっては取引デジタルプラットフォーム消費者保護法、特定商取引法、景品表示法、情報流通関連法制の対応が必要。法適用は法務レビューで分類する。

### 9-3. C：MAKEMONEYに入力・保存された情報の責任（引き受ける）

- MAKEMONEYの会員情報、企画メモ、AIへの指示、作品・制作履歴、外部OAuth連携情報、ストア出品、紹介・取引に関する**実際に保有・処理するデータ**の安全管理・利用目的・保存・削除・漏洩対応。
- AI制作Providerへ何を送るか、学習利用の有無、外部送信先、保存期間、再委託、アクセス権限を明示。MAKEMONEYへの入力情報の**保存・送信・安全な取扱い**に責任を負うことと、ユーザーが入力した**内容自体の合法性を全部保証する**ことを分ける。
- SaaSが独立公開された後、そこで**SaaSの顧客**が登録する名前・パスワード・予約・健康情報等は、**原則として制作者とその契約DB/認証会社**の担当。MAKEMONEYがその情報を保有・処理しない構成にする。
- 例外：MAKEMONEYが全SaaS共通認証、顧客台帳、顧客情報を含むStripeイベント保存、共通のAPI/DBを運営するなら、その**取り扱った範囲についてMAKEMONEYの責任が追加**される。
- 「SaaSの顧客情報は作ったユーザーの責任」という理解は、**MAKEMONEYが直接取得・処理しない設計である限り概ね正しい**。ただし事故原因がMAKEMONEYの欠陥なら別途責任が生じ得る。

### 9-4. MAKEMONEYが引き受ける具体的業務（MECE：6分類）

### 9-5. 原則引き受けない仕事（設計上の非提供範囲）

| 事項 | 基本担当／理由 |
|---|---|
| 独立SaaSの顧客への役務提供・個別サポート | 制作者本人が販売者・運営者 |
| SaaS固有のバグ修正・仕様保証・24時間稼働保証 | 制作者と外部技術基盤。MAKEMONEYは品質保証を約束しない |

## 10. 法的リスクを実装で最小化する方法（P / U）

1. SaaSの本番ホスティング/DB/ドメインの契約は**制作者本人に帰属**させる。MAKEMONEYの一括契約を続けるなら期限/原価上限/責任の別審査を要する。
2. SaaSの販売者（Merchant of Record）と購入者に対するサービス提供者は、**原則制作者本人**とする。MAKEMONEYの表記や決済明細でも誤認させない。
3. Stripe Connectは **direct charges（販売者の連結アカウントに請求）**を第一候補にする。返金、手数料、マイナス残高の最終負担は**アカウント構成とStripe契約**を個別確認。direct chargesだけで自動免責という説明を禁止。
4. SaaSの顧客DB・認証をMAKEMONEYが共通管理しない。必要な購入権限の同期でも最小限の識別子に限定し、決済顧客情報を取得する場合は明示管理。
5. MAKEMONEYが制作機能を再提供する契約で、**エンドユーザーの行為に関する補償責任の上限と条件**を確認。外部AIに委託すれば責任が完全に消えるとは扱わない。
6. 公開前の本人確認、ストア掲載への同意、非公開プロジェクトのアクセス分離、公開後の販売者表示、違反通報・削除、実行上限を実装。
7. MAKEMONEY自身が「生成アプリはセキュリティ保証済み」「必ず稼げる」「合法性を保証」などと断定しない。
8. 自社規約で責任の範囲を合理的に規定し、免責全面条項で解決したと主張しない。日本の消費者契約法に適合させる。
9. ストア/紹介者の不正を放置しない。本人情報の取得・保存は必要最小限。事故の検知・停止・照会先を持つ。
10. **利用者が制作した独立SaaSから、MAKEMONEYの廃業時にも退避可能**な契約/コード/DB/ドメイン・決済の独立性を目標にし、完全移管が実証できないProviderを安易に採用しない。
11. 日本法の該当性（特商法、景表法、個人情報保護法、取引DPF法、情報流通関連法、資金移動/前払式支払手段、著作権等）は実際の取引・保有情報・カード/クレジット/報酬設計に応じて判定する。
12. 自社責任範囲の必要最小限のサポート窓口・ログ・利用停止・情報漏洩対応手順を設ける。責任ゼロを目指すのではなく、**利用者数に比例して他社SaaSの運営仕事が無制限に積み上がる構造を避ける**。

### 11-2. どうすればMAKEMONEYに継続収益が入るか（P）

| 方式 | 継続する条件 | 利点 | 限界 |
|---|---|---|---|

- **「MAKEMONEYで作ったから永久に売上の何％」は技術だけでは発生しない。** 著作権所有だけでも、Stripe接続だけでも、自動的な無期限徴収権は生まれない。

- 一般利用者に永久ロイヤリティを強制するより、制作費・広告費・販路・継続技術を提供する**希望制・個別の事業パートナープラン**を将来検討する。

### 11-3. 継続手数料が成立するための因果関係

制作者が自分で制作・公開した後も、MAKEMONEYに商品掲載・検索・販売、紹介者ネットワーク、決済/継続管理という便益があれば、継続して手数料を払う理由がある。

反対に、MAKEMONEYが制作だけして、購入者を生まず、更新も提供しない場合、制作者は外部直販へ移る。よって**手数料の契約を強めるだけではなく、継続して選ばれる販路を作る**ことが長期利益の条件。

## 12. Stripe・月額販売・紹介報酬の正確な境界（V / P / U）

### 12-1. 制作者が販売者になる方式（第一候補）

1. 制作者本人がStripeの連結アカウントを開設し、本人確認・銀行登録等を行う。
2. MAKEMONEYは本人確認済みの接続情報と商品・販売条件・合意済み手数料率を保存する。
3. 顧客が制作者のSaaSまたはMAKEMONEYの商品ページから購入する。
4. **販売者の連結アカウント上で direct charge**を処理し、適用できる subscription application fee をMAKEMONEYが取得する。
5. Stripeの署名済み通知を検証して、契約の成功・継続・失敗・解約・返金等を正しい売上・利用権へ反映する。
6. 制作者は顧客へ商品を提供し、返金や商品サポートに対応する。実際の費用・チャージバック・負残高等の分担は**採用アカウント構成を個別に照合**する。
7. MAKEMONEYは自身の手数料と紹介報酬について正確な台帳を管理する。

**Stripeがしてくれないこと**：誰の紹介で成約したかを自動確定する、どのAI生成機能をSaaSに実装したか判断する、完成SaaSのサブスク利用権を各アプリへ自動配備する、制作者の商材の合法性を保証する。

### 12-2. 生成SaaS内の利用権

販売するSaaSに月額課金を付ける場合、単に支払リンクを表示するだけでなく、本人認証・支払済み/未払い/解約・機能権限をつなげる必要がある。
- **できれば制作者本人が所有するSaaSのDB/認証とStripeを直接連携**させる。
- MAKEMONEYは手数料/紹介に必要な取引識別子のみ扱い、完成SaaSの全顧客DBを共有保存しない。
- 生成コードに無検証の課金部品を埋め込み「安全」とは断言しない。購入/再請求/失敗/返金/解約/再登録のE2Eが必要。
- サブスク解約後の利用権、ストア掲載状態、Stripe連携解除、MAKEMONEY退会時の挙動を定義する。

### 12-3. 紹介報酬

- 自分の商品を紹介した制作者と紹介者の混同、自己紹介、架空注文、返金による二重払いを防ぐ。
- 紹介トラッキングの有効期限・最後/最初の紹介の帰属・Cookieなしの端末切替・購入時凍結・返金時取消・継続期間は明示規則が必要。
- 10/09文書は「30日帰属」「売り手が率/期間を設定」「月次まとめ払い」を開始案として記録済み。10/10会話で上書きされたわけではない。
- 現時点では紹介者への自動送金まで本番完了したと扱わない。Stripeの送金手段が要件を満たすか、別の対応サービスが必要か確認する。
- アフィリエイト記事/SNSの広告表示、誇大な利益主張、スパム対策が必要。

## 13. 個人開発での原価・運用の上限（O / P）

- API生成の前に最大クレジット・回数・時間・並列数を表示・予約する。外部APIエラーや多重タブ/再送により限界を超えない。
- 制作途中の原価と本番公開後の費用を**別の請求主体・別の上限**とする。
- 制作者本人の本番契約が有効になるまで、高額な独立SaaSの公開を開始しない。
- 本番公開後の想定超過費用・停止条件を制作者へ明示。MAKEMONEYが「無制限ホスティング無料」と見せかけない。
- MAKEMONEYは自社の開発原価、PRO会費の変動費、無料体験の獲得原価、手数料収益、紹介費、サポート費を分けて計測する。
- 10/09の料金（初回50クレジット、PRO100、追加100=1,100円、変動費予算など）は**提案仕様**で、実原価・本番決済の承認とは区別する。
- 外部Providerの障害や変更でプレビュー・編集が停止しても、成果物や契約が消滅しないエクスポート・代替接続を設計する。

- 「MVPだから画面だけ・偽注文だけで完成」とはしない。各段階の必須ユーザー体験が実動するまで合格させない。
- 外部提供会社の条件が未解決の場合はG0で止め、他のproviderを検証する。ユーザー価値を安易に削ったり、外部Boltへの遷移を最終形だと置き換えたりしない。

## 15. 開発仕様の骨格（P：設計、未実装）

### 15-1. 既存実装との関係

- 2026-10-10に確認された main は **faa4c5e504c3ecb7fddd21039321bb407df7e400**（照合時点）。v0向けのBuilder、プレビュー、出品、テスト購入、紹介モデル、既存会費Stripeがある。

- 最新の収益・UI仕様はPR #221の10/09文書が優先。10/02以前の全画面構成を新規上書きしない。

### 15-2. 必要な論理データ（概念名。マイグレーション確定ではない）

- **Project**：MAKEMONEYの本人所有の企画・制作・公開・販売をつなぐ単一親ID。
- **BuildSpecVersion**：元事例/機会、顧客、機能、価格仮説、根拠、プロンプト/仕様版。
- **ProviderConnection**：Provider、外部アカウント、本人許可、対象scope、接続/失効状態。
- **BuildOperation**：生成・修正・プレビューの要求ID、状態、原価予約・実績、重複防止ID。
- **ExternalProject**：外部制作/公開のプロジェクトID、所属者、ソース取得可否、同期世代。
- **Deployment**：公開ID、URL、状態、本人契約、公開時の同意、停止・移管・再デプロイ。
- **Listing/Product**：作品との1対1対応、掲載条件、宣伝ページ、販売者、価格・表示状態。
- **ConnectSeller / ProductPrice**：Stripe本人契約とプラン、手数料率と適用時点。
- **Order / Subscription / Entitlement**：購入、毎月更新、返金、利用権。決済事実を正本として監査。
- **Referral / Attribution / Commission / Payout**：紹介者・帰属・計算・調整・送金。状態は互いに別。
- **FeedbackEvent**：閲覧/企画/制作/公開/掲載/販売/継続・出典と集計許諾。
- **ModerationCase**：通報・証拠・停止・異議申立て。

### 15-3. 実装で必須の境界

- Client UIはAPI秘密鍵に触れない。OAuthなどは最小権限・サーバー側管理、CSRF/state/署名検証、失効対応。
- 生成/公開/決済の要求IDを使い、再送・多重タブ・ネットワーク不通でも同じ外部操作が二重実行されない。
- 長時間生成はジョブ化し、状態を「未着手／実行中／成功／失敗／要照合」に分離する。実行成否不明なら調査し、盲目的に再送しない。
- 作った本人しか公開・外部アカウント移管・料金変更・商品出品できない。認証IDの自己申告を信じない。
- AI出力の機能説明は仮説。実際の操作テストが成功したもののみ「動作確認済み」と表示。
- 生成プレビューと一般公開の環境・認証・DBを分離。プレビューで実課金や実顧客メール送信をしない。
- 公開時の本人同意、ストア掲載の同意、Stripeを使う販売開始の同意は**別の明示的な操作**として記録する。
- Stripeの金額・時点は、MAKEMONEYの楽観表示ではなく署名検証済みイベントと照合結果で確定。返金/解約/重複通知に耐える。
- 出品者・紹介者・購入者は別のIDと権限で扱い、自己購入・自己紹介・虚偽評価・多重報酬を防ぐ。
- 品質/権利/実績データの公開ゲートと既存R2保存正本は変更しない。

## 16. 完成判定の現実的なシナリオ（P）

### S1 制作と所有

1人目が実在事例を選び、ログイン・DBを持つWebサービスをMAKEMONEY内で作成・修正できる。
2人目は1人目の非公開仕様、ソース、プレビューにアクセスできない。
公開費用と外部契約を本人が確認・取得し、独立URLとして動く。
MAKEMONEY側の解約/障害で、本人所有の独立公開アプリは原則停止しない。
ソースやDB等の移管に不足があれば、欠落を明示し合格させない。

### S2 自動掲載と追跡

公開後、許諾・検査に合格した作品の掲載ページが自動生成される。
未完成・非公開・通報中の作品は誤掲載されない。
制作者が商品ページをXに共有できる。
外部での許可済み更新は同期。連携解除後は取得せず、最終同期時点を表示。
外部での独立変更を「全自動で追跡済み」と偽らない。

### S3 制作者の月額販売

制作者のStripe本人アカウントで月額購入が成立する。
継続請求・支払失敗・解約・返金が生成SaaSの有料利用権と一致する。
MAKEMONEYの合意済み手数料が指定の取引だけに発生し、無関係な外部売上には発生しない。
二重通知や支払遅延でも二重請求・二重手数料にならない。

### S4 紹介者の月額報酬

制作者Aが商品を登録し、別ユーザーBが紹介、顧客Cが契約。
紹介者Bの成果が継続請求で正しく反映され、返金では取消が記録される。
制作者が自分の商品を自分で紹介して報酬を発生させることはできない。
送金事業者の本人確認・契約・法務要件が満たされるまで実送金しない。

### S5 安全と契約

違法/権利侵害の通報で、MAKEMONEYの表示と連携提供範囲を適切に停止できる。
API会社への補償責任・責任上限が確認済み。
全外部サービスの障害と解除時に、情報と状態が矛盾しない。
クレジット超過、他人の秘密情報露出、意図しない公開、実課金を防げる。

## 18. 明示的に採用しない誤解・案（X）

- 制作は外部、完成物は外部なのに、MAKEMONEYが全作品の本番サーバー代を永久に立替する。
- 「MAKEMONEY内で全部」とは、AIエンジン・公開設備・クレジットカード決済・顧客DBを全部自前実装するという意味。
- Boltなどの通常個人アカウントを1件契約し、不特定多数へ規約確認なしに再販売する。
- Boltで作った全プロジェクトにMAKEMONEYが無断でアクセス・追跡できると思う。
- 公開URLが独立しているだけで契約・請求・顧客DBも完全独立済みだと判断する。
- Stripeを接続するだけで、紹介者・プラットフォーム・制作者への3分配や購入者へのSaaS利用権がすべて自動で完成すると思う。
- MAKEMONEYが著作権を持てばあらゆる売上のロイヤリティを自動徴収できると思う。
- 制作者に責任を負わせる条文だけで、自社のAI API契約・個人情報・ストア・決済連携の責任がすべて消えると考える。
- 完成していない非公開作品を、本人の同意なくストアで一般公開する。
- AIが作った内容や事例を成功実績・安全保証・権利確認済みと無根拠に表示する。
- 顧客を買う前に、MAKEMONEYで作ったすべてのSaaSに遡って無期限売上分配を強制する。
- 10/09のPRO価格・手数料10%・4入口・既存事例UIを、10/10の説明用例で無断変更する。
- ユーザーの明示的な承認なしに、実決済・実送金・対外公開・外部契約・デプロイ・R2/収集タスク変更を実行する。

## 22. この保存によって「決まったこと」と「決まっていないこと」

**明確になったユーザー意図**：
- 事例・企画・AI制作・独立公開・ストア自動掲載・販売・紹介をMAKEMONEY内の一貫した体験にする。
- 制作/公開/決済の難しい実処理は外部会社に任せ、MAKEMONEYは指示・管理・流通の基盤を所有する。
- 制作者は自分のSaaS・事業・公開契約を持ち、MAKEMONEYは作品情報を適正に把握・掲載する。
- 自動商品蓄積と制作者自身の宣伝、紹介者の活動によって取引を増やし、運営者が継続収益を得る。
- ストア・MAKEMONEYの入力情報に対する自社責任は受容。ただし他人のSaaS固有の顧客情報・サーバー・バグ・顧客対応を無制限に抱えない。
- 将来は制作ロイヤリティ/事業分配契約も検討。ただしMVPで永久徴収は必須ではない。

**実装・契約として未確定**：
- 具体的なAI制作Providerと利用契約、再販売権、補償責任の上限。
- 制作者本人への公開契約・DB・認証/ドメインの引継ぎと継続編集。
- MAKEMONEY外での制作・売上・変更内容の取得範囲。
- 自動掲載の最終同意文言と例外・表示ガード。
- Stripe Connectの具体アカウント条件と手数料負担、紹介者の支払実務。
- 将来のロイヤリティ契約・対象範囲・上限/期間・監査と法的有効性。
- MVP各フェーズの実際の原価、実利用と成約需要、サポート工数、E2E結果。

**最終一文**：MAKEMONEYは「ユーザーのSaaSをすべて保有・運営する会社」ではなく、**事業を見つけて作り、作品情報を蓄積・流通させ、本人の販売・紹介・継続取引から適正な対価を得る場所**になる。その操作体験を自社に統合し、技術実行と本番事業運営を適切に外部・本人へ分担する。
