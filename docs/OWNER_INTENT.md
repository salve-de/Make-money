# Make-Money 正本 — 何を・なぜ・どう・どこまで（最初に読む1本）

最終更新: 2026-10-03（収集の10情報領域・文章品質。画像の優先順位は2026-10-02決定を継続）。
この文書は Make-Money の**唯一の入口**です。オーナー（ユーザー）が会話で伝えてきたことを1本にまとめています。何を作るか、なぜか、何を集め、どう集め、どこに貯め、どう見せ、何を守り、どうなれば完成か、を書きます。
オーナーは長い指示を書きません。AI・作業者は、これを読んでから動いてください。

**優先順位**
1. この文書
2. 土台（Universal Foundation）の正本（事実と証拠の残し方に限る。16章）
3. その他の文書

他の文書とこの文書が食い違ったら、この文書が勝ちます。食い違う古い規則の一覧と置き換え先は17章にあります。
オーナーの訂正が入ったら、その場でこの文書と台帳（`~/.claude/intent/projects/Make-Money.md`）に書き足します（15章）。

## 1. なぜ作るのか
- 作るのは、読者が「これを見ずに動くのは損だ（自殺行為だ）」と思って金を払う、**資本主義の裏帳簿**です。誰が・誰から・何の恐怖や面倒を消して・どれだけ楽に・いくら抜いているかを、1画面で掴ませます。
- 読者は、これから稼ぎたい個人、経営者、投資家です。欲しいのは会計の正確さではありません。**金の抜き方の構造と規模感、それに1秒で刺さる強い一行**です。
- **勝ち**: 1件開くと、何を誰にどう売り、何が実際に起き、いくら売れ、どう運営し、自分が何を応用できるかを、根拠に応じて具体的に理解できることです。出典と推論の根拠を追える状態に保ち、文章の読みやすさと事例固有の中身を重視します。確度ラベルや未確認表示を機械的に並べて完成記事にしません。
- **負け**: 中身の薄い一般論、作った物語、数字の意味を取り違える説明、同じ文の水増しです。足りない材料は必要に応じて追加調査しますが、空欄率や見栄えのために埋めません。材料のない任意本文・節は表示せず、調査状態は記録に残します。
- 集めたデータは Make-Money だけの物ではありません。共通の土台に入れて、Investrader・Idea Spark・GOLDMINE・将来の事業でも集め直さずに使い回します（16章）。

## 2. 何を集めるか（10情報領域と、上限のない補助目録）

### 2-1. 今後の基本となる10情報領域（2026-10-03決定）

事業の理解と他事例への応用に必要な材料を、次の10領域で整理します。**収集の上限でも、全件必須の10章構成でもありません。** 既存の収集対象を削らず、業種・規模・形態に合う有用な情報を柔軟に追加します。収集範囲・調査済みかどうかと、本文に何を表示するかを分けます。

| 領域 | 集める具体的な材料 |
|---|---|

| 2. 商品と売り方 | 何をどう提供するか、利用者と支払者の違い、購入・納品方法、確認できた料金、課金単位・契約条件とその変遷。 |
| 3. 売れた実績 | 売上、販売数、有料顧客数など。期間・時点・対象範囲・定義・原通貨・単位・由来を保ち、売上、MRR、ARR、GMVや無料利用者を混同しない。 |
| 4. 利益と費用 | 原価、手数料、人件費・外注費、広告、インフラ・API・道具、その他の費用と、確認できた利益。費用の把握範囲と未確認部分も残す。全費用が不明なら、一部費用を引いた残額を利益・個人手残りと断定しない。 |
| 5. 最初の需要と購入の実経緯 | 需要をどう見つけ、誰が何を試し、最初の購入へどうつながったか。実際の行動・順序・結果を集める。最初の客や動機・突破の物語を創作しない。 |
| 6. その後の集客と購入・継続 | 認知、流入、問い合わせ、購入、継続、再購入、紹介、解約の経路と変化。初動と現在を分け、効果を裏付ける数字や観測も集める。 |
| 7. 日常運営 | 仕入れ・制作・提供・納品・サポート等の工程、担当人数、所要時間、頻度、外注、自動化、道具、実際の負担とボトルネック。 |

| 9. 転機・失敗・外部条件・依存リスク | 成長・停滞・失敗・ピボット、競合や大手の制約、時代・市場・規制・プラットフォームの変化、供給者・API・集客先等への依存と停止条件。 |
| 10. 根拠ある応用行動と条件 | 読者が何を試せるか、その根拠となる行動・結果、必要資源、成立条件、向かない条件と限界。事例の事実と分析者の提案を分け、成功保証や一般論で埋めない。 |

- **表示で選ぶことと、収集項目を絞ることを混同しません。** 従来の全scopeと10領域以外の有用情報も、可能な限り幅広く集めて保持します。既存資料に見つかった関連情報は、今の本文に不要でも捨てません。
- 会社の身元、創業者、場所、技術、競合、価格履歴、前金、紹介、過去の失敗、周辺生態系など、従来の対象はそのまま維持します。画像は7章、出典・権利・不確実性は3・6・8・16章の横断要件です。
- 10領域・12領域・46次元・91細目はそれぞれ整理・確認のための見方です。「型にないから集めない」「全て揃わなければ保存しない」「全件に10章を作る」には使いません。
- 材料が取れた領域を具体的に書きます。取れていない領域を、推測というラベルだけで埋めることはしません。根拠のある推論は3章に従って使えます。

## 3. 事実と推論
**種類は5つ**で、内部記録と出典詳細で区別できるようにします。読み物の本文に「本人申告」「対象月未確認」等を機械的に連発しません。誤認を招く断定は避け、根拠の弱い数値を見出しや訴求の中心に使いません。

| 種類 | 意味 | データ上の印 |
|---|---|---|
| 事実 | 公式サイト・届出・上場資料・取引所の掲載どおり | attribution / origin = OFFICIAL・FILING・LISTING・FILED |
| 本人申告 | 本人が公表した数字や発言。本人が言っているなら採用してよい | SELF_REPORTED |
| 第三者推計 | 記事や他社の推計。本人の数字として扱わない | ARTICLE・THIRD_PARTY |
| 推定 | 数字の推論。式・入力・前提・費用の把握範囲を付ける（例: 売上 − 確認済み費用 = その範囲での残額。未把握費用があれば利益・手残りと呼ばない） | `analysis` の formula あり、または metric origin = ESTIMATED |
| 推測 | 言葉の推論（客の痛み、大手が来ない理由など） | `analysis`（basis に拠った事実の id、confidence） |

- **根拠のある推論は使えますが、穴埋めは目的にしません。** 根拠の事実ID（basis）、前提、確度を付け、数字の推定は式・入力・適用時点と範囲も残します。業界相場や公開料金を使う場合も、出典と対象国・期間・プラン等への適用を確かめます。業界平均の粗利率や現在の手数料を、その会社の過去の実績に機械的に当てません。
- **禁止**: 推論を事実や本人発言に見せること、存在しない出典、未確認料金の仮置き、創作した初客・行動・動機・物語、根拠のない一般論による穴埋め。「推測」と書いても許されません。
- 費用の一部しか分からない場合は「確認できた費用を差し引いた残額」等、その計算の範囲を示します。粗利・営業利益・純利益・事業の現金残・個人手取りを区別し、全費用や控除が未確認のまま利益・手残りを断定しません。
- 調べれば公開の事実があるもの（創業年・料金・本人が公表した売上）は、推測で埋める前に一次情報を取りに行きます。
- 事実の欄は、事実が無ければ空のまま残します。0円や仮の人数を事実の欄に入れません。推論は別の欄（`analysis`）に置き、出典詳細で種類・根拠を示します。本文で必要な推論を使う際も事実と誤認させない表現にし、同じラベルを連発して読みづらくしません。これは土台の「不明は不明のまま」と矛盾しません（16章）。
- 手残りの推定は「事業の手残りの推定」であって、個人の所得ではありません。本人が公表していない限り、個人の実額は「不明」です（土台の規則と同じ）。

### 状態を混同しない
- **不明・未確認（unknown / UNVERIFIED）**: 根拠がまだ足りない状態。調べて取れなかった場合の `attempted_unavailable` と、未調査の `not_attempted` も分けて残します。
- **非公開**: 当事者の明示など、公開していないと実際に判断できた場合だけ使います。検索で見つからなかっただけでは「非公開」にしません。
- **該当なし（not_applicable）**: その事例には当てはまらないことと理由を記録します。
- **0**: 出典がゼロと示す値です。不明・非公開・該当なしの代用にはしません。
- 状態は既存のschemaで表し、足りない説明は既存のobservations / Journalへ残します。新しいenumや真実スキーマを勝手に作りません。

### 3-1. 強い一行（HEADLINE）の基準
- 誰に何を売り、何がこの事例の特徴かが自然に伝わる短い文にします。55字等の固定文字数に、数字・由来・時点・限定をすべて押し込まず、読みやすさを優先します。根拠のない強さや煽りを足しません。
- 手本:
  - 「工場のラインが止まる恐怖を消して5億（キーエンス）」
  - 「構築10日、あとは週1時間の保守。面倒な管理は絶対にしない男の戦略」
  - 「大手が改悪した夜、怒った常連を拾って年会費を取り、社員ゼロのまま11年間、年約$20万を抜き続けた1人のブックマーク屋（Pinboard）」
- 数字は根拠と意味が十分に確認できるものだけ見出しに使います。根拠の弱い数値や「対象月未確認」等の断りがないと成立しない数字を見出しに据えません。十分な数字がなくても、具体的な商品・行動・結果から読みたいと思える一行にします。事実に無い日数・年齢・人数・経歴は作らず、発言の形にもしません。
- 由来・時点・定義・確度は内部記録と出典詳細に保ちます。本文は確認できた具体的な中身を中心にし、「未確認」「本人申告」等を一律の定型句として繰り返しません。数字を出す場合に意味を変える重要限定（期間、累計か月次か、費用範囲、推計であることなど）は、その数字に近い自然な文で示すか、主画面への掲載を見送ります。由来を隠して断定する解決はしません。
- 後から事実と食い違ったら作り直します。

### 3-2. 経緯の文章（STORYは任意）
実際に確認できた需要・行動・購入・結果の経緯を自然につなぎます。「前夜→隙→突破→金が回る仕組み」は、各段を支える材料がある場合の構成例です。4段・400文字を埋めるために創作しません。
- 前夜 = 創業者は何者で、何に苛立っていたか。
- 隙 = どんな市場の歪み、放置された不満、価格の穴を見つけたか。
- 突破 = 最初に金が動いた行動。
- 金が回る仕組み = なぜ続くか、何が危ういか。
（土台の MAKE_MONEY_RESEARCH_REQUIREMENTS §5 は構成の参考。素材がない段・任意本文は非表示にします。）

### 3-3. 書き方
- 文系の経営者が1秒で分かる言葉で書きます。コンサル用語・横文字の熟語は使いません。
- 抽象的な一般論（「〜が重要」）は価値がありません。どの会社にも当てはまる文なら書き直します。
- 作業経過の羅列や「本文では」等の編集メモは読者向け本文に出しません。出典リンク、数値の由来、時点、重要な不確実性は隠しません。
- 具体的な主体・行動・結果・条件を優先し、同じ説明を複数の節で繰り返しません。会社に固有の材料がない任意本文は表示しません。

## 4. 厳密さはどこまで要るか（公開の合格基準）
- **数字は読みやすく丸めてよい。** 根拠がある値を「約」「幅」で示せます。ただし単位・通貨・期間・定義・由来を変えず、未確認の料金や費用を仮置きしません。
- 厳しくするのは2つだけです。
  1. 事実のふりをした嘘
  2. 出してはいけない物（権利・違法指南・事業と関係ない個人情報）

  言い換えや丸めは咎めません。
- **公開の合格基準**（抜き取り監査で測る）:
  - 具体的な商品・料金・施策・経緯・運営・結果等から、何が起きたかを理解でき、読む価値があること。全部が揃う必要はありませんが、未確認表示を並べただけの薄い事例は掲載の完成形にしません。
  - 主要な説明が事例固有の根拠に支えられ、10領域の材料・調査状態と残る不足を把握していること。全領域の本文表示や空欄率5%未満を合格条件にしません。
  - 事実・本人申告・第三者推計・推定・推測が区別され、捏造・事実の偽装・根拠のない穴埋めがないこと。
  - 出してはいけない物が 0 件。
  - 推論の水準が手本（[`data/samples/pinboard.stamped.json`](../data/samples/pinboard.stamped.json)）と並べて同等。
- 経緯: 2026-09-29〜30 に「出典どおり95%」を目指して監査を14回回しました。その結果、推論まで作文として消して、画面が空になりました。正確さの検査を守ることが目的になっていました。この失敗を繰り返しません。95% は公開の条件ではありません。事実の欄の照合の目安です。

## 5. どう集めるか
### 5-1. 探し先
**実料金・具体的な施策・購入の実経緯・運営・結果・製品画面等が取れる、情報の豊富な事例とsourceを優先します。** 薄い素材から定型記事を量産せず、材料のあるものを深掘りします。一次情報を優先しますが、一次情報だけに絞りません。探し先は次の9つです。
1. 公式（サイト・料金表・規約・更新履歴・届出）
2. 本人の発信（ブログ・インタビュー・ポッドキャスト・X）
3. 過去の魚拓（Wayback などの公開アーカイブ）
4. 報道・専門メディア
5. マーケット（Product Hunt・App Store・比較サイト）
6. 客の声（レビュー・Reddit・HN・フォーラムの不満）
7. 流入・技術・求人・提携の公開シグナル（推計は推計として）
8. 失敗・閉鎖・売却の記録
9. 出典不明の手がかり（未確認として残す）

### 5-2. 2段で取る
- 第1波: 保存済みの出典・事実・時点・権利と今回の不足を確認し、使える素材を再利用します。完全新規の収集、既存事例のバックフィル、既存素材の活用を柔軟に選び、10領域と従来の全目録から可能な限り有用な情報を持ち帰ります。必要な不足を重点に調べることは、収集対象をそこだけに限定する意味ではありません。出典や期間が異なる新しい事実は、既存の記録を消さず追加します。
- 第2波: 次の3つを掘ります。
  - 創業者が後から消した初期の姿（公開アーカイブ）
  - 宣伝に埋もれた本音の不満
  - 自称ではない本当の集客経路

どちらも合法な公開情報だけを使います。403・CAPTCHA・ログイン・有料の壁は越えません。LinkedIn は使いません。

### 5-3. 実際の流れ（コマンド）
0. **既存素材を照合する**: 保存済みsource / evidence / facts / observationsを先に読み、再利用できる内容と必要な追加調査を分けます。全文・画像の再取得も権利と取得条件に従います。
1. **必要な出典の本文を取る**: `scripts/reader-case/fetch-sources.ts`。`data/source-cache/` に入ります。
2. **事実を出典と照合する**: `build-verify-batches.ts` → `run-verify.sh`（Codex）→ `merge-verdicts.ts` の順です。結果は `data/reader-verdicts.json` に入ります。
3. **根拠のある分析を作る**: `build-analyze-batches.ts` → `run-analyze.sh`（Codex、指示文は `scripts/reader-case/analyze-prompt.md`）→ `merge-analysis.ts` の順です。結果は `data/reader-analysis.json` に入り、機械で落とした分は `data/analyze/dropped.json` に残ります。全項目を埋めるためには実行せず、材料のない任意本文は出しません。
   機械で落とす条件:
   - 根拠の id が無い
   - 発言の捏造
   - 作業の言葉
   - 式の無い数字
   - 事実と矛盾する
   - 事実がある項目の上書き
   - 違法指南
4. **公開版を作る**: `pnpm catalog:prepare`。`data/catalog-release.json` と、事例ごとの表示印 `data/case-display.json` ができます。
5. **抜き取り監査**: 4章の基準で、画面に出る主張を出典と並べて読みます。検査スクリプトの合格は、正しさの証拠になりません。
6. **R2 に公開して本番に出す**: `pnpm catalog:publish` で R2 に入れます。本番の画面は `pnpm deploy:workers` で変わります。
7. **本番の画面で確かめる**（12章）。

- 1件ごとに、調査・保存・読み戻し・画面確認を同じ件で最後まで通します。途中の工程の成功で進捗を報告しません。

## 6. 出してよいか（権利と法）
- 事実そのもの（数字・出来事）は、著作権で守られません。自分の言葉で書けば商用で出せます。記事の文章・構成は写しません。
- **eBiz Facts（ebizfacts.com）は、利用規約で素材の商用利用・公の表示を禁じています**（2026-09-30 確認。準拠法ワイオミング州）。
  - 事例を見つける手がかりにだけ使い、数字・出来事は本人・公式の一次情報に付け替えます。
  - 付け替えるまで、eBiz しか出典の無い事例は画面に出しません（HOLD_RESOURCE）。
  - 権利3層の表で eBiz を「事実のみ可」に置く旧記述は、これで置き換えます。
- 違法・規約違反・グレーな手口のやり方は、推奨・手順化しません（自作自演・スパム・規約の抜け方・不正な取得・送りつけ営業のテンプレート）。その会社が実際にやったことを事実として述べるのは可です。
- 実在の人・会社について、事実に無い違法の疑いを推測で書きません。
- 誰の発言か出典で食い違う言葉は、本人の言葉として引きません（例: Pinboard の「パンツ一丁で…」）。
- 事業と関係ない個人情報（私生活・住所・家族）は書きません。

## 7. 画像
- 画像も収集対象です。実製品の画面、利用場面、出来上がる物・出力例を優先して探します。favicon・ロゴだけで製品画像の収集要件を完了にしません。見つからない・取得できない・権利上出せない場合は理由を残し、架空画像や関係ない画像で埋めません。
- **取得できること、保存してよいこと、商用表示してよいことは別です。** 既存の提供元条件、収集制限、画像台帳、保留・禁止・許可判定、保存承認と公開ゲートを保持します。画像が必要という方針だけで、保留や禁止を許可に変えたり、無条件の転載許可を作ったりしません。
- **一番大事なのは「実際に使うときの画面」**（2026-10-02 オーナー決定）。管理画面・作業中の画面・出来上がる物など、その製品で何ができるかが一目で分かる画像を最優先で取ります。ロゴと飾り背景だけの宣伝バナーは、事例の理解に役立たないので画面に出しません。
- **取る物（上ほど優先）**:
  1. App Store のストアの画面写真（運営会社が載せた実際の画面。最大3枚）
  2. 公式サイトのトップ・機能紹介・使い方・ドキュメントに載っている製品の画面写真
  3. App Store のアイコンと、公式サイトのアイコン（favicon）。一覧の小さな印に使う
  4. OG画像は出さない（自動判定は一律 `blocked`、理由 `promo_banner_no_product`。実際の画面は 2. の取得で別に集める）。ロゴ・飾り・文字だけのバナーは出さない
- ログインした後の画面を自分で撮ることはしません（ログイン禁止）。公開されている画面写真から取ります。
- **出し方**: 小さく出し、元のページへリンクし、出典を記録します。削除依頼に応じます。
- **やらないこと**:
  - 拡大・ダウンロード・ギャラリー・大きな見出し画像にしない（土台の MEDIA_THUMBNAIL_AND_LIKENESS_POLICY と同じ線）。
  - 人物写真は使わない。
  - 出所の分からない Web 画像は取らない。
- 細則と台帳: [`MEDIA_ASSETS_AND_PROVENANCE.md`](./MEDIA_ASSETS_AND_PROVENANCE.md)。取得スクリプトは `scripts/media/`（公式サイト・App Store・自動審査・R2 への投入）です。

## 8. スタンプ（全部に印を押して保存する）
- **項目ごと**: 種類（3章の5つ）、根拠（basis・formula）、出典（どこから持ってきたか）、対象期間・観測時点、画面に出してよいか、を押します。
- **保存する粒度**: 長い詳細文だけを唯一の保存物にせず、一つの事実・行動・結果ごとに切り出します。主体、何をしたか・何が起きたか、対象、source / evidence ID・URLと該当箇所、出来事の時点・適用期間、資料の発行日、取得日、事実/本人申告/第三者推計/推定/推測の種類を、判明した範囲で結び付けます。分からない日時は創作しません。行動と結果の対応を残し、因果が未確認なら断定しません。
- 既存のEntity / Claim / Metric / MoneySignal / Event / Relationship / observations / Journalを使い、検索・比較・共通パターンの分析・応用提案・別プロジェクトにも再利用できるようにします。10領域のための新しい保存方式は作りません。詳細文・見出し・物語は元の記録から作り直せる派生物です。
- **事例ごと**: 画面に出すか、出さないならその理由を `data/case-display.json` に押します（公開版を作る時に自動で作られます）。

| 印 | 意味 |
|---|---|
| SHOW | 出典と照合した事実がある → 出す |
| HOLD_UNVERIFIED | 出典と照合できた事実が無い（出典が開けない・消えた・未照合）→ 一次情報を探し直す |
| HOLD_THIN | 事実2件以下で数字なし → 一次情報を探し直す |
| HOLD_RESOURCE | 出典が eBiz Facts だけ → 一次情報に付け替えるまで出さない |
| HOLD_SCHEMA | 形式の検査を通らない → 直す |
| HOLD_NO_RAW | 元の記録が無い → 収集からやり直す |

- 手本: [`data/samples/pinboard.stamped.json`](../data/samples/pinboard.stamped.json)。オーナーが「最高」と評価した水準です。

## 9. 薄い事例・難しい事例
- 事例数のために全件を無条件で掲載しません。具体性と読む価値を掲載条件にし、情報が薄ければ追加調査へ戻します。実料金、具体的施策、需要から購入までの実経緯、運営、製品画面等を取れるsourceや別の情報豊富な事例を優先します。
- 数字が無い、出典が消えた、事実が少ない、という事例は、まず一次情報と既存のsourceを探し直します。全項目が揃わなくても、十分に具体的で有用な事例は扱えます。
- 見つからなければ捨てません。保存したまま「データが少ないので画面に出さない」と印を付けて保管し、後の収集で埋まれば出します。
  - これは「集めない（足切り）」ではありません。「集めて保存し、画面に出さない」です。
- 第三者の推計しか無い場合も、根拠・定義・期間を確認して出典詳細に種類を残します。種類のラベルを付けるだけで薄い記事を合格にせず、根拠の弱い数字を見出しに使いません。
- 不明・非公開等は内部の調査状態として保ちます。「数値がなければ未確認を主画面へ常設する」という固定仕様にはしません。原本の保持と、読者に見せる部分の選別は別です。

## 11. どう見せるか（データ側の約束）
- 画面の実装は UI 担当の会話がやります。データの会話は画面を触りません。
- 画面の文字は次の3つからだけ作ります。作業メモ・判定規則は画面に届きません（`src/shared/reader-case.ts`）。
  - `entity.reader` の facts（出典つきの事実）
  - metrics（数字をコードが書式化したもの）
  - analysis（根拠ある推論。種類・根拠は出典詳細で追え、本文でも事実と誤認させない）
- 1件の画面では、10領域と追加の有用情報から、その事例を理解するのに必要な材料を読みやすく見せます。10章固定、全項目・4段物語の強制表示はしません。素材のない任意本文は隠し、数値そばの重要限定と詳細根拠への導線を残します。画像は7章の基準で扱います。

## 12. 完成の測り方（終点）
完成は「R2 に入り、本番の画面に出たか」で測ります。途中の工程の成功では測りません。
1. **R2**: 公開版（catalog release）の最新が R2 にあり、ローカルの `data/catalog-release.json` とハッシュが一致すること。測り方は `~/.claude/intent/projects/Make-Money.check`（R2 とローカルの件数・ハッシュの比較）です。
2. **中身**: 抜き取り監査が4章の基準を満たすこと。空欄率や章数でなく、根拠・具体性・数字の意味・文章の読みやすさ・不確実性の扱いを確かめること。
3. **本番の画面**: 本番で実在の事例を1件以上開き、次の4つを目で確かめること。
   - 強い一行
   - 具体的な事実が読みやすく、事実と推論の違い・出典・時点を詳細で追える。未確認ラベルを並べた薄い記事になっていない
   - 実製品画面等の画像を7章に従って確認した。faviconだけを完了扱いせず、表示できない場合は理由を記録した
   - 作業の言葉が見えない
4. **報告**: 「マージ」「デプロイ」「R2 のデータ」を分けて書きます。main へのマージと本番反映は別です。本番は `pnpm deploy:workers` で変わり、画面の中身は R2 の公開版で決まります。

## 16. 土台（Universal Foundation）との関係
集めたデータは、共通の土台 [salve-de/universal-foundation](https://github.com/salve-de/universal-foundation) に入れて、他の事業でも使い回します。土台の正本は次の3つです。
- **北極星**（`docs/NORTH_STAR.md`）: 「広く取る。証拠をそのまま残す。事実は控えめに組む。変化を時系列で追う。深掘りは価値のある物だけ。事業ごとの見せ方は最後に作る」。狙いは、新しい事業を思いついた時に集め直さずに済むことです。
- **何を集めるか**（`docs/MAKE_MONEY_COLLECTION_SCOPE.md`）: 12の領域と9つの探し先（5-1）です。「見つかった／探したが無かった／探していない／該当しない／不明」を区別して記録します。
- **Make-Money の物語の決まり**（`docs/MAKE_MONEY_RESEARCH_REQUIREMENTS.md`）: 強い一行・4段の物語・客の心理・堀は、根拠と材料がある場合の派生表現として残します。今回の10領域は全件に同じ文章構成を強制しません。事実を先に確かめ、推論に印を付け、後から作り直せる形にします。

この文書と土台の分け方:
- **土台に入れる物（長く残す）**: 出典、取得日時、出典の本文（権利上許される時だけ）、事実・数字・出来事、食い違い、未確認。
- **作り直せる物（事業ごとの見せ方）**: 強い一行、4段の物語、推論の各項目、手残りの推定、今も通用するか。モデルが良くなった時や事実が増えた時に作り直します。
- **画面の決定はこの文書が優先**: 土台は「出典なしの手がかりも表示してよい」としています。Make-Money の画面では「データが少ない事例は保存したまま出さない」とします（9章）。

土台の決まりに届いていない所（13章の「その後」で埋める）:
- 出典の本文（`data/source-cache`）が、土台の証拠置き場に入っていない。
- 推論と表示の印が、土台の派生データとして入っていない。
- 12領域×9探し先の記録が無い。
