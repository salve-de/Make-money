# MAKEMONEY｜読者価値を優先する編集・表現・検査基準

2026-10-12。オーナーの「情報そのものではなく、利用者に理解させる」「見出しだけで結論を伝えろ」「短くしても情報は削るな」「これをすべての事例・機能へ適用」という要求を実装へ伝える仕様案。現行GitHub mainへの変更許可・本番公開承認ではない。

## 編集の根本原則

- 画面を組む前に、対象読者が**何を知りたいか**を確定する。収集項目やデータベースの順番を、そのまま画面の構成にはしない。
- 原典から主体・買い手・支払者・商品・提供工程・お金・集客の行動・結果・時点を再構成する。原典が示さない因果は推測だと内部で区別し、勝因と断定しない。
- 大分類「概要／仕組み／お金／集客／運営／経緯／出典」は**目次だけの安定した共通ラベル**。本文の小見出しはその事例に固有の**答えを一文で言い切る**。「無料版と有料版の違い」のような問いや「無料サービスが広がる仕組み」のような同義反復を避ける。
- 本文は自然な日本語で短く具体的に。情報の核を削らず、具体的な顧客、初期資源、実作業、費用、取引条件、失敗や競合、根拠を省略しない。薄い素材は再収集する。
- 出典や未確認状態、原典取得日時は内部正本で追跡する。読者には**数値の種類・期間・対象・重要な契約条件**を明確にし、言い訳や記録メタデータの文章を羅列しない。
- 収集担当が根拠を理解しつつ自然な原稿を作る。保存・表示時に無断で要約し直さず、修正が必要ならrevision・理由・根拠参照を保存する。

## 表現の選び方

| 読者に分からせたいこと | 適した表現 |
|---|---|
| 一つの核心 | 答え型の小見出し＋必要な短文 |
| 異なる複数の事実 | 箇条書き。ただし重複を繰り返さない |
| 実際の順序 | 番号付き工程。主体・入力・出力・結果を記述 |
| 人の移動・紹介・お金・データの流れ | 矢印付きの精密な関係図。単なる3カードに情報を削らない |
| 料金・対象・契約の比較 | 比較可能な範囲の表。スマホでは縦積み |
| 出来事の変化 | 実際の日付の年表・前後比較 |
| 同定義の数値の変化 | 単位・期間・母集団が揃い、十分な点のあるグラフ |
| 商品のイメージ | 許諾・権利を確認した実写真・実画面。生成イメージを事実扱いしない |

常に図を描く／全事例同じ数の表を作るという意味ではない。図表の有無・精密さ・表現方法は事例の情報によって決める。

## UIと拡張

- 既存のPC一覧＋右520px詳細、スマホ一覧→全画面詳細を保護。
- 詳細の目次は記事上部に固定**1行で全有効大分類を同時表示**し、クリックで該当章へ移動、読んでいる章をスクロール連動で強調。見出しやスクロール位置が隠れないようにする。
- 大分類に入る具体的な小見出し数・文章・図表・実画像は事例ごとに可変。空の分類を出さない。分類に入りきらない重要な発見は根拠付きで保持し、後で分類のバージョン改訂を判断する。
- 事例の上限を表示分類の数で制限しない。事例IDと詳細取得、検索・索引・キャッシュ・データ更新・権利撤回・1万〜1億件の性能は別の技術的検証が必要。

## 検証すべき失敗

1. 「何を提供し、誰が払う？」と見出しが問いだけになっている。
2. 大分類と小見出しが同じ話を二度言う。さらに本文と図解も同じ結論を繰り返す。
3. “無料vs有料” の機能差だけで、どこから収益を得るか説明していない。
4. 縦長の図を短くするために重要な矢印・役割・条件を削除する。
5. GMV・売上・MRR・累計額・利益・顧客数の種類や対象期間を混ぜる。
6. 事例の初期集客や運営上の仕事、前から持っていた顧客・資金・技能を捨て、簡単に再現できるかのように書く。
7. 元の原稿と根拠が、変換・再生成・公開の段階で食い違う。
8. 未確認/権利不明の画像や数値を、完成記事に紛れ込ませる。

機械検査は空章・結論なし・未接続の根拠・文字はみ出し等の明白な失敗を担当する。意味の正しさ、説得力、因果の過剰主張、読者の理解は、元情報との照合と独立した人間/AIの編集監査が必要。
