## 4. 原稿と図解を決める手順

1. **事業理解**：収集した素材を読み、商流・需要・製品・顧客獲得・運営・重要な転機を全体で把握する。
2. **編集計画**：主役と重要補足を選ぶ。各事実・数字に「最も適した章」を割り当て、章をまたぐ重複を計画段階で除く。価値ある未掲載材料は消去せず研究データ側に残す。
3. **追加調査**：重要な流れが説明できない、肝心の期間が曖昧、事例特有の工夫が分からない時は関連出典を再調査する。単に任意項目が空という理由では調査を無限に延ばさない。
4. **原稿化**：見出しだけ追っても何をしている事業か分かり、本文を読むと具体的な行動と結果が分かる文章にする。**重要度による文字の強弱**を与える。大人が読んで自然な日本語を使う。
5. **表示方法選択**：数字が一点なら主要数値、同単位・同定義の推移ならグラフ、参加者や支払経路なら商流図、商品なら実画像、順序ならステップ、変化なら前後比較、出来事なら年表。**図を作ること自体をノルマにしない**。
6. **視覚素材の準備**：グラフは確認済みの構造化数値から共通描画部品で作る。関係図は確認済みの主体・矢印・説明から描く。実写真・実画面は権利・出典・利用条件を確認し、許可なしの転載や架空の製品画像をしない。
7. **独立レビュー**：執筆者と別の担当が「初見の読者」として検査する。重要度、重複、意味不明の専門用語、数字の誤認、図の誤解、スマホでの可読性を調べ、必要なら前工程に戻す。
8. **公開判断**：事実・権利・文章・表示の各検査を通った原稿だけ次へ。現行の承認・出版ゲートを勝手に緩めない。

### 既存デザインとの境界

- 現行の暗色系配色、章見出し帯、罫線、共通目次と階層を基準にする。**セクションを勝手に別デザインへ改造しない**。
- 情報の強弱は本文・重要数値・図の使い分けで付ける。全行を同じ太字・サイズ・カードにしない。
- **スマホの本文16px前後**を実装上の検証目安とする。狭い画面で文字を縮めて情報を押し込まず、折り返し・縦配置を優先。iPhoneで長く読むテストを行う。
- 1億件の全HTMLを丸ごとブラウザへ渡さない。1記事を読み込んで共通レンダラーで表示し、検索や一覧は別索引を使う構造が将来の目標。
- 現在採用されたUIの章見出し・共通目次の見た目は勝手に変えず、無内容の章・任意ブロックは表示しない。本文7分類を全件必須への硬直化も、無承認の別UIへの改造もしない。記事が読めるためにJavaScriptが必須になる、全部の記事が縦に連なる、といった退行をしない。

## 5. 品質判定：機械検査と編集品質の両方が必要

**自動で機械的に確かめる項目**
- schemaと識別子、引用・URLの対応、recordKeyと原調査との結びつき、数値・単位・日付・期間の整合性
- 権利の判定、停止対象の非掲載、他社画像の掲載条件、図中の事実の出典
- 図表の描画データが原典の数値と一致すること、異なる期間の不適切なグラフ化がないこと
- モバイル・デスクトップの横はみ出し、文字欠け、図拡大、目次、事例切替、アクセシビリティの基本

**独立したAIレビューと実際の読者評価で確かめる項目**
- 最初の画面から、その商売の姿と最重要点が把握できるか
- 主要な事実が小さな補足へ埋もれず、見た目にも重要度が表現されているか
- 章を移動すると新しい理解があり、冒頭／概要／仕組み／成功理由で同じ話を繰り返していないか
- 情報が多いだけでなく、重要な具体的事実や実際の経緯が十分にあるか
- 利益・原価・本人の手残りなど、存在しない数字を要求したり、曖昧な概算を事実に混ぜたりしていないか
- 書き手だけに分かる省略がないか。音読しても自然な日本語か
- 写真・図・グラフが文章より理解を助けており、同じ内容を重複表示していないか

上記は**目標とテスト観点**。2026-10-14時点、現行の機械検査だけでこれらの編集品質がすべて自動保証されるわけではない。「検査が通る＝有料記事として完成」と報告しない。
