# 新しい事例の収集（調査記録を作る）

あなたは事例の調査担当です。下の対象の事業を、出典つきの事実で調べ、調査記録（JSON の配列）を1つ書きます。
形と必須項目は `docs/research-record/README.md`、見本は `docs/research-record/keygen.example.json`。何を・なぜ集めるかは `docs/OWNER_INTENT.md`。

## 必ず集めるもの
1. 何の事業か（公式サイトを出典にした `kind: DESCRIPTION` を先頭に）。誰に・何を・いくらで売っているか。
2. **創業と転機**: いつ・誰が・なぜ始めたか（`FOUNDING`）、最初の客をどこで得たか（`CHANNEL`）、人数・専業化（`TEAM`）、何を変えた後に伸びたか・売却・調達（`EVENT` `EXIT` `FUNDING`）。料金と利用規約だけの記録は薄い事例になり、章が作れない（storemapper の失敗）。創業者の投稿・インタビュー・Hacker News・Indie Hackers・報道・Web アーカイブの旧ページまで探す。それでも無ければ `reaudit.unknown` に書く。
3. 料金とその変遷、規模の数字（売上・客の数・調達額など、公表されている物）。
4. **一覧の1行の材料**（整形はしない。事実だけ集める。書き方は、この指示の末尾に付けた「オーナーとのやりとりと経緯」（LEAD_LINE_SHEET と OWNER_DIALOGUE_LOG）を読み、決まりだけでなく理由から判断する）。仕組みの説明だけで終わらせず、次の3つを事実で集める。足りなければ `reaudit.unknown` に書く。
   - 使う人が何をできるようになるか、誰のどんな困りごとを解決するか。
   - その会社自身の売上・客の数などの確かな数字（客が得た成果とは別に）。
   - 創業者の人物像（経歴・状況）と、始めた場面。

## 事実の文の書き方（そのまま画面に出る）
書き方の正本は `.claude/skills/natural-japanese/SKILL.md`。**書く前に必ず全部読む**（ここには要点だけ）。
- 1文＝1つの事実。誰が（何が）・何を・どうした／いくらか、が1文で分かる。
- 数字には、何の数字か・いつ時点か・何に対する割合か、を書く。
- 程度の語（よく・ほぼ・かなり）を使わず、割合・金額・件数で書く。数が出典に無ければ「人数は出典に無い」と書く。
- 修飾語を3つ以上つなげない。何が無料で、誰が誰に何のために払うかを書く。固有名詞と専門語は初出で一言説明する。出典の事実を変えない。
- 悪い例: 「Cool Tools経由はよく払い、Reddit経由はほぼ払わなかった」 → 良い例: 「Cool Toolsから来た読者は払う人が多く、Redditから来た読者は払う人がほとんどいなかった。人数は出典に無い」
- 原文の引用は別欄 `quote`（どの事実にも付ける。原文どおり3〜15語）。
- 自己点検: 書いた後に自分の文を英語に戻し（逆翻訳）、出典の英語と意味が合うかを確かめる。

## 数字の決まり（1件ずつすべて付ける）
金額・人数・件数などの数字は `metrics` に1件ずつ書き、次の5点を付ける。数を含む事実の文（`facts`）にも同じ5点を付ける。
- `numberKind`: 何の数字か。`REVENUE`（売上）`GMV`（取扱高）`DIRECT_PAYMENT`（直接の支払い・寄付・スポンサー）`SURVEY_TIER`（アンケートの区分）`FUNDING` `VALUATION` `EXIT` `PROFIT` `PRICE` `USERS` `COST` `OTHER`（`label` に名前）`ESTIMATE`（推定。事実には入らない）
- `asOf`: いつ時点か。**出来事の日付**（`YYYY` / `YYYY-MM` / `YYYY-MM-DD`）。投稿日・記事の日付を使わない。原文に月が無ければ年だけにする（記事の日付から月を推し量らない）。日付の無いページ（料金表など）の今の表示は、取得日の年・月。
- `quote`: 原文をそのまま写した短い引用（英語15語・日本語40字まで）。**数字そのものを含める**。言い換えない・作らない（後で取得した本文と機械で照らす）。
- `sourceUrl`: 引用を取ったページの URL。
- `checkedAt`: 取得日（`YYYY-MM-DD`）。

強い名前（年商・月商・売上・ARR・MRR）は、原文がそう言っている時だけ。直接の支払い・取扱高・アンケートの区分・前身や別事業の数字を売上にしない。
期間の数字（売上・利益・費用）は `periodKind`（`MONTH` `YEAR` `FISCAL_YEAR` `QUARTER` `CUMULATIVE` `TRAILING_DAYS`）を付ける。
外貨は元の通貨のまま（円にしない）。

## 突き合わせ
同じ事例の同じ種類の数字（調達額・月商・客の数など）は、書き終えたら並べて見比べる。同じ時点で金額が違えば出典を見直し、別の数字なら `basis` に何の分か（例「App Store 分だけ」）を書く。食い違いと採った方は `reaudit.conflicts` に書く。

## 出典ごとの権利の記録（必ず書く）
`sources` の各出典に `rights` を付ける。サイトごとに、次の3つを実際にページと規約を見て判断する。
- `loginFree`: ログインなしで本文が読めたか（`yes` / `no` / `unconfirmed`）。
- `noPaywall`: 有料の壁が無いか（同上）。
- `quoteTerms`: 規約が引用や転載を禁じているか。`permits`（許している）/ `prohibits`（禁じている）/ `silent`（規約に書いていない）/ `unconfirmed`。
- `termsUrl`: 見た規約ページの URL（無ければ null）。`note`: 判断の根拠を1〜2文。
判断できない所は `unconfirmed` と書く（公開は止めない）。3つのどれかが `no` / `prohibits` のサイトの事実は画面に出ない（記録には残る）ので、そのサイトだけに頼る事実は、別の出典を探す。台帳は `data/source-rights-ledger.json`、見方は `docs/architecture/RIGHTS_LEDGER.md`。公式サイトの事実は標準の規則があるので `rights` は省略してよい。

## 読めない出典
403・ログインの壁・後から描くページで本文が読めない出典は、引用を取れたことにしない。
1. Web アーカイブ（`https://web.archive.org/web/2024*/<URL>` など）の保存版を開き、取れたら保存版の URL を `sourceUrl` にする。
2. だめなら同じ事実を書いた別の出典（本人の投稿・公式・報道・提出書類）を探す。
3. どれも無ければ、その数字・事実は書かず `reaudit.unknown` に「何が取れなかったか」を書く。

## してはいけないこと
- 分からない数を0や仮の数で埋める。推定を事実の欄に書く（推定は `numberKind: ESTIMATE`。取り込みで事実から外れる）。
- 引用・年・金額を作る。円換算を書く。
- eBiz Facts を出典にする。ログインの壁・CAPTCHA を越える。

## 書き終えたら
1. `node --import tsx scripts/reader-case/add-entity-records.ts --from-research <記録.json> --name <名前>` を実行し、出力の `unconfirmedFacts`（決まりを満たさず取り込まなかった事実・数字）と `thinCases`（創業も転機も無い記録）が0件になるまで直す。
2. 理由は、作られたファイルの各記録の `unconfirmedFacts[].reasonLabels` と `detail`（文の直し方）に書いてある。差し戻しの指示書は `data/runner/instructions/collect-return/<名前>.md`。同じ項目は3回で保留になる。
